HashMap bên trong hoạt động thế nào

Mảng bucket, hàm hash, collision, treeify và resize, đọc thẳng từ source OpenJDK 21.

Sau bài này bạn sẽ Trả lời trọn vẹn câu phỏng vấn kinh điển “Giải thích cơ chế hoạt động của HashMap” với các con số chính xác (16, 0.75, 8, 64) và biết mỗi con số nằm ở dòng nào trong source.
Ôn lại Bài 2–3

(1) HashMap so sánh hash trước hay equals trước? (2) Vì sao key nên là immutable? (3) == giữa hai reference so sánh gì?

Đáp án: (1) So hash trước, rồi mới tới == hoặc equals. (2) Hash được tính và lưu lúc put; sửa key sau đó thì tìm sai ngăn. (3) So hai mũi tên: có cùng object không.

1. Cấu trúc: một mảng các danh sách

Bên trong HashMap có một field Node<K,V>[] table. Mỗi ô của mảng là một bucket, chứa một linked list các Node. Mỗi node gồm hash, key, value và next.

2. put(key, value) từng bước

Bước 1: tính hash và “trộn” bit

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

HashMap.java L336–339. Key null luôn có hash 0, nên HashMap cho phép một key null. Phép ^ (h >>> 16) trộn 16 bit cao xuống 16 bit thấp. Comment trong source giải thích lý do: bảng chỉ dùng các bit thấp để chọn bucket, nên những hash chỉ khác nhau ở bit cao “will always collide” nếu không trộn.

Bước 2: chọn bucket bằng (n - 1) & hash

Với n = 16 thì n − 1 = 15 = 0b1111, nên phép AND giữ lại 4 bit thấp của hash. Kết quả luôn nằm trong 0..15. Khi n là lũy thừa của 2, phép này cho cùng kết quả với chia lấy dư, nhưng nhanh hơn nhiều. Đó là lý do capacity của HashMap luôn là lũy thừa của 2.

Bước 3: bucket rỗng thì đặt node; có rồi thì so sánh

if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);       // bucket rỗng
else {
    if (p.hash == hash &&
        ((k = p.key) == key || (key != null && key.equals(k))))
        e = p;                                       // trùng key ⇒ ghi đè value
    ...                                              // không trùng ⇒ duyệt list, nối vào cuối
}

HashMap.putVal L631–672. Đây chính là chỗ hợp đồng ở Bài 3 phát huy tác dụng.

Bước 4: list quá dài thì treeify

Nếu sau khi nối thêm, bucket có từ TREEIFY_THRESHOLD = 8 node trở lên, HashMap gọi treeifyBin để biến list thành cây đỏ-đen, giúp tìm kiếm còn O(log n) thay vì O(n). Nhưng có một ngoại lệ ít người biết:

if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)   // 64
    resize();

Nếu bảng còn nhỏ hơn 64 ô, HashMap không tạo cây mà gấp đôi bảng để rải node ra. Khi số node trong cây giảm xuống UNTREEIFY_THRESHOLD = 6 (lúc resize), cây được chuyển lại thành list.

Bước 5: quá tải thì resize

if (++size > threshold)        // threshold = capacity × loadFactor
    resize();                  // gấp đôi table, chia lại các node

Mặc định DEFAULT_INITIAL_CAPACITY = 16 và DEFAULT_LOAD_FACTOR = 0.75, nên threshold là 12. Kết quả chạy thật:

sau new HashMap()   : table.length = 0      ← chưa cấp phát (lazy)
put thứ 1           : table.length 0 -> 16
put thứ 13          : table.length 16 -> 32
put thứ 25          : table.length 32 -> 64
Hệ quả thực tế: nếu biết trước sẽ chứa khoảng 1000 phần tử, hãy dùng HashMap.newHashMap(1000) (có từ Java 19) để tránh nhiều lần resize liên tiếp.

3. get(key) và độ phức tạp

get đi lại đúng bước 1–3: tính hash, chọn bucket, rồi so hash và equals dọc theo list hoặc cây. Trung bình là O(1). Nếu rất nhiều key collide vào một bucket thì list cho O(n), còn cây cho O(log n). Vì vậy một hashCode tệ, ví dụ luôn return 1, vẫn đúng hợp đồng nhưng biến HashMap thành chậm như duyệt list.

Lưu ý: HashMap không thread-safe. Nhiều thread cùng put có thể làm mất dữ liệu. Môi trường đa luồng thì dùng ConcurrentHashMap; chủ đề này sẽ có ở phần concurrency.

4. Luyện tập

Q1 (ôn Bài 1). Mảng table của một HashMap nằm ở đâu?

Mảng là object nên luôn nằm trên heap. Field table của HashMap chỉ giữ mũi tên trỏ tới nó.

Q2. Ngay sau new HashMap<>(), mảng table đã được cấp phát chưa?

table là null cho tới put đầu tiên, khi đó resize() mới tạo mảng 16 ô (lazy initialization).

Q3. Bảng có 16 ô, hash (đã trộn) của key là 37. Key vào bucket nào?

37 = 0b100101, AND với 0b1111 ra 0b0101 = 5. Cũng bằng 37 % 16.

Q4. HashMap mặc định resize lần đầu (16 lên 32) ở lần put thứ mấy?

threshold = 16 × 0.75 = 12. Điều kiện là ++size > threshold, nên resize xảy ra khi size thành 13.

Q5. Bảng dài 16, một bucket đã có 8 node, put thêm key thứ 9 vào bucket đó. HashMap làm gì?

Node mới được nối vào list, rồi treeifyBin được gọi. Nhưng vì 16 < MIN_TREEIFY_CAPACITY (64), nó gọi resize() thay vì tạo cây.

Q6. Vì sao capacity của HashMap luôn là lũy thừa của 2?

Với n = 2^k thì (n-1) & hash cho cùng kết quả với hash % n (khi hash không âm) nhưng nhanh hơn nhiều, và luôn ra chỉ số hợp lệ kể cả khi hash âm.

5. Chạy thử

java --add-opens java.base/java.util=ALL-UNNAMED lessons/code/L0004HashMapInside.java

Cờ --add-opens cho phép reflection đọc field private table (mở file). Thử thêm: đổi vòng lặp thành new HashMap<>(100) và đoán xem table.length ban đầu sẽ là bao nhiêu (gợi ý: lũy thừa của 2 gần nhất ≥ 100).
