Transaction không có rollback

Ở bài 2 bạn đã biết pipeline không nguyên tử. Giờ là các công cụ cho tính nguyên tử: MULTI/EXEC, WATCH và Lua. Mỗi công cụ có một cái bẫy riêng. ~18 phút.

Sau bài này bạn sẽ Tự tay thấy một transaction "thành công một nửa", dùng WATCH để chặn lost update, và hiểu vì sao một script Lua viết dở có thể làm treo cả Redis.

1. MULTI/EXEC: xếp hàng rồi chạy liền một mạch

Sau MULTI, các lệnh chưa chạy mà chỉ được xếp hàng (Redis trả về QUEUED). Tới EXEC, cả khối chạy liền một mạch trên luồng chính, và không lệnh nào của client khác chen vào giữa được. Đó là phần "nguyên tử" của transaction.

Nhưng có một điểm khác hẳn transaction của database SQL: Redis không hỗ trợ rollback. Nếu một lệnh lỗi khi đang chạy, các lệnh còn lại vẫn chạy.

Lỗi xảy ra khiVí dụKết quả
Xếp hàng (trước EXEC)Sai tên lệnh, sai số tham sốEXECABORT: cả transaction bị huỷ, không lệnh nào chạy
Thực thi (trong EXEC)INCR lên một chuỗi không phải sốLệnh đó báo lỗi, các lệnh khác vẫn được ghi

2. WATCH: khoá lạc quan

Bài toán: đọc số dư, tính toán trong app, rồi ghi lại. Nếu giữa lúc đọc và lúc ghi có client khác sửa số dư, bản ghi của bạn sẽ đè mất thay đổi của họ (lost update). WATCH key giải quyết việc này: nếu key bị sửa trước EXEC, thì EXEC trả về nil và không ghi gì cả. App phải tự thử lại.

3. Lua: nguyên tử thật sự, và nguy hiểm thật sự

Script Lua (EVAL) chạy trọn vẹn trên server như một lệnh duy nhất. Script có thể đọc dữ liệu, rẽ nhánh rồi ghi, tất cả nguyên tử. Đây là cách viết các thao tác như "trừ tồn kho nếu còn hàng" hay rate limiter.

Cái giá: trong lúc script chạy, luồng chính bị chiếm hoàn toàn (đúng mô hình ở bài 1). Script chạy quá busy-reply-threshold (mặc định 5000 ms) thì Redis bắt đầu trả lỗi BUSY cho mọi client khác. AWS cũng khuyên giữ script Lua ngắn và khai báo trước mọi key script dùng, để ở cluster mode các key đó nằm cùng một hash slot.

4. Lab (~8 phút)

  1. Transaction thành công một nửa: 
    docker exec -it redis-lab redis-cli
SET s hello
MULTI
SET a 1          QUEUED
INCR s           QUEUED   ← sẽ lỗi khi chạy
SET b 2          QUEUED
EXEC
1) OK
2) (error) ERR value is not an integer or out of range
3) OK
MGET a b         1) "1"  2) "2"   ← a và b vẫn được ghi
  2. Lỗi lúc xếp hàng thì huỷ cả khối: 
    MULTI
SET c 1
NOTACOMMAND      (error) ERR unknown command …
EXEC             (error) EXECABORT Transaction discarded because of previous errors.
GET c            (nil)
  3. WATCH chặn lost update. Mở hai terminal redis-cli: 
    # Terminal 1
SET bal 100
WATCH bal
GET bal                    "100"
# Terminal 2
SET bal 500
# Terminal 1
MULTI
SET bal 90
EXEC                       (nil)   ← bị huỷ vì bal đã đổi
GET bal                    "500"   ← thay đổi của terminal 2 được giữ nguyên
  4. Lua chiếm luồng chính. Terminal 1 chạy một script bận 7 giây: 
    docker exec redis-lab redis-cli EVAL "local t=redis.call('TIME')[1]+0; while redis.call('TIME')[1]+0 < t+7 do end return 1" 0
    Sau hơn 5 giây, ở terminal 2: 
    docker exec redis-lab redis-cli GET bal
(error) BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.
docker exec redis-lab redis-cli SCRIPT KILL   OK
    SCRIPT KILL chỉ dừng được script chưa ghi dữ liệu. Script đã ghi rồi thì chỉ còn cách SHUTDOWN NOSAVE, tức là tắt server.

5. Tự kiểm tra

Điểm: 0/5

Trong EXEC, lệnh thứ 2 trên 3 bị lỗi kiểu dữ liệu. Lệnh 1 và lệnh 3 thì sao?

Redis không rollback. Lỗi lúc thực thi chỉ ảnh hưởng đúng lệnh đó, các lệnh khác trong khối vẫn chạy.

Sau WATCH stock, client khác sửa stock trước khi bạn gọi EXEC. Điều gì xảy ra?

WATCH là khoá lạc quan: không chặn ai, chỉ huỷ EXEC nếu key đã đổi. App phải tự thử lại.

Script Lua chạy 8 giây trên production. Các client khác gặp gì?

Lua chạy trên luồng chính. Quá busy-reply-threshold (5000 ms), Redis trả BUSY cho mọi lệnh khác ngoài SCRIPT KILL/SHUTDOWN NOSAVE.

Cần "trừ tồn kho chỉ khi còn hàng" một cách nguyên tử, nhanh, ít đi về. Chọn gì?

Pipeline không nguyên tử. Trong MULTI, GET chỉ trả về QUEUED nên không rẽ nhánh theo giá trị được. Lua đọc, kiểm tra, rồi ghi trong một bước.

Ôn bài 4: Key cache có TTL, sau khi cập nhật thì TTL trả về -1. Nguyên nhân có khả năng nhất?

-1 nghĩa là key tồn tại nhưng không có hạn (bị xoá thì phải là -2). Lệnh ghi đè như SET xoá TTL.
