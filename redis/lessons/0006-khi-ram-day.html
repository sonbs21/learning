Khi RAM đầy

maxmemory và eviction policy quyết định Redis sẽ xoá bớt key hay từ chối ghi. Chọn sai là app bắt đầu nhận lỗi OOM. ~15 phút.

Sau bài này bạn sẽ Tái hiện lỗi OOM command not allowed, hiểu vì sao policy mặc định của ElastiCache (volatile-lru) vẫn có thể ném lỗi OOM, và chọn đúng policy cho một cache.

1. maxmemory: trần bộ nhớ

maxmemory là giới hạn RAM dành cho dữ liệu. Chạm trần thì Redis làm theo maxmemory-policy. Redis tự host mặc định là maxmemory 0 (không giới hạn) và noeviction; bạn sẽ kiểm tra lại trong lab.

PolicyXoá key nào khi đầyHợp với
noevictionKhông xoá; lệnh ghi bị từ chối, lệnh đọc vẫn chạyDữ liệu không được mất (queue, store chính)
allkeys-lruKey lâu nhất không được dùng, xét trên mọi keyCache thuần
allkeys-lfuKey ít được dùng nhất, xét trên mọi keyCache có tập key "nóng" ổn định
volatile-lru / -lfu / -ttl / -randomChỉ xét các key có TTLTrộn cache (có TTL) với dữ liệu cần giữ (không TTL)
allkeys-randomNgẫu nhiên trên mọi keyHiếm khi dùng

Hai chi tiết quan trọng từ tài liệu eviction:

  • LRU chỉ là xấp xỉ. Redis không theo dõi chính xác thứ tự truy cập của mọi key. Nó lấy ngẫu nhiên maxmemory-samples key (mặc định 5) và xoá key "già" nhất trong mẫu đó.
  • Các policy volatile-* hoạt động như noeviction khi không có key nào có TTL. Đây chính là bẫy.

2. Lab (~6 phút)

  1. Xem cấu hình mặc định, rồi đặt trần thật nhỏ: 
    docker exec -it redis-lab redis-cli
CONFIG GET maxmemory            0
CONFIG GET maxmemory-policy     noeviction
CONFIG GET maxmemory-samples    5
FLUSHALL
CONFIG SET maxmemory 2mb
  2. Thoát ra shell, nạp 100 000 key không có TTL: 
    docker exec redis-lab redis-cli EVAL "for i=1,100000 do redis.call('SET','k:'..i,string.rep('x',100)) end" 0

    Bạn sẽ thấy script này nạp được cả 100 000 key, vượt xa 2 MB. Lý do: Redis chỉ kiểm tra bộ nhớ lúc script bắt đầu, rồi để script chạy trọn vẹn cho đảm bảo nguyên tử. Hiện tượng phụ, nhưng đáng biết.

  3. Giờ RAM đã vượt trần. Thử từng policy: 
    SET one more                         (error) OOM command not allowed when used memory > 'maxmemory'.
CONFIG SET maxmemory-policy volatile-lru
SET two more                         (error) OOM …   ← không key nào có TTL nên không có gì để xoá
CONFIG SET maxmemory-policy allkeys-lru
SET three more                       OK
INFO stats                           evicted_keys:84544   ← xoá hàng loạt trong một lần ghi
DBSIZE                               ~1094
CONFIG SET maxmemory 0

Chú ý dòng evicted_keys:84544: việc xoá key được thực hiện ngay trong lệnh ghi, trên luồng chính. Khi RAM vượt trần xa (ví dụ ai đó hạ maxmemory đột ngột), một lệnh SET có thể phải xoá hàng chục nghìn key trước khi trả về.

3. ElastiCache: bẫy volatile-lru

Theo AWS, policy mặc định trong parameter group của ElastiCache là volatile-lru. Nếu code lưu key không kèm TTL (lỗi mất TTL ở bài 4!), thì khi RAM đầy, Redis không có key nào để xoá và app sẽ nhận lỗi OOM. Có hai cách xử lý:

  • Đảm bảo mọi key cache đều có TTL, hoặc
  • Nếu cluster chỉ dùng làm cache, tạo custom parameter group với allkeys-lru. AWS không cho sửa parameter group mặc định (docs).

Theo dõi bằng metric Evictions và mức dùng bộ nhớ trên CloudWatch (metric nên theo dõi). Evictions tăng đều đặn nghĩa là cache quá nhỏ so với tập dữ liệu "nóng".

4. Tự kiểm tra

Điểm: 0/5

ElastiCache dùng volatile-lru, RAM đầy, app nhận lỗi OOM khi ghi. Nguyên nhân có khả năng nhất?

Các policy volatile-* chỉ xoá key có TTL. Không có key nào có TTL thì chúng hoạt động như noeviction.

Redis dùng làm hàng đợi job, mất job là không chấp nhận được. Chọn policy nào?

Eviction là im lặng xoá dữ liệu. Với dữ liệu không được mất, thà báo lỗi ghi (rồi cảnh báo và scale) còn hơn mất job mà không ai biết.

Redis chọn key để xoá theo allkeys-lru như thế nào?

LRU xấp xỉ: lấy maxmemory-samples key (mặc định 5). Duyệt toàn bộ sẽ là thao tác O(N) chặn luồng chính.

Vì sao hạ maxmemory đột ngột trên production có thể gây spike latency?

Eviction chạy ngay trong lệnh ghi trên luồng chính. Lab cho thấy một lệnh SET đã xoá 84 544 key.

Ôn bài 5: Transaction có 3 lệnh. Lệnh 2 sai tên lệnh (phát hiện ngay lúc xếp hàng). Khi gọi EXEC thì sao?

Lỗi lúc xếp hàng thì cả transaction bị huỷ. Chỉ lỗi lúc thực thi mới cho kết quả "thành công một nửa".
