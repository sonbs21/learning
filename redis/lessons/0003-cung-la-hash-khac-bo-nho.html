Cùng là HASH, khác 4.6 lần bộ nhớ

Bên dưới mỗi data type, Redis âm thầm chọn một cấu trúc lưu trữ. Thêm đúng một field có thể làm key to gấp mấy lần. ~15 phút.

Sau bài này bạn sẽ Dùng OBJECT ENCODING và MEMORY USAGE để nhìn vào bên trong một key, và giải thích được vì sao một hash 513 field tốn bộ nhớ gấp 4.6 lần hash 512 field.

1. Type là thứ bạn thấy, encoding là thứ nằm trong RAM

Khi bạn gọi HSET, bạn làm việc với kiểu hash. Nhưng Redis tự chọn cách lưu hash đó trong RAM, gọi là encoding. Việc chọn này hoàn toàn trong suốt với API: lệnh của bạn vẫn y nguyên, chỉ có bộ nhớ và CPU là khác.

TypeEncoding khi nhỏEncoding khi lớn
stringint (số nguyên), embstr (chuỗi ngắn)raw

setintset (toàn số nguyên), listpackhashtable

Tên encoding theo OBJECT ENCODING cho Redis 7.x. Redis 6.2 trở về trước gọi listpack là ziplist; bạn vẫn sẽ gặp tên này trong tài liệu cũ và trong cấu hình.

Listpack: mảng nén, đổi CPU lấy RAM

Listpack xếp các phần tử liền nhau trong một khối bộ nhớ, không có con trỏ, không có bucket. Rất tiết kiệm RAM, docs cho biết tiết kiệm tới 10 lần, trung bình khoảng 5 lần. Cái giá: muốn tìm một field phải duyệt tuần tự, độ phức tạp O(N). Với N nhỏ thì không đáng kể. Với N lớn thì luồng chính bị chiếm lâu, và bạn đã biết chuyện đó dẫn tới đâu ở bài 1.

Vì vậy Redis đặt ngưỡng. Vượt ngưỡng, key tự chuyển sang hashtable (tra cứu O(1) nhưng tốn RAM hơn nhiều). Ngưỡng mặc định trên Redis 7.4 (đo bằng CONFIG GET khi soạn bài):

hash-max-listpack-entries   512   ← tối đa số field
hash-max-listpack-value     64    ← tối đa độ dài một field/value (byte)
set-max-intset-entries      512
set-max-listpack-entries    128
zset-max-listpack-entries   128

Một số blog ghi hash-max-listpack-entries mặc định là 128. Trên Redis 7.4 giá trị này là 512. Luôn kiểm tra bằng CONFIG GET trên đúng phiên bản bạn chạy.

2. Lab: nhìn tận mắt (~7 phút)

  1. Vào redis-cli (container từ bài trước): 
    docker exec -it redis-lab redis-cli
  2. Encoding của string: 
    SET n 12345        →  OBJECT ENCODING n   "int"
SET s hello        →  OBJECT ENCODING s   "embstr"
  3. Tạo hash 512 field và hash 513 field. Thoát redis-cli rồi chạy ở shell (gửi lệnh hàng loạt qua stdin): 
    for i in $(seq 1 512); do echo "HSET h512 f$i v$i"; done | docker exec -i redis-lab redis-cli > /dev/null
for i in $(seq 1 513); do echo "HSET h513 f$i v$i"; done | docker exec -i redis-lab redis-cli > /dev/null
  4. So sánh: 
    docker exec redis-lab redis-cli OBJECT ENCODING h512   "listpack"
docker exec redis-lab redis-cli MEMORY USAGE h512      6192   (byte)
docker exec redis-lab redis-cli OBJECT ENCODING h513   "hashtable"
docker exec redis-lab redis-cli MEMORY USAGE h513      28816  (byte)  ← gấp 4.6 lần, chỉ vì thêm 1 field
  5. Thí nghiệm then chốt: xoá bớt field của h513 cho tới khi chỉ còn 1: 
    for i in $(seq 2 513); do echo "HDEL h513 f$i"; done | docker exec -i redis-lab redis-cli > /dev/null
docker exec redis-lab redis-cli HLEN h513              1
docker exec redis-lab redis-cli OBJECT ENCODING h513   "hashtable"  ← không quay về listpack
    Đã chuyển sang hashtable thì key ở luôn đó trong lúc server đang chạy. Chỉ một lần phình to tạm thời cũng để lại chi phí lâu dài.
  6. Bẫy thứ hai: chỉ một value dài hơn 64 byte cũng đủ chuyển cả hash: 
    HSET user:2 name son
HSET user:2 bio "<một chuỗi dài 65 ký tự>"
OBJECT ENCODING user:2   "hashtable"

3. Hệ quả trên production

  • Ước tính RAM sai. Bạn test với 100 field/user, rồi production có user 600 field: mỗi key to gấp nhiều lần dự tính. Trên ElastiCache, kích cỡ node (và tiền) dựa trên RAM, nên đây là bài toán chi phí thật.
  • Một field "lạc loài" phá cả key. Nhét một chuỗi JSON dài vào một field là cả hash chuyển sang hashtable.
  • Đừng tăng ngưỡng bừa. Tăng hash-max-listpack-entries lên 10000 tiết kiệm RAM nhưng mỗi HGET phải duyệt tuần tự hàng nghìn phần tử trên luồng chính. Docs khuyên benchmark trước khi tăng ngưỡng nhiều.
  • Trên ElastiCache bạn không sửa được redis.conf; cấu hình đi qua parameter group (sẽ học ở phần ElastiCache).

4. Tự kiểm tra

Điểm: 0/5

Hash đang có 300 field ngắn. Bạn thêm một field có value dài 200 byte. Điều gì xảy ra?

Ngưỡng hash-max-listpack-value (64 byte) áp dụng cho từng phần tử. Một phần tử vượt ngưỡng là cả key chuyển encoding. Redis không từ chối ghi.

Một hash phình lên 2000 field rồi bị xoá còn 10 field. Encoding bây giờ là gì?

Bạn đã tự kiểm chứng trong lab: xoá bớt không làm key quay về listpack trong lúc server đang chạy.

Vì sao Redis không dùng listpack cho mọi kích thước?

Listpack là mảng liền nhau, phải duyệt tuần tự. N lớn thì mỗi lệnh chiếm luồng chính lâu, làm chậm mọi client.

Lệnh nào cho biết một key đang chiếm bao nhiêu byte RAM?

OBJECT ENCODING cho biết cấu trúc lưu trữ; HLEN/STRLEN cho biết số phần tử hoặc độ dài; MEMORY USAGE mới trả về số byte.

Ôn bài 2: Endpoint đọc cache cho 50 sản phẩm bằng vòng lặp GET. Cách sửa tốt nhất?

Thủ phạm là 50 lần đi và về, không phải CPU của Redis. MGET (hoặc pipeline) giảm xuống còn 1 RTT.
