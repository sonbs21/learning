Kẻ thù là round-trip

Redis chạy một lệnh mất chưa tới một micro-giây. Thứ làm app của bạn chậm gần như luôn là đường mạng. ~15 phút.

Sau bài này bạn sẽ Đo được throughput tăng gấp ~8–10 lần nhờ pipelining trên chính máy bạn, và nhận ra được lỗi "N+1 với Redis", một lỗi rất hay gặp trên production.

1. Một lệnh tốn thời gian ở đâu?

Ở bài 1, bạn đã biết luồng chính chạy lệnh rất nhanh. Nhưng nhìn từ phía app, mỗi lệnh phải đi trọn một vòng: gửi qua mạng, xếp hàng, thực thi, rồi gửi kết quả về. Khoảng thời gian một vòng đi và về đó gọi là RTT (round-trip time).

Tài liệu Redis đưa ví dụ cực đoan: với RTT 250 ms, một client chỉ gửi được 4 lệnh mỗi giây, dù server xử lý được 100k lệnh/giây. Trong cùng một VPC, RTT nhỏ hơn rất nhiều, nhưng nguyên lý vẫn vậy: số lần đi và về quyết định tốc độ.

Pipelining còn giúp chính server

Mỗi lệnh gửi riêng lẻ khiến Redis tốn một lần read() và một lần write(), tức là các syscall chui xuống kernel. Khi pipeline, Redis đọc nhiều lệnh trong một read() và trả nhiều kết quả trong một write(), nên throughput có thể tăng tới khoảng 10 lần. Nghĩa là pipelining giảm tải cho luồng chính, chứ không chỉ tiết kiệm thời gian mạng.

Hai điều phải nhớ

  • Pipeline không phải transaction. Lệnh của client khác vẫn có thể chen vào giữa các lệnh trong pipeline của bạn. Cần tính nguyên tử (atomic) thì dùng MULTI/Lua, sẽ học ở bài sau.
  • Đừng pipeline vô hạn. Server phải giữ toàn bộ kết quả trong RAM cho tới khi gửi xong. Docs khuyên chia thành từng mẻ cỡ hợp lý, ví dụ 10k lệnh.

2. Lab: đo bằng redis-benchmark (~5 phút)

  1. Khởi động lại container của bài 1 nếu đã xoá: 
    docker run -d --name redis-lab -p 6379:6379 redis:7.4 --enable-debug-command yes
  2. Đo khi không pipeline (mặc định 50 client chạy song song): 
    docker exec redis-lab redis-benchmark -q -t set,get -n 200000
SET: ~200000 requests per second
GET: ~200000 requests per second
  3. Đo lại, mỗi client pipeline 16 lệnh một lần (-P 16): 
    docker exec redis-lab redis-benchmark -q -t set,get -n 200000 -P 16
SET: ~1700000 requests per second
GET: ~2000000 requests per second
    Con số trên là kết quả đo thật khi soạn bài; máy bạn sẽ khác, nhưng tỷ lệ chênh lệch thường tương tự. Lưu ý benchmark chạy bên trong container nên RTT gần bằng 0. Mức tăng ở đây chủ yếu đến từ việc giảm syscall. Qua mạng thật, chênh lệch còn lớn hơn.

3. Trên production: lỗi N+1 với Redis

Trang danh sách hiển thị 100 sản phẩm, và code lấy cache cho từng sản phẩm:

// ❌ 100 lần đi và về
for (String id : productIds) {
    redisTemplate.opsForValue().get("product:" + id);
}

// ✅ 1 lần: MGET là một lệnh duy nhất
redisTemplate.opsForValue().multiGet(keys);

// ✅ Nhiều loại lệnh khác nhau: pipeline (callback bắt buộc trả về null)
List<Object> results = redisTemplate.executePipelined(new SessionCallback<Object>() {
    public Object execute(RedisOperations ops) {
        for (String id : productIds) ops.opsForHash().entries("product:" + id);
        return null;
    }
});

API executePipelined theo tài liệu Spring Data Redis. Với Redis Cluster, Spring Data Redis chỉ hỗ trợ pipeline qua driver Lettuce (mặc định của Spring Boot).

Nối sang ElastiCache: app chạy trên ECS/EC2 khác AZ với node ElastiCache sẽ có RTT lớn hơn chạy cùng AZ. Lỗi N+1 nhân con số đó lên 100 lần. AWS cũng khuyên tái sử dụng connection (connection pool), vì mở connection mới tốn cả thời gian lẫn CPU của cache.

4. Tự kiểm tra

Điểm: 0/5

API gọi Redis 100 lần tuần tự, mỗi lần RTT 1 ms. Thời gian chờ Redis tối thiểu là bao nhiêu?

Thời gian thực thi gần như bằng 0; mỗi lệnh tuần tự tốn trọn một RTT. 100 × 1 ms = 100 ms. Dùng MGET hoặc pipeline thì chỉ còn khoảng 1 ms.

Ngoài giảm thời gian mạng, pipelining giúp server Redis thế nào?

Lệnh vẫn chạy tuần tự trên luồng chính, nhưng một read() đọc được nhiều lệnh và một write() trả được nhiều kết quả, nên CPU tốn cho syscall giảm hẳn.

Pipeline gồm GET balance rồi SET balance. Client khác có thể ghi vào balance ở giữa hai lệnh không?

Pipeline chỉ là cách gửi lệnh. Lệnh của client khác vẫn có thể chen vào giữa. Cần nguyên tử thì dùng MULTI/EXEC hoặc Lua.

Vì sao không nên nhét 5 triệu lệnh vào một pipeline duy nhất?

Server đệm toàn bộ kết quả cho tới khi gửi đi, nên bộ nhớ dùng cho output buffer có thể phình to. Chia mẻ khoảng 10k lệnh.

Ôn bài 1: Redis bỗng chậm với mọi client. Lệnh nào nên chạy đầu tiên để tìm thủ phạm?

Slow log cho biết lệnh nào đã chiếm luồng chính lâu, kèm client gửi lệnh đó. Còn KEYS * thì chính nó là một thủ phạm.
