Key hết hạn thế nào

TTL về 0 không có nghĩa là key biến mất ngay lúc đó. Và chỉ một lệnh SET vô tình cũng xoá mất TTL của key. ~15 phút.

Sau bài này bạn sẽ Giải thích được hai cơ chế xoá key hết hạn, quan sát Redis tự dọn 100 000 key không ai đọc tới, và tránh được hai lỗi production: mất TTL khi ghi đè và hàng loạt key hết hạn cùng lúc.

1. Hai cơ chế: thụ động và chủ động

Redis không đặt hẹn giờ riêng cho từng key, vì hàng triệu bộ hẹn giờ sẽ tốn quá nhiều chi phí. Thay vào đó, Redis dùng hai cơ chế:

Cơ chếKhi nào chạyĐiểm yếu
Passive (thụ động)Khi có client truy cập key, Redis kiểm tra key đã hết hạn chưa. Hết hạn thì xoá luôn và trả về nil.Key không ai đọc tới sẽ nằm mãi trong RAM.
Active (chủ động)Định kỳ, Redis lấy ngẫu nhiên một số key có TTL ra kiểm tra và xoá những key đã hết hạn. Nếu tỷ lệ hết hạn trong mẫu cao thì lặp lại ngay.Là lấy mẫu xác suất: luôn còn một phần nhỏ key "đã chết" chưa bị dọn.

Tần suất chạy của cơ chế active gắn với tham số hz, mặc định là 10 (10 lần mỗi giây). Bạn sẽ kiểm tra giá trị này trong lab. Tài liệu bản cũ mô tả chi tiết thuật toán: lấy 20 key, nếu trên 25% đã hết hạn thì lặp lại. Các con số này có thể đã thay đổi ở phiên bản mới, nên đừng học thuộc. Chỉ cần nhớ đây là lấy mẫu ngẫu nhiên và tự điều chỉnh.

Replica không tự xoá key hết hạn

Khi key hết hạn trên primary, primary gửi lệnh DEL xuống các replica (và ghi vào AOF). Replica không tự xoá key mà chờ lệnh DEL từ master. Mọi việc xoá key hết hạn đều do một nơi quyết định. Bạn sẽ gặp lại chi tiết này ở phần replication.

2. Lab (~6 phút)

  1. Tham số của cơ chế active: 
    docker exec redis-lab redis-cli CONFIG GET hz                    10
docker exec redis-lab redis-cli CONFIG GET active-expire-effort  1   (thang 1–10, càng cao càng dọn mạnh, càng tốn CPU)
  2. Tạo 100 000 key sống 2 giây, rồi không đọc tới chúng nữa. Script Lua chạy vòng lặp ngay trên server, nên không tốn 100 000 lần đi về (nhớ lại bài 2): 
    docker exec redis-lab redis-cli EVAL "for i=1,100000 do redis.call('SET','tmp:'..i,'x','EX',2) end" 0
docker exec redis-lab redis-cli INFO keyspace
db0:keys=100000,expires=100000,avg_ttl=1850
  3. Đợi 3 giây rồi xem lại: 
    docker exec redis-lab redis-cli DBSIZE                       0
docker exec redis-lab redis-cli INFO stats | grep expired_   expired_keys:100000 …
    Không client nào đọc tới các key đó, vậy mà chúng vẫn bị xoá. Đó là cơ chế active.
  4. Bẫy mất TTL. Ghi đè bằng SET sẽ xoá TTL; lệnh sửa tại chỗ như INCR thì giữ nguyên (docs EXPIRE): 
    SET counter 1 EX 100
INCR counter        →  TTL counter   ~100  (giữ TTL)
SET counter 5       →  TTL counter   -1    (TTL đã mất!)

3. Hai lỗi production kinh điển

Lỗi 1: mất TTL vì ghi đè

// Lần đầu: có TTL
redisTemplate.opsForValue().set("product:7", json, Duration.ofMinutes(10));
// Ở chỗ khác, khi cập nhật: quên TTL → key thành vĩnh viễn
redisTemplate.opsForValue().set("product:7", newJson);

Hệ quả: RAM tăng dần mãi, dữ liệu cũ không bao giờ hết hạn. Tìm ra bằng TTL key trả về -1 (đã học ở bài 1), hoặc so sánh keys với expires trong INFO keyspace.

Lỗi 2: hàng loạt key hết hạn cùng một lúc

Job warm-up nạp 1 triệu key lúc 00:00, tất cả EX 3600. Đúng 01:00, chúng hết hạn cùng lúc, mọi request đều miss cache và đổ thẳng xuống database. Hiện tượng này gọi là cache avalanche. Cách phòng phổ biến là cộng thêm một khoảng ngẫu nhiên (jitter) vào TTL, ví dụ 3600 + random(0..300), để các key hết hạn rải rác. Phần pattern sẽ đào sâu chủ đề này.

4. Tự kiểm tra

Điểm: 0/5

Có 1 triệu key đã hết hạn và không client nào đọc lại. Điều gì sẽ dọn chúng khỏi RAM?

Passive chỉ chạy khi có client truy cập. Key không ai đọc tới được cơ chế active dọn dần, đúng như lab: DBSIZE về 0 dù không ai đọc.

Key có EX 600. Code chạy SET key newValue (không kèm EX). TTL bây giờ là bao nhiêu?

Lệnh ghi đè toàn bộ value sẽ xoá timeout. Luôn truyền Duration khi set lại một key cache.

Primary và replica: key session:9 vừa hết hạn. Ai xoá key đó trên replica?

Việc xoá key hết hạn do master quyết định: master sinh lệnh DEL và gửi cho replica (và AOF).

1 triệu key cùng EX 3600 được nạp cùng lúc. Một giờ sau DB bị quá tải. Cách phòng nào hợp lý?

Vấn đề là các key hết hạn đồng loạt. Jitter rải thời điểm hết hạn ra. Bỏ TTL thì RAM phình mãi; tăng hz không giải quyết được việc miss cache đồng loạt.

Ôn bài 3: Lệnh nào cho biết hash user:1 đang được lưu dạng listpack hay hashtable?

TYPE chỉ trả về "hash"; MEMORY USAGE trả về số byte; OBJECT ENCODING mới cho biết cấu trúc bên trong.
