AOF và câu hỏi "mất bao nhiêu dữ liệu?"

RDB có thể làm mất dữ liệu của vài phút. AOF thu hẹp con số đó xuống còn khoảng một giây. Còn trên ElastiCache thì câu trả lời lại khác. ~15 phút.

Sau bài này bạn sẽ Mở file AOF ra đọc tận mắt, chọn được appendfsync phù hợp, và trả lời được câu hỏi khi thiết kế hệ thống: "Redis sập thì mất tối đa bao nhiêu dữ liệu?"

1. AOF: ghi lại mọi lệnh ghi

Thay vì chụp ảnh định kỳ như RDB, AOF (append-only file) ghi nối đuôi mọi lệnh ghi mà server nhận được. Khi khởi động lại, Redis chạy lại toàn bộ log để dựng lại dữ liệu.

Điểm mấu chốt là khi nào dữ liệu thật sự xuống đĩa. Ghi vào file chỉ là ghi vào bộ đệm của kernel; phải fsync thì mới chắc chắn nằm trên đĩa:

appendfsyncfsync khi nàoMất tối đa khi sậpHiệu năng
alwaysSau mỗi lệnh ghiGần như không mấtChậm nhất
everysec (mặc định)Mỗi giây một lần~1 giây dữ liệuGần bằng không có AOF
noĐể hệ điều hành tự quyếtCó thể nhiều giâyNhanh nhất

Rewrite: chống phình file

INCR visits chạy một triệu lần thì log có một triệu dòng, nhưng trạng thái cuối chỉ là một con số. AOF rewrite viết lại log thành dạng gọn nhất. Rewrite cũng dùng fork(), nên mang theo đúng những cái giá bạn đã học ở bài 7. Từ Redis 7, AOF gồm nhiều file: một file base (dạng RDB), một file incr (các lệnh mới) và một manifest liệt kê chúng.

RDB hay AOF?

Có thể bật cả hai cùng lúc. RDB gọn, khởi động nhanh, tiện backup. AOF mất ít dữ liệu hơn. Nếu Redis chỉ là cache có thể dựng lại từ database, thường không cần AOF.

2. Lab (~5 phút)

  1. Bật AOF khi đang chạy rồi ghi vài lệnh: 
    docker exec redis-lab redis-cli CONFIG GET appendfsync    everysec
docker exec redis-lab redis-cli CONFIG SET appendonly yes
docker exec redis-lab redis-cli SET hello world
docker exec redis-lab redis-cli INCR visits
docker exec redis-lab redis-cli INCR visits
docker exec redis-lab ls /data/appendonlydir
appendonly.aof.1.base.rdb  appendonly.aof.1.incr.aof  appendonly.aof.manifest
  2. Đọc file incr. Đây chính là giao thức RESP mà client gửi lên: 
    docker exec redis-lab sh -c 'cat /data/appendonlydir/*.incr.aof'
*3        ← mảng 3 phần tử
$3        ← chuỗi dài 3 byte
SET
$5
hello
$5
world
*2
$4
INCR
$6
visits
…
    Hai lệnh INCR được lưu thành hai mục riêng: log ghi lại lệnh, không ghi lại trạng thái.
  3. Rewrite rồi xem manifest: 
    docker exec redis-lab redis-cli BGREWRITEAOF
docker exec redis-lab cat /data/appendonlydir/appendonly.aof.manifest
file appendonly.aof.2.base.rdb seq 2 type b
file appendonly.aof.2.incr.aof seq 2 type i
    Dữ liệu cũ được gộp vào base mới (seq 2), file incr bắt đầu lại từ đầu.

3. ElastiCache: độ bền đến từ replica, không phải đĩa

Trên một node đơn, AOF nằm trên đĩa của chính node đó, tức là trong một AZ duy nhất. AWS chỉ ra rủi ro mất dữ liệu khi AOF chỉ nằm cục bộ trên primary. Cách AWS khuyến nghị cho Redis OSS/Valkey là bật Multi-AZ với replica: primary chết thì replica ở AZ khác được promote lên.

Cái bẫy: replication là bất đồng bộ. Những lệnh ghi primary đã trả OK nhưng chưa kịp sang replica sẽ mất khi failover. Nếu cần độ bền cao hơn, có các lựa chọn riêng: tính năng durability của ElastiCache, với yêu cầu Valkey 9.0+, Multi-AZ và cluster mode, hoặc dịch vụ MemoryDB. Hãy kiểm tra docs hiện hành trước khi quyết định.

Quy tắc thiết kế Mặc định coi Redis là cache: mất dữ liệu thì dựng lại từ nguồn chính (database). Chỉ dùng Redis làm nơi lưu dữ liệu chính khi bạn đã trả lời được rõ ràng câu hỏi "failover thì mất tối đa bao nhiêu?".

4. Tự kiểm tra

Điểm: 0/5

AOF bật với appendfsync everysec. Máy mất điện đột ngột. Mất tối đa khoảng bao nhiêu dữ liệu?

Lệnh đã ghi vào bộ đệm nhưng chưa fsync sẽ mất. Với everysec, khoảng đó là ~1 giây.

Vì sao cần AOF rewrite?

Log ghi lại từng lệnh, kể cả những lệnh đã bị ghi đè. Rewrite gộp lại thành trạng thái hiện tại (file base) cộng với phần mới (file incr).

ElastiCache Redis OSS có Multi-AZ. Primary chết, replica được promote. Dữ liệu nào có thể mất?

Replication bất đồng bộ: primary trả OK trước rồi mới gửi sang replica. Phần còn trên đường truyền sẽ mất khi failover.

Redis chỉ làm cache, dữ liệu dựng lại được từ PostgreSQL. Cấu hình persistence nào hợp lý?

Mất cache chỉ làm tăng tải database tạm thời. AOF always trả giá hiệu năng cho thứ bạn không cần.

Ôn bài 7 + bài 1: Cái gì chặn luồng chính khi Redis snapshot hoặc AOF rewrite?

Process con mới là nơi ghi file. Riêng lời gọi fork() (sao chép page table) chạy trên luồng chính, đo bằng latest_fork_usec.
