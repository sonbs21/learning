  • Nói được 4 điểm khác nhau giữa interface và abstract class, kèm bằng chứng chạy thật.
  • Chọn đúng một trong hai khi thiết kế, và hiểu vì sao Spring thích interface.
  • Thuộc bảng 4 mức truy cập, và tránh được 2 bẫy hay gặp khi phỏng vấn.

2 · Hai câu chuyện để nhớ

Abstract class giống một căn nhà xây dở. Móng, tường, mái đã làm xong và giống nhau cho mọi căn. Chỉ còn vài phòng để trống, ai mua thì tự hoàn thiện theo ý mình. Không ai ở được trong căn nhà dở dang, phải hoàn thiện xong mới dọn vào. Và mỗi căn nhà chỉ xây trên một cái móng.

Interface giống một tấm bằng hay chứng chỉ. "Bằng lái xe" chỉ hứa một điều: người có bằng thì lái được xe. Nó không quan tâm bạn là ai, cao hay thấp, làm nghề gì. Một người có thể có nhiều bằng cùng lúc: bằng lái xe, chứng chỉ bơi, chứng chỉ tiếng Anh.

Hai câu chuyện chứa đủ ý chính: abstract class là "là một loại gì" (có phần làm sẵn, có trạng thái chung). Interface là "làm được việc gì" (một lời hứa, gắn được nhiều cái).

3 · Abstract class: phần chung làm sẵn, phần riêng để trống

Mở AbstractDemo.java:

static abstract class Hinh {
    final String ten;                         // được có field (trạng thái)
    Hinh(String ten) { this.ten = ten; }      // ...và constructor
    abstract double dienTich();               // chưa làm: để class con làm
    String moTa() { return ten + ": " + dienTich(); }   // làm sẵn, dùng chung
}
static class HinhVuong extends Hinh {
    final double canh;
    HinhVuong(double canh) { super("Hình vuông"); this.canh = canh; }
    @Override double dienTich() { return canh * canh; }
}
// HinhTron tương tự, dienTich() = π·r²
cd lab/l0018
javac AbstractDemo.java
java AbstractDemo
Hình vuông: 9.0
Hình tròn: 3.14

Đọc từng phần:

  • Method abstract (dienTich()) chỉ có tên, không có thân. Đó là "phòng để trống". Class con bắt buộc phải override nó (bài 7), nếu không thì class con cũng phải là abstract.
  • Method thường (moTa()) đã có thân, mọi class con dùng chung. Bên trong nó gọi dienTich(), và nhờ override, lúc chạy JVM gọi đúng bản của hình vuông hay hình tròn.
  • Field và constructor: abstract class giữ được trạng thái (ten). Class con gọi super("Hình vuông") để điền phần đó (bài 6).

"Không ai ở được trong nhà dở dang": thử tạo object từ abstract class, file loi/NewAbstract.java:

javac loi/NewAbstract.java
loi/NewAbstract.java:4: error: Hinh is abstract; cannot be instantiated

Hợp lý thôi: nếu tạo được new Hinh() thì gọi dienTich() sẽ chạy cái gì? Nó đâu có thân.[JLS §8.1.1.1]

Abstract class = class chưa hoàn chỉnh. Có thể có field, constructor, method đã làm sẵn, và method abstract để con làm. Không new được. Mỗi class chỉ extends được một class.

4 · Interface: một lời hứa "làm được việc gì"

Mở InterfaceDemo.java:

interface CoTheBay {
    int SO_CANH = 2;                          // trông như field thường...
    void bay();                               // không có thân: class phải tự làm
    default String gioiThieu() { return "Tôi bay được"; }   // Java 8+: có thân sẵn
}
interface CoTheBoi { void boi(); }

static class Vit implements CoTheBay, CoTheBoi {          // một class, nhiều interface
    @Override public void bay() { System.out.println("Vịt vỗ cánh bay"); }
    @Override public void boi() { System.out.println("Vịt bơi"); }
}
javac InterfaceDemo.java
java InterfaceDemo
Vịt vỗ cánh bay
Vịt bơi
Tôi bay được
Vịt vỗ cánh bay
SO_CANH là: public static final
bay() là:   public abstract

Hai dòng cuối dùng reflection (bài 17) để hỏi JVM: "SO_CANH và bay() thật ra được khai báo thế nào?". Câu trả lời cho thấy những chữ mà compiler tự thêm vào:

  • int SO_CANH = 2; thật ra là public static final. Interface không có field của object, chỉ có hằng số dùng chung.[JLS §9.3] Đó là điểm khác lớn nhất so với abstract class: interface không giữ trạng thái riêng cho từng object.
  • void bay(); thật ra là public abstract. Mọi method trong interface tự động public.[JLS §9.4] Vì vậy class Vit phải ghi public void bay(). Quên chữ public thì gặp lại lỗi của bài 7:
javac loi/NarrowImpl.java
loi/NarrowImpl.java:4: error: chao() in NarrowImpl cannot implement chao() in ChaoHoi
  attempting to assign weaker access privileges; was public

javap (bài 1) cho thấy cùng điều đó:

javap 'InterfaceDemo$CoTheBay'
interface InterfaceDemo$CoTheBay {
  public static final int SO_CANH;
  public abstract void bay();
  public default java.lang.String gioiThieu();
}

default method (có từ Java 8) là method có thân sẵn trong interface. Nó sinh ra để thêm method mới vào interface cũ mà không làm hỏng mọi class đang implement nó. Ví dụ List.sort(...) và Collection.stream() được thêm vào Java 8 theo cách này.[Oracle: Default Methods]

Nhưng nếu một class nhận hai default method trùng tên từ hai interface thì sao? loi/Diamond.java:

interface Chim   { default String keu() { return "Chíp chíp"; } }
interface DoChoi { default String keu() { return "Bíp bíp"; } }
public class Diamond implements Chim, DoChoi { }
javac loi/Diamond.java
loi/Diamond.java:4: error: types Chim and DoChoi are incompatible;
  class Diamond inherits unrelated defaults for keu() from types Chim and DoChoi

Java không tự đoán thay bạn: compiler bắt bạn tự override và nói rõ muốn bản nào. Đó là thử thách ở mục 9.

Interface = lời hứa "làm được việc gì". Method tự động public (thường là abstract, hoặc default/static có thân). Field tự động public static final, nên không có trạng thái riêng cho từng object. Không new được. Một class implements được nhiều interface.

5 · Chọn cái nào?

Abstract classInterface
Ý nghĩa"là một loại..." (nhà xây dở)"làm được..." (tấm bằng)
Một class được dùng mấy cáimột (extends)nhiều (implements)
Field của object, constructorCóKhông (chỉ hằng số public static final)
Method có thânCó, mọi mức truy cậpdefault, static, private (Java 9+)
Mức truy cập của method abstractTuỳ bạn chọnLuôn public

Quy tắc thực tế: mặc định dùng interface để mô tả "làm được gì". Chỉ dùng abstract class khi các class con thật sự dùng chung trạng thái hoặc các bước làm sẵn. Thường gặp nhất là kết hợp cả hai: một interface, cộng một abstract class cài sẵn phần chung cho interface đó. Ví dụ List (interface) đi kèm AbstractList (abstract class), và ArrayList kế thừa AbstractList. Effective Java đặt tên quy tắc này là Item 20: "Prefer interfaces to abstract classes".

Liên hệ Spring. Spring khuyến khích viết OrderService (interface) và OrderServiceImpl (class). Lý do nằm ngay ở bài 17: JDK dynamic proxy tạo ra một class mới implements các interface bạn đưa vào. Vì một class implements được bao nhiêu interface cũng được, proxy có thể "đóng vai" bean của bạn mà không cần là class con của nó. Nếu bean không có interface nào, Spring phải chuyển sang CGLIB (tạo class con, bài 7), và mang theo các giới hạn về final/private.[Spring: Proxying Mechanisms]

6 · Access modifier: ai được nhìn thấy cái gì

Một quán cà phê có 4 loại thông tin:

  • Tên món trên bảng menu: ai cũng thấy, kể cả người đi đường.
  • Công thức pha: nhân viên của quán thấy, và các chi nhánh nhượng quyền (class con) ở nơi khác cũng được biết.
  • Số hàng tồn kho: chỉ nhân viên trong quán này biết.
  • Giá vốn: chỉ chủ quán biết.

Bốn mức truy cập trong Java ứng đúng bốn loại đó. "Package" là thư mục chứa class, ứng với "cái quán":[Oracle: Controlling Access]

public (tên món)✔✔✔✔
protected (công thức)✔✔✔✘
(không ghi gì), gọi là package-private (tồn kho)✔✔✘✘

Kiểm chứng bằng hai package. cuahang/SanPham.java:

package cuahang;
public class SanPham {
    public String ten = "Cà phê";         // ai cũng thấy
    protected String moTa = "Rang xay";   // cùng package + class con
    int tonKho = 50;                       // (không ghi gì) chỉ cùng package
    private int giaVon = 18000;            // chỉ trong class SanPham
    ...
}

Ba class đứng ở ba vị trí khác nhau:

  • cuahang/KhoHang.java: cùng package, đọc ten, moTa, tonKho.
  • khach/SanPhamGiamGia.java: class con ở package khác, đọc ten và moTa.
  • khach/KhachHang.java: người lạ ở package khác, thử đọc cả 4.

Người lạ chỉ đọc được ten. Mỗi dòng lỗi khớp với một hàng trong bảng.

Hai bẫy hay gặp khi phỏng vấn

  1. protected rộng hơn bạn tưởng. Nhiều người nghĩ protected nghĩa là "chỉ class con". Sai: nó gồm cả cùng package. KhoHang không phải class con mà vẫn đọc được moTa. Nhìn lại bảng: mỗi mức trên luôn bao gồm mọi quyền của mức dưới.
  2. private là riêng của class, không phải riêng của object. Trong SanPham có method: 
    public boolean reHon(SanPham khac) {
    return this.giaVon < khac.giaVon;   // đọc private của object KHÁC: được!
}
    Code này biên dịch được. Quy tắc truy cập được compiler kiểm tra theo chỗ đặt code (đang ở trong class nào), không theo object nào.[JLS §6.6.1] Đây chính là lý do equals ở bài 3 đọc được o.x dù x là private.
Nguyên tắc chọn: để mức hẹp nhất có thể. Field gần như luôn private. Mở rộng ra chỉ khi có lý do. Thứ gì đã public thì người khác sẽ dùng, và bạn sẽ không bao giờ sửa được nữa mà không làm hỏng code của họ. (Effective Java, Item 15: "Minimize the accessibility of classes and members".)

7 · Nối lại với Spring

Bài 7 đã nói @Transactional trên method private không có tác dụng. Giờ bạn hiểu trọn vẹn vì sao: proxy là một class khác. JDK proxy chỉ "đóng vai" được các method public của interface. CGLIB là class con, mà class con thì không nhìn thấy và không override được method private. Cả hai cách đều không chạm tới method private.

9 · Thử thách: gỡ "kim cương"

Sửa loi/Diamond.java cho biên dịch được, sao cho new Diamond().keu() in ra cả hai tiếng kêu: Chíp chíp + Bíp bíp.

Gợi ý: override keu() trong Diamond. Để gọi bản default của một interface cụ thể, cú pháp là TenInterface.super.tenMethod(). Nó giống super.method() ở bài 6, nhưng ghi rõ "của interface nào".[JLS §15.12.1]

Xem lời giải 
public class Diamond implements Chim, DoChoi {
    @Override public String keu() { return Chim.super.keu() + " + " + DoChoi.super.keu(); }
    public static void main(String[] args) { System.out.println(new Diamond().keu()); }
}
Chíp chíp + Bíp bíp

Chú ý phải có public: default method trong interface là public, nên bản override không được hẹp hơn.

Đào sâu: protected còn một luật ngầm

Class con ở package khác chỉ đọc được protected qua tham chiếu kiểu chính nó (hoặc con của nó), không qua tham chiếu kiểu class cha.[JLS §6.6.2] Thử trong khach/ một class ProtectedTrap extends SanPham:

void thu(SanPham khac, ProtectedTrap cungLoai) {
    System.out.println(this.moTa);       // được
    System.out.println(cungLoai.moTa);   // được
    System.out.println(khac.moTa);       // ?
}
error: moTa has protected access in SanPham     ← dòng khac.moTa

Lý do: "chi nhánh nhượng quyền" được biết công thức của chính mình, chứ không được đọc công thức trong một object SanPham bất kỳ, vì object đó có thể thuộc một chi nhánh khác hẳn.

Ngoài ra, từ Java 9, module (JPMS) thêm một lớp kiểm soát nữa bên trên: class public trong một package không được module exports thì module khác cũng không dùng được. Đó là lý do bài 10 và 11 phải chạy với --add-opens khi dùng reflection đọc field bên trong java.util.
