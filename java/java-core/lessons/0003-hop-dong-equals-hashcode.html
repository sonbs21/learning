Hợp đồng equals và hashCode

Vì sao “override equals thì phải override hashCode”, và chuyện gì xảy ra nếu bạn quên.

Sau bài này bạn sẽ Viết được equals/hashCode đúng hợp đồng, và giải thích được vì sao thiếu hashCode làm HashSet.contains trả về false với một phần tử “rõ ràng là có”.
Ôn lại Bài 1–2

(1) equals mặc định của Object làm gì? (2) Vì sao Integer 128 so sánh bằng == thì ra false? (3) Field int x của object nằm ở đâu?

Đáp án: (1) Giống ==: chỉ true khi cùng object. (2) 128 nằm ngoài cache −128..127 nên mỗi lần boxing tạo object mới. (3) Trong object, tức là trên heap.

1. Hợp đồng là gì?

Javadoc của Object đặt ra một “hợp đồng”. Các class như HashMap hay HashSet tin rằng bạn tuân thủ nó. Nếu bạn vi phạm, compiler không báo lỗi; chương trình chỉ chạy sai một cách lặng lẽ.

equals phải là một quan hệ tương đương

Theo Object.equals, với mọi tham chiếu khác null:

  • Phản xạ: x.equals(x) luôn true.
  • Đối xứng: x.equals(y) ⇔ y.equals(x).
  • Bắc cầu: x.equals(y) và y.equals(z) ⇒ x.equals(z).
  • Nhất quán: gọi nhiều lần cho cùng kết quả, nếu object không đổi.
  • x.equals(null) luôn false.

hashCode phải khớp với equals

“If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result. It is not required that if two objects are unequal according to the equals method, then calling the hashCode method on each of the two objects must produce distinct integer results.” — Object.hashCode — Javadoc Java 21

Nhớ theo một chiều duy nhất:

equals bằng nhau ⇒ hashCode BẮT BUỘC bằng nhau.
hashCode bằng nhau ⇒ chưa chắc equals (gọi là collision, hoàn toàn hợp lệ).

Ví dụ collision có thật: "Aa".hashCode() và "BB".hashCode() đều bằng 2112, nhưng hai chuỗi khác nhau.

2. Vì sao quên hashCode lại hỏng?

HashSet bên trong là một HashMap. Khi tìm một phần tử, nó dùng hashCode trước để chọn ngăn (bucket), rồi mới gọi equals trên các phần tử trong ngăn đó. Đây là điều kiện thật trong source HashMap.putVal:

if (p.hash == hash &&
    ((k = p.key) == key || (key != null && key.equals(k))))

Hãy để ý thứ tự: so hash trước, sau đó mới tới == hoặc equals. Nếu hai object “bằng nhau” theo equals nhưng dùng hashCode mặc định (mỗi object một giá trị riêng gần như chắc chắn khác nhau), chúng sẽ rơi vào hai ngăn khác nhau và equals không bao giờ được gọi.

class BadPoint {                 // có equals, KHÔNG có hashCode
    final int x, y;
    public boolean equals(Object o) { return o instanceof BadPoint p && p.x == x && p.y == y; }
}
set.add(new BadPoint(1, 2));
set.contains(new BadPoint(1, 2));  // false  (đã chạy thử)
set.add(new BadPoint(1, 2));
set.size();                         // 2      ← "trùng" mà vẫn thành 2 phần tử

3. Cái bẫy thứ hai: key thay đổi được

Hash của key được tính một lần, lúc bỏ vào, rồi lưu lại trong node. Nếu sau đó bạn sửa field dùng trong hashCode:

MutableKey k = new MutableKey(1);
set.add(k);              // nằm ở ngăn tính theo hash(1)
k.id = 99;               // hash bây giờ là hash(99) ⇒ tìm sai ngăn
set.contains(k);         // false, dù chính object đó vẫn nằm trong set
set.size();              // 1

Object vẫn nằm trong set, nhưng không ai tìm thấy và không xoá được. Đây là một dạng memory leak trong Java (sẽ gặp lại ở Bài 6). Bài học rút ra: key của HashMap/HashSet nên là immutable, như String, Integer hoặc record.

4. Viết đúng thế nào?

Cách 1: tự viết, dùng cùng một tập field cho cả hai method

@Override public boolean equals(Object o) {
    return o instanceof GoodPoint p && p.x == x && p.y == y;
}
@Override public int hashCode() { return Objects.hash(x, y); }

Cách 2 (khuyên dùng cho class dữ liệu): record

record Point(int x, int y) {}    // equals, hashCode, toString được sinh tự động
“[The] implicitly provided implementation returns true if and only if the argument is an instance of the same record class as this record, and each component of this record is equal to the corresponding component of the argument.” — Record.equals — Javadoc Java 21
Record còn có các field final, nên giải quyết luôn bẫy “key thay đổi được” ở phần 3, với điều kiện các component của nó cũng immutable.

5. Luyện tập

Q1 (ôn Bài 2). Integer a = 100, b = 100; thì a == b là?

100 nằm trong khoảng cache bắt buộc −128..127, nên hai lần boxing trả về cùng một object.

Q2. Class chỉ override equals. set.add(new P(1)); set.contains(new P(1)) gần như luôn trả về?

Hai object có hashCode mặc định khác nhau nên rơi vào hai ngăn khác nhau. equals không bao giờ được gọi tới.

Q3. Hai object có cùng hashCode thì:

Collision là hợp lệ: "Aa" và "BB" đều có hash 2112. Hợp đồng chỉ ràng buộc theo chiều ngược lại.

Q4. Hai object equals nhau thì hashCode của chúng:

Đây chính là câu “must produce the same integer result” trong Javadoc.

Q5. Bỏ k vào HashSet, rồi sửa field dùng trong hashCode của nó. set.contains(k) trả về?

Hash mới trỏ tới ngăn khác. Hash cũ đã được lưu trong node lúc add, nên set tìm sai chỗ.

Q6. Cách ít lỗi nhất để có equals/hashCode đúng cho một class dữ liệu bất biến?

Record sinh cả hai method theo cùng tập component và các field đều final.
