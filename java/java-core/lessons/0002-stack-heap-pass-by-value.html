Bộ nhớ JVM: stack, heap, metaspace, và vì sao Java luôn truyền giá trị

Bài 2 (viết lại) · Ba vùng nhớ quan trọng nhất, mỗi vùng chứa gì, khi nào đầy, và câu phỏng vấn "pass-by-value hay pass-by-reference?"

~45 phútCần biết: Bài 1 (javac, class được nạp vào JVM)Thư mục thực hành: lab/l0002

Học xong bài này, bạn sẽ:

  • Biết stack, heap và metaspace mỗi vùng chứa gì, sống bao lâu, ai dùng chung.
  • Nhìn một lỗi là biết vùng nào đầy: StackOverflowError, OutOfMemoryError: Java heap space, hay OutOfMemoryError: Metaspace.
  • Giải thích được vì sao Java luôn là pass-by-value, bằng sơ đồ bộ nhớ.

1 · Câu chuyện: một văn phòng có ba khu vực

Hình dung JVM là một văn phòng. Mỗi nhân viên trong đó là một thread. Văn phòng có ba khu vực:

  • Bàn làm việc riêng của từng nhân viên (stack): mỗi khi bắt đầu một việc, nhân viên đặt lên bàn một tờ giấy nháp cho việc đó. Làm xong thì vứt tờ giấy đi ngay. Bàn chỉ to đến thế: chồng quá nhiều giấy là đổ.
  • Kho chung (heap): mọi đồ vật thật đều để trong kho, và nhân viên nào cũng vào lấy được. Trên giấy nháp chỉ ghi "món đồ ở kệ số 7", chứ không bê món đồ lên bàn. Thỉnh thoảng có người dọn kho (GC), bỏ đi những món không còn ai ghi tên.
  • Tủ hồ sơ bản thiết kế (metaspace): mỗi loại đồ vật có một bản thiết kế: có những bộ phận gì (field), làm được việc gì (method). Có 1 000 cái ghế thì vẫn chỉ có một bản thiết kế "Ghế".

Nguồn: JVM Specification mô tả các vùng nhớ runtime ở JVMS §2.5. Metaspace là cách HotSpot (JVM bạn đang dùng) hiện thực vùng "method area" trong spec.

Ghép lại trong một dòng code

Chỉ một dòng Box box = new Box(1); trong main đã dùng tới cả ba vùng:

  STACK (thread main)          HEAP (dùng chung)             METASPACE (dùng chung)
 ┌──────────────────────┐     ┌──────────────────────┐      ┌──────────────────────────┐
 │ frame main           │     │ object @A1           │      │ class Box                │
 │   box  = @A1 ───────┼────►│   value = 1          │      │   field: int value       │
 │   args = @...        │     │   (thuộc class) ─────┼─────►│   method: Box(int), ...  │
 └──────────────────────┘     └──────────────────────┘      │   bytecode của method    │
                                                            └──────────────────────────┘
  • Stack: biến box là một slot trong frame của main. Nó chỉ chứa tham chiếu @A1, tức "món đồ ở kệ số A1".
  • Heap: object thật, với field value = 1.
  • Metaspace: bản thiết kế của class Box, được tạo ra lúc JVM nạp class (bài 1, bài 5). Mọi object Box đều trỏ về cùng một bản thiết kế này.

2 · Stack: chồng giấy nháp

Mỗi lần gọi method, JVM đặt thêm một frame lên đỉnh stack của thread đang chạy. Method return thì frame đó bị bỏ đi. Method gọi sau cùng sẽ xong trước, giống chồng giấy: tờ đặt sau cùng nằm trên cùng và được bỏ đi đầu tiên.[JVMS §2.6]

Mỗi frame chứa các slot cho biến cục bộ và tham số. Một slot chỉ chứa được một con số (int, double...) hoặc một tham chiếu. Không bao giờ chứa nguyên cả object.[JLS §4.1]

Thí nghiệm: làm đổ chồng giấy

Depth.java có một hàm gọi lại chính nó mãi không dừng (đệ quy). Mỗi lần gọi là thêm một frame, cho tới khi stack hết chỗ:

static void dive() { depth++; dive(); }
cd lab/l0002
javac Depth.java
java -Xss256k Depth
java -Xss1m Depth
StackOverflowError ở độ sâu 2732
StackOverflowError ở độ sâu 22461

(Số trên máy bạn sẽ khác một chút sau mỗi lần chạy.)

-Xss đặt kích thước stack của mỗi thread. Stack lớn gấp 4 lần thì đệ quy được sâu hơn nhiều. Ngoài đời, StackOverflowError thường đến từ đệ quy vô tình. Ví dụ hai entity JPA trỏ qua lại nhau (Order có Customer, Customer có list Order), và toString() hoặc thư viện chuyển sang JSON cứ gọi qua gọi lại không dừng.

3 · Heap: kho chung

Mọi object tạo bằng new đều nằm trong heap. Heap dùng chung cho mọi thread. Đó là lý do hai thread cùng sửa một object thì sinh ra race condition (bài 12). Object nào không còn tham chiếu nào trỏ tới thì GC dọn đi (bài 9). Kích thước tối đa của heap đặt bằng -Xmx. Đầy mà GC không dọn được thêm thì JVM báo OutOfMemoryError: Java heap space.

4 · Metaspace: tủ bản thiết kế (phần mới)

Khi JVM nạp một class (bài 1, bài 5), nó phải lưu lại mọi thông tin về class đó: tên, các field, các method và bytecode của chúng. Những thông tin này gọi là class metadata, và từ Java 8 chúng được cất trong Metaspace.

  • Metaspace không nằm trong heap. Nó dùng native memory, tức bộ nhớ JVM xin thẳng từ hệ điều hành. Vì vậy -Xmx không giới hạn được Metaspace.
  • Trước Java 8, thông tin class nằm trong một vùng tên là PermGen (permanent generation), có kích thước cố định nhỏ, rất hay gây lỗi OutOfMemoryError: PermGen space. Java 8 bỏ hẳn PermGen và thay bằng Metaspace.[JEP 122: Remove the Permanent Generation]
  • Oracle viết: "The amount of native memory that can be used for class metadata is by default unlimited. Use the option -XX:MaxMetaspaceSize to put an upper limit."[Oracle GC Tuning Guide: Class Metadata]

Tận mắt xem heap và metaspace của một chương trình

Cờ -Xlog:gc+heap+exit bảo JVM in tình trạng bộ nhớ ngay trước khi thoát:

javac PassByValue.java
java -Xlog:gc+heap+exit PassByValue | grep -E -i 'garbage-first|Metaspace|class space'
 garbage-first heap   total 516096K, used 3531K ...      ← HEAP: đang dùng ~3,5 MB
 Metaspace       used 232K, committed 448K, ...         ← METASPACE: tách riêng, ~232 KB
  class space    used 13K, committed 128K, ...

Heap và Metaspace được báo cáo riêng, đúng như sơ đồ ở mục 1. Một chương trình nhỏ chỉ dùng vài trăm KB Metaspace. Một ứng dụng Spring Boot nạp hàng chục nghìn class (của bạn, của Spring, của thư viện...) nên thường dùng tới hàng chục hoặc hàng trăm MB Metaspace.

Thí nghiệm: làm đầy tủ bản thiết kế

Bài 17 cho thấy JVM có thể sinh ra class mới lúc đang chạy (dynamic proxy, $Proxy0). MetaspaceLeak.java lợi dụng điều đó: mỗi vòng lặp tạo một ClassLoader mới, buộc JVM sinh thêm một class proxy mới, rồi giữ mãi trong một list static, nên không class nào được gỡ đi:

ClassLoader loader = new URLClassLoader(new URL[0], MetaspaceLeak.class.getClassLoader());
Object proxy = Proxy.newProxyInstance(loader, new Class<?>[]{ Runnable.class }, (p, m, a) -> null);
giuLai.add(proxy);     // giữ mãi → class không bao giờ được dọn

Chạy với Metaspace giới hạn 20 MB:

javac MetaspaceLeak.java
java -XX:MaxMetaspaceSize=20m MetaspaceLeak
Đã sinh 2000 class
Sập sau 3224 class: java.lang.OutOfMemoryError: Metaspace

Heap gần như trống, vì mỗi object proxy rất nhỏ. Thứ bị đầy là tủ bản thiết kế, do có quá nhiều class.

Ngoài đời, OutOfMemoryError: Metaspace thường đến từ: thư viện sinh class lúc chạy một cách mất kiểm soát (proxy, CGLIB, script engine); hoặc ở các app server cũ, mỗi lần redeploy ứng dụng mà không restart JVM, ClassLoader cũ bị giữ lại nên toàn bộ class cũ không được gỡ. Khi gặp lỗi này, hướng điều tra là "ai đang sinh ra hoặc giữ lại quá nhiều class", chứ không phải tăng -Xmx.

  • Stack: biến cục bộ và tham số, riêng từng thread → StackOverflowError, chỉnh bằng -Xss.
  • Heap: object, dùng chung → OutOfMemoryError: Java heap space, chỉnh bằng -Xmx.
  • Metaspace: thông tin class, native memory, dùng chung → OutOfMemoryError: Metaspace, chỉnh bằng -XX:MaxMetaspaceSize.

5 · Pass-by-value: Java luôn truyền bản sao

Giờ ta dùng hiểu biết về stack và heap để trả lời câu phỏng vấn kinh điển. Quy tắc chỉ có một câu:

Khi gọi method, JVM chép giá trị trong slot của bên gọi sang slot trong frame mới. Với số thì chép con số. Với object thì chép tham chiếu (tờ giấy ghi số kệ). Object thì vẫn nằm yên trong heap, không bị chép.[JLS §15.12.4.5]

Bạn photo tờ giấy "món đồ ở kệ số 7" rồi đưa bản photo cho đồng nghiệp. Đồng nghiệp có thể tới kệ số 7 sơn lại món đồ, và bạn sẽ thấy món đồ đã bị sơn. Nhưng nếu đồng nghiệp gạch bản photo, viết thành "kệ số 9", thì tờ giấy gốc của bạn vẫn ghi "kệ số 7".

Mở PassByValue.java. Có 4 method:

static void changeInt(int x)      { x = 99; }                  // đổi số
static void changeField(Box b)    { b.value = 99; }            // sửa object
static void reassign(Box b)       { b = new Box(99); }         // gán biến sang object khác
static void swap(Box a, Box b)    { Box t = a; a = b; b = t; } // đổi chỗ hai biến

Đoán trước 4 dòng output, ghi ra giấy, rồi chạy:

javac PassByValue.java
java PassByValue
1. n = 1
2. box.value = 99
3. box2.value = 1
4. p = 1, q = 2

Từng trường hợp, vẽ ra stack và heap

1. changeInt(n): số 1 được chép vào slot x của changeInt. Gán x = 99 chỉ đổi bản chép. n của main vẫn là 1.

2. changeField(box): tham chiếu @A1 được chép sang b. Cả hai tờ giấy cùng chỉ một object, nên sửa field qua b thì main cũng thấy:

Stack

changeField
b@A1
main
box@A1

Heap

@A1 · Box
value199

Hai slot khác nhau, cùng giữ một tham chiếu, nên cùng thấy object bị sửa ("sơn lại món đồ").

3. reassign(box2): b được gán sang một object mới. Việc này chỉ ghi đè slot b trong frame của reassign ("gạch bản photo"). Slot box2 của main không bị đụng tới:

Stack

reassign
b@B1@B2
main
box2@B1

Heap

@B1 · Box
value1
@B2 · Box (thành rác khi reassign return)
value99

Gán lại tham số chỉ đổi bản sao trong frame của method được gọi.

4. swap(p, q): a và b là hai bản chép của tham chiếu. Đổi chỗ hai bản chép thì p và q của main vẫn y nguyên. Vì vậy trong Java không viết được hàm swap đổi chỗ hai biến của người gọi.

Bằng chứng ở bytecode

javap -c PassByValue cho thấy hai cách "thay đổi" khác nhau hoàn toàn:

changeField:  aload_0 ... putfield value    // ghi vào OBJECT trên heap → ai giữ tham chiếu cũng thấy
reassign:     new Box ...   astore_0          // ghi vào SLOT 0 của frame hiện tại → chỉ frame này thấy

Không có lệnh bytecode nào cho phép một method ghi vào slot thuộc frame của method khác. Vì thế Java không thể có pass-by-reference.

Câu phỏng vấn: "Java là pass-by-value hay pass-by-reference?"

"Java luôn là pass-by-value. Khi gọi method, giá trị trong biến của người gọi được chép sang tham số. Với primitive thì chép con số. Với object thì chép tham chiếu, còn bản thân object nằm trên heap và không bị chép. Vì cùng trỏ tới một object, method sửa được trạng thái của object và người gọi thấy được. Nhưng gán tham số sang object khác chỉ đổi bản sao, biến của người gọi không đổi. Bằng chứng: không viết được hàm swap(a, b) đổi chỗ hai biến của người gọi."

7 · Thử thách

A. Đoán output (không chạy trước!)

static void a(int[] arr)        { arr[0] = 10; arr = new int[]{20}; arr[0] = 30; }
static void b(StringBuilder sb) { sb.append(" world"); sb = new StringBuilder("bye"); }
static void c(String s)         { s = s + "!"; }

int[] arr = {1};                                a(arr);
StringBuilder sb = new StringBuilder("hello");  b(sb);
String s = "hi";                                c(s);
System.out.println(arr[0] + " | " + sb + " | " + s);

Vẽ sơ đồ stack/heap cho hàm a ra giấy, ghi đáp án, rồi mới chạy javac Challenge.java && java Challenge.

Xem đáp án 
10 | hello world | hi
  • a: arr[0] = 10 sửa mảng gốc trên heap ("sơn món đồ"). Sau đó arr bị gán sang mảng mới ("gạch bản photo"), nên arr[0] = 30 chỉ sửa mảng mới, và mảng mới sẽ thành rác.
  • b: append sửa object gốc. Gán sb sang object mới chỉ đổi bản sao.
  • c: String không sửa được (bài 4), nên s + "!" tạo object mới rồi gán vào bản sao s. Cùng cơ chế với reassign.

Nhận xét: String "trông như" pass-by-value còn StringBuilder "trông như" pass-by-reference. Thật ra cả hai đều là pass-by-value. Khác biệt duy nhất là StringBuilder có method sửa được object, còn String thì không.

B. Khi Metaspace không có giới hạn

Chạy lại MetaspaceLeak nhưng không có -XX:MaxMetaspaceSize=20m, kèm timeout 10 để tự dừng sau 10 giây:

timeout 10 java MetaspaceLeak | tail -2

Đoán trước: lần này có in ra OutOfMemoryError: Metaspace không? Vì sao?

Xem đáp án 
Đã sinh 38000 class
Đã sinh 40000 class

Rồi bị timeout giết sau 10 giây, mà không có lỗi nào.

Không đặt giới hạn thì Metaspace mặc định là không giới hạn, nên chương trình cứ sinh class và chiếm thêm bộ nhớ hệ điều hành (hơn 40 000 class chỉ trong 10 giây), cho tới khi bị giết hoặc máy hết RAM. Ở production, nên đặt -XX:MaxMetaspaceSize để lỗi lộ ra sớm và rõ ràng là OutOfMemoryError: Metaspace, thay vì để JVM âm thầm ăn hết RAM của máy chủ.

Đào sâu: danh sách đầy đủ các vùng nhớ runtime trong JVM Spec

JVMS §2.5 liệt kê 6 vùng nhớ runtime.[JVMS §2.5] Bài này đã học ba vùng quan trọng nhất. Ba vùng còn lại:

  • PC register: mỗi thread có một "ngón tay chỉ" vào lệnh bytecode đang chạy.
  • Native method stack: stack dành cho code viết bằng C/C++ mà JVM gọi tới (method native).
  • Run-time constant pool: bảng hằng số của từng class (tên class, tên method, chuỗi literal... những thứ bạn thấy dạng #7 trong javap ở bài 1). Trong HotSpot, nó nằm cùng thông tin class trong Metaspace.

Spec gọi vùng chứa thông tin class là method area. Spec chỉ nói phải có vùng này, còn cách hiện thực thì tuỳ JVM. HotSpot từ Java 8 hiện thực nó bằng Metaspace. Ngoài ra còn những vùng native memory khác ngoài heap: code cache (nơi JIT ở bài 8 cất mã máy), stack của các thread, bộ nhớ của thư viện mạng... Vì vậy tổng RAM một tiến trình Java dùng luôn lớn hơn -Xmx. Đây là điều rất quan trọng khi đặt giới hạn bộ nhớ cho container Docker hay Kubernetes.
