1 · Hai vùng nhớ, hai luật chơi

JVM spec mô tả nhiều vùng nhớ runtime. Bài này chỉ cần hai vùng:[JVMS §2.5]

Stack (của mỗi thread)Heap (dùng chung)
Chứa gìFrame: mỗi lần gọi method sinh ra một frame, gồm local variable slots và operand stackObject và mảng, tức mọi thứ tạo bằng new
Sống đến khiMethod return thì frame bị bỏ ngayKhông còn ai tham chiếu tới, rồi GC dọn
Ai thấyChỉ thread đóMọi thread (gốc rễ của bug concurrency)

Một slot chỉ chứa được hai loại giá trị: giá trị primitive (int, double...) hoặc tham chiếu (reference) trỏ tới object trên heap. Một slot không bao giờ chứa nguyên cả object.[JLS §4.1] Trong bài, ta viết tham chiếu thành @A1. Bạn cứ hình dung nó như "địa chỉ" của object.

Khi gọi method, JVM sao chép giá trị trong slot của caller sang slot của frame mới. Với object, thứ được sao chép là tham chiếu, còn object thì vẫn nằm yên một chỗ trên heap.[JLS §15.12.4.5]

2 · Vẽ ra từng trường hợp

Trường hợp 2: changeField(box) → box.value = 99

Stack

changeField
b@A1
main
box@A1

Heap

@A1 · Box
value199

b và box là hai slot khác nhau, nhưng giữ cùng một tham chiếu. Sửa field của object thì cả hai đều thấy thay đổi.

Trường hợp 3: reassign(box2) → b = new Box(99)

Stack

reassign
b@B1@B2
main
box2@B1

Heap

@B1 · Box
value1
@B2 · Box (thành rác sau khi return)
value99

Gán lại b chỉ ghi đè slot của reassign. Slot box2 của main không bị đụng tới.

Bytecode cho thấy đúng điều này (javap -c PassByValue):

static void changeField(PassByValue$Box);
   0: aload_0              // lấy tham chiếu trong slot 0
   1: bipush 99
   3: putfield value       // ghi vào object trên HEAP

static void reassign(PassByValue$Box);
   0: new PassByValue$Box  // tạo object mới trên heap
   ...
   9: astore_0             // ghi đè slot 0 của frame NÀY

Chỉ có hai cách để "thay đổi" một thứ: putfield sửa object (ai cầm tham chiếu cũng thấy), còn astore sửa slot (chỉ frame đó thấy). Không lệnh bytecode nào cho phép một method ghi vào slot thuộc frame của method khác. Vì thế Java không thể có pass-by-reference.

Câu trả lời phỏng vấn mẫu "Java luôn là pass-by-value. Với primitive, giá trị được sao chép. Với object, tham chiếu được sao chép. Vì vậy method sửa được trạng thái của object, nhưng không làm biến của caller trỏ sang object khác được. Ví dụ: hàm swap(a, b) không hoạt động trong Java."

3 · Stack có giới hạn

Mỗi thread có một stack riêng với kích thước cố định. Trên máy này mặc định là 1 MB (ThreadStackSize = 1024 KB), và chỉnh được bằng -Xss.[java man: -Xss] Đệ quy không có điểm dừng sẽ đẩy thêm frame cho đến khi stack đầy:

javac Depth.java
java -Xss256k Depth   # StackOverflowError ở độ sâu ~2 679
java -Xss1m   Depth   # ~22 000
java -Xss4m   Depth   # ~101 000

Con số này đổi một chút sau mỗi lần chạy (22 364, 22 203, 22 350...). Lý do là frame của code đang thông dịch và frame của code đã JIT có kích thước khác nhau (nhớ lại bài 1). Ngoài production, StackOverflowError thường đến từ đệ quy vô tình, ví dụ hai entity trỏ qua lại nhau và toString()/JSON serialize gọi nhau mãi không dừng.

5 · Thử thách

A. Đoán output (không chạy trước!)

static void a(int[] arr)        { arr[0] = 10; arr = new int[]{20}; arr[0] = 30; }
static void b(StringBuilder sb) { sb.append(" world"); sb = new StringBuilder("bye"); }
static void c(String s)         { s = s + "!"; }

int[] arr = {1};                 a(arr);
StringBuilder sb = new StringBuilder("hello"); b(sb);
String s = "hi";                 c(s);
System.out.println(arr[0] + " | " + sb + " | " + s);

Viết đáp án ra giấy, vẽ sơ đồ stack/heap cho hàm a, rồi mới chạy javac Challenge.java && java Challenge.

Đáp án

10 | hello world | hi

  • a: arr[0] = 10 sửa mảng gốc trên heap. Sau đó arr được gán sang mảng mới, nên arr[0] = 30 chỉ sửa mảng mới (sẽ thành rác).
  • b: append sửa object gốc. Gán sb sang object mới chỉ tác động tới slot của b.
  • c: String là immutable, nên s + "!" tạo ra object mới rồi gán vào slot của c. Đây là cùng cơ chế với reassign.

B. Tìm frame trong bytecode

Chạy javap -v PassByValue | grep -A4 'void swap' rồi tìm dòng stack=..., locals=... của swap. Đoán trước: locals bằng bao nhiêu, và mỗi slot là gì?

Đáp án

locals=3: slot 0 = a, slot 1 = b, slot 2 = t. Kích thước frame được javac tính sẵn từ lúc build và ghi vào file .class.[JVMS §4.7.3]

Đọc thêm (nguồn chính)

JVMS SE 21, §2.5 Run-Time Data Areas và §2.6 Frames. Bạn sẽ thấy cả các vùng nhớ chưa học (method area, run-time constant pool, PC register). Chúng sẽ quay lại ở các bài class loading và GC.

Có chỗ nào chưa rõ? Cứ hỏi agent (giáo viên của bạn). Một gợi ý để tự kiểm tra: hãy giải thích bằng lời vì sao String trong thử thách A "trông như" pass-by-value còn StringBuilder thì "trông như" pass-by-reference, dù thực chất cả hai giống hệt nhau. Gửi câu trả lời cho agent để được nhận xét.
