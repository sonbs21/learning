2 · Comparable và Comparator: hai cách nói "cái nào đứng trước"

Một menu đồ uống có thể xếp theo nhiều cách. Comparable giống cách xếp mặc định in sẵn trên menu (theo giá). Comparator giống tờ giấy hướng dẫn bạn cầm theo: "hôm nay xếp theo tên", "xếp theo giá giảm dần". Đưa tờ giấy khác thì ra thứ tự khác, mà không phải in lại menu.

Cả hai đều trả lời cùng một câu hỏi bằng một con số: âm nghĩa là "a đứng trước b", 0 là "ngang nhau", dương là "a đứng sau b".[Comparator] SapXep.java:

record Mon(String ten, int gia) implements Comparable<Mon> {
    @Override public int compareTo(Mon khac) { return Integer.compare(gia, khac.gia); }   // thứ tự "tự nhiên": theo giá
}

menu.sort(null);                                            // null = dùng compareTo
menu.sort(Comparator.comparing(Mon::ten));                  // một cách sắp khác, không sửa class
menu.sort(Comparator.comparingInt(Mon::gia).reversed().thenComparing(Mon::ten));

Giá giảm dần, rồi theo tên: [trà sữa 35000, americano 30000, bạc xỉu 30000, cà phê 25000]

Bẫy 1 · "Mẹo" trừ hai số

Nhiều người viết (a, b) -> a - b cho gọn. TruSo.java:

javac TruSo.java
java TruSo
a - b             : [5, 2147483647, -2147483648, -10]
Integer.compare   : [-2147483648, -10, 5, 2147483647]
MIN_VALUE - 5 = 2147483643

Sắp xếp sai hoàn toàn. Lý do: int có giới hạn. Một số rất âm trừ đi số dương thì tràn qua phía dương (dòng cuối: số âm nhỏ nhất trừ 5 ra một số dương rất lớn), nên dấu của kết quả bị đảo. Với ID hay số tiền lớn, lỗi này xảy ra thật. Luôn dùng Integer.compare(a, b), Long.compare, hoặc Comparator.comparingInt(...).

Bẫy 2 · TreeSet không dùng equals

MatPhanTu.java thêm 3 món vào một HashSet và một TreeSet sắp theo giá:

Set<Mon> tree = new TreeSet<>(Comparator.comparingInt(Mon::gia));    // chỉ so theo giá
s.add(new Mon("bạc xỉu", 30000));
s.add(new Mon("americano", 30000));
s.add(new Mon("cà phê", 25000));
javac MatPhanTu.java
java MatPhanTu
HashSet: 3 món [...]
TreeSet: 2 món [Mon[ten=cà phê, gia=25000], Mon[ten=bạc xỉu, gia=30000]]

americano biến mất. TreeSet (và TreeMap) coi hai phần tử là "trùng" khi compare trả về 0, chứ không gọi equals. Hai món cùng giá thì compare = 0, nên món sau bị coi là trùng và bị bỏ. Tài liệu Java gọi đây là thứ tự "không nhất quán với equals" và cảnh báo set sẽ cư xử "strangely".[Comparable] Sửa: thêm tiêu chí phân xử, ví dụ .thenComparing(Mon::ten), để chỉ hai món thật sự giống nhau mới ra 0.

So sánh trả về âm / 0 / dương. Dùng Integer.compare hoặc Comparator.comparing..., không trừ hai số. Với TreeSet/TreeMap, compare == 0 nghĩa là trùng, nên thêm thenComparing để không mất phần tử.

3 · TreeMap: map luôn được sắp xếp theo key

TreeMap giữ các key theo thứ tự tăng dần (theo Comparable hoặc Comparator bạn đưa vào). Bên trong là một cây đỏ–đen, nên get/put/remove tốn O(log n), chậm hơn HashMap một chút (HashMap gần như O(1), bài 11).[TreeMap] Bù lại, nó trả lời được những câu mà HashMap không trả lời được: "key gần nhất bên dưới X là gì?", "các key từ A tới B?".

Ví dụ thực tế trong BangPhiShip.java: bảng phí ship theo cân nặng, "từ X gram trở lên thì phí Y":

m.put(1000, 25000);  m.put(0, 15000);  m.put(5000, 50000);  m.put(3000, 35000);   // vào cả TreeMap lẫn HashMap

Map.Entry<Integer, Integer> bac = phi.floorEntry(gram);     // bậc lớn nhất <= gram
phi.subMap(1000, 5000)                                      // các bậc từ 1000 tới dưới 5000
javac BangPhiShip.java
java BangPhiShip
TreeMap duyệt: [0, 1000, 3000, 5000]
HashMap duyệt: [0, 1000, 5000, 3000]
300g → bậc 0g → phí 15000
1000g → bậc 1000g → phí 25000
2700g → bậc 1000g → phí 25000
9000g → bậc 5000g → phí 50000
Các bậc từ 1000g tới dưới 5000g: {1000=25000, 3000=35000}

Với HashMap bạn phải tự duyệt hết để tìm bậc phù hợp. Với TreeMap chỉ cần một dòng floorEntry. Các method tương tự: ceilingKey (nhỏ nhất ≥ X), firstKey/lastKey, headMap/tailMap. Hợp với bảng giá bậc thang, lịch theo thời gian, xếp hạng.

4 · LinkedHashMap: nhớ thứ tự, và làm LRU cache

LinkedHashMap là HashMap (vẫn nhanh O(1)) có thêm một chuỗi nối các phần tử theo thứ tự. Mặc định là thứ tự thêm vào. Nếu tạo với tham số accessOrder = true, mỗi lần get/put sẽ chuyển phần tử đó xuống cuối, nên phần tử ở đầu luôn là phần tử lâu nhất chưa được dùng. Ghép với removeEldestEntry là có ngay một LRU cache (Least Recently Used: đầy thì bỏ cái lâu nhất chưa dùng).[LinkedHashMap: "well-suited to building LRU caches"] LruCache.java:

Map<String, Integer> cache = new LinkedHashMap<>(16, 0.75f, true) {     // true = accessOrder
    @Override protected boolean removeEldestEntry(Map.Entry<String, Integer> eldest) {
        return size() > 3;                       // quá 3 phần tử: bỏ phần tử lâu nhất chưa dùng
    }
};
cache.put("u1", 1); cache.put("u2", 2); cache.put("u3", 3);
cache.get("u1");
cache.put("u4", 4);
javac LruCache.java
java LruCache
Thứ tự thêm vào: {c=3, a=1, b=2}
Cache:            {u1=1, u2=2, u3=3}
Sau get(u1):      {u2=2, u3=3, u1=1}
Sau put(u4):      {u3=3, u1=1, u4=4}
  1. Dòng đầu: LinkedHashMap thường giữ đúng thứ tự thêm vào (c, a, b). HashMap thì không.
  2. get("u1") chuyển u1 xuống cuối: nó vừa được dùng.
  3. put("u4") làm size thành 4 > 3, nên phần tử đầu (u2, lâu nhất chưa dùng) bị bỏ. u1 sống sót vì vừa được đọc.

Cách viết new LinkedHashMap<>(...) { ... } là một class ẩn danh (bài 22). Trong code thật, nên viết thành một class static riêng. Và cache này không an toàn khi nhiều thread dùng chung (bài 12); production thường dùng thư viện như Caffeine.

Chọn Map theo thứ tự bạn cần: không cần thứ tự → HashMap. Cần đúng thứ tự thêm vào (hoặc LRU) → LinkedHashMap. Cần sắp theo key, tìm "gần nhất", "trong khoảng" → TreeMap.

5 · ConcurrentModificationException: sửa list trong lúc duyệt

Tên có chữ "Concurrent" nhưng lỗi này thường xảy ra chỉ với một thread.[ConcurrentModificationException] Cme.java thử xoá phần tử ngay trong vòng for-each:

for (String s : a) if (s.equals("trà")) a.remove(s);        // xoá phần tử đầu
for (String s : b) { daDuyet.add(s); if (s.equals("sữa")) b.remove(s); }   // xoá phần tử ÁP CHÓT
javac Cme.java
java Cme
Xoá phần tử đầu: java.util.ConcurrentModificationException
Xoá áp chót: không lỗi! đã duyệt [trà, cà phê, sữa], list còn [trà, cà phê, nước cam]
iterator.remove(): [trà, sữa, nước cam]
removeIf:          [cà phê, nước cam]

Vì sao? Vòng for-each thật ra dùng một iterator (chính là inner class ArrayList.Itr ở bài 22). Xem bên trong:

javap -p 'java.util.ArrayList$Itr' | grep -E 'ModCount|checkFor'
javap -p java.util.AbstractList | grep modCount
  int expectedModCount;
  final void checkForComodification();
  protected transient int modCount;
  1. List giữ một bộ đếm modCount, tăng lên mỗi lần list bị thêm hoặc xoá.
  2. Lúc bắt đầu duyệt, iterator chép lại con số đó vào expectedModCount.
  3. Mỗi lần lấy phần tử tiếp theo (next()), iterator kiểm tra hai số còn bằng nhau không. Khác nhau nghĩa là "có ai đó sửa list sau lưng tôi", và nó ném ConcurrentModificationException ngay. Cách làm này gọi là fail-fast: báo lỗi sớm thay vì chạy tiếp với dữ liệu sai.

Trường hợp áp chót còn nguy hiểm hơn: xoá sữa (phần tử thứ 3/4) làm list còn 3 phần tử. Iterator đang ở vị trí 3, hỏi hasNext() ("vị trí 3 khác size 3?") được trả lời không, nên vòng lặp kết thúc trước khi kịp gọi next() để kiểm tra. Kết quả: không có lỗi, nhưng "nước cam" không bao giờ được duyệt. Đó là lý do tài liệu nói fail-fast "cannot be guaranteed" và chỉ nên dùng để phát hiện bug.[ArrayList: fail-fast]

Cách đúng (hai dòng cuối của output):

  • list.removeIf(dieuKien): gọn nhất, nên dùng mặc định (lambda, bài 21).
  • iterator.remove(): xoá thông qua chính iterator, nên nó tự cập nhật expectedModCount.
  • Nhiều thread cùng đọc và sửa: dùng collection dành cho đa luồng (ConcurrentHashMap, CopyOnWriteArrayList). Iterator của chúng không ném lỗi này.
Không bao giờ gọi list.add/list.remove bên trong for-each của chính list đó. Dùng removeIf hoặc iterator.remove(). ConcurrentModificationException là cảnh báo có thể có, không phải đảm bảo: không thấy lỗi chưa chắc code đúng.

7 · Thử thách: sắp xếp đơn hàng nhiều tiêu chí

Challenge.java có 5 đơn hàng. Viết một Comparator, không dùng if, sắp theo:

  1. Khách VIP lên trước.
  2. Cùng nhóm thì tổng tiền giảm dần.
  3. Bằng tiền thì mã đơn tăng dần.
record Don(String ma, boolean vip, long tong) { }

// TODO: sửa dòng này
Comparator<Don> thuTu = Comparator.comparing(Don::ma);

Kết quả mong muốn:

D07 vip=true tong=250000
D01 vip=true tong=80000
D02 vip=true tong=80000
D09 vip=false tong=300000
D05 vip=false tong=120000

Gợi ý: Boolean có thứ tự false < true. Cẩn thận với .reversed(): nó đảo toàn bộ chuỗi đứng trước nó.

Xem lời giải 
Comparator<Don> thuTu = Comparator.comparing(Don::vip).reversed()
        .thenComparing(Comparator.comparingLong(Don::tong).reversed())
        .thenComparing(Don::ma);
  • comparing(Don::vip).reversed(): true lên trước.
  • Tổng giảm dần phải bọc riêng: thenComparing(comparingLong(Don::tong).reversed()). Nếu viết .thenComparingLong(Don::tong).reversed() thì reversed() đảo luôn cả tiêu chí VIP phía trước.
  • D01 và D02 cùng VIP, cùng 80 000, nên mã tăng dần phân xử.
Đào sâu: hợp đồng của compare, và vì sao TimSort có thể ném lỗi

Một comparator hợp lệ phải tuân theo "hợp đồng" giống equals ở bài 3: đảo dấu khi đổi chỗ (sgn(compare(a,b)) == -sgn(compare(b,a))), bắc cầu (a < b và b < c thì a < c), và nhất quán.[Comparator.compare] Comparator vi phạm (ví dụ trừ số bị tràn như mục 2, hoặc so sánh dựa trên giá trị ngẫu nhiên/thời gian hiện tại) có thể khiến thuật toán sắp xếp của Java (TimSort) ném IllegalArgumentException: Comparison method violates its general contract! với dữ liệu lớn. Đây là một lỗi production có thật, và nó chỉ xuất hiện với một số bộ dữ liệu, nên rất khó tái hiện.
