Khi nào một object “chết”?

Reachability, GC roots, generational GC với G1, và vì sao Java có GC mà vẫn bị memory leak.

Sau bài này bạn sẽ Giải thích được GC quyết định object nào là rác, đọc được một dòng log -Xlog:gc, và chỉ ra memory leak trong một đoạn code Java.
Ôn lại Bài 1, 3 và 5

(1) Khi replace() ở Bài 1 kết thúc, object “Bình” ra sao? (2) Vì sao key thay đổi được trong HashSet là một dạng leak? (3) iadd lấy toán hạng từ đâu?

Đáp án: (1) Không còn ai trỏ tới nên trở thành rác. Bài này sẽ gọi đúng tên: unreachable. (2) Object vẫn nằm trong set nhưng không ai tìm thấy hay xoá được. (3) Từ operand stack của frame.

1. Rác = không còn đường đi tới

GC không hỏi “object này còn được dùng không?”. Nó chỉ hỏi “object này còn đi tới được không?”.

“A reachable object is any object that can be accessed in any potential continuing computation from any live thread.” — JLS §12.6.1
“An object is considered garbage and its memory can be reused by the VM when it can no longer be reached from any reference of any other live object in the running program.” — HotSpot GC Tuning Guide: Garbage Collector Implementation

Trên thực tế, GC bắt đầu từ một tập điểm xuất phát, thường gọi là GC roots, rồi lần theo mọi mũi tên. Hai loại root quan trọng nhất bạn đã biết từ Bài 1:

  • Biến local và tham số trong frame của các thread đang sống.
  • Field static của các class đã load.

Object nào không được đánh dấu sau khi lần hết các mũi tên thì là rác.

Và object thì không bao giờ được giải phóng thủ công. System.gc() cũng chỉ là lời gợi ý:

“Calling this method suggests that the Java Virtual Machine expend effort toward recycling unused objects…” — Runtime.gc — Javadoc Java 21

2. Vì sao chia “thế hệ”: đa số object chết trẻ

“The most important of these observed properties is the weak generational hypothesis, which states that most objects survive for only a short period of time.” — HotSpot GC Tuning Guide

Vì đa số object chết trẻ, heap được chia làm young generation (gồm eden và survivor) và old generation. Object mới được cấp phát trong eden. Khi eden đầy, GC chạy một young collection: chỉ quét vùng nhỏ này, sao chép những object còn sống sang survivor, rồi coi cả eden là trống. Việc này rất rẻ vì hầu như mọi thứ trong eden đã chết. Object sống sót qua nhiều lần như vậy sẽ được “thăng cấp” lên old generation.

Từ Java 9, collector mặc định là G1 (“G1 is the default collector”, theo G1 guide). G1 chia heap thành nhiều region bằng nhau, và mỗi region được gán vai trò eden, survivor hoặc old. Trên máy bạn, java -XX:+PrintCommandLineFlags -version in ra -XX:+UseG1GC.

Đọc một dòng log GC (chạy thật)

[0.486s][info][gc] GC(3) Pause Young (Normal) (G1 Evacuation Pause) 11M->3M(17M) 0.379ms
                   │     │                                           │    │  │      └ thời gian dừng app
                   │     └ loại: young collection                    │    │  └ heap hiện có
                   └ lần GC thứ 3                                    │    └ sau GC
                                                                     └ trước GC

Vòng lặp tạo 200 MB mảng byte[100] chết ngay, mà mỗi lần young GC chỉ dừng chương trình chưa tới 1 ms (11M xuống 3M). Đó chính là giả thuyết thế hệ đang hoạt động.

3. Memory leak trong Java

Trong Java, memory leak không phải là “quên free” như trong C. Nó là: object không còn cần nữa nhưng vẫn reachable, nên GC không được phép thu hồi.

static final List<byte[]> CACHE = new ArrayList<>();   // static field = GC root
for (;;) CACHE.add(new byte[1_000_000]);              // thêm mãi, không bao giờ xoá
// ⇒ OutOfMemoryError sau khi giữ ~60 MB (heap -Xmx64m), chạy thật

Log lúc này cho thấy GC đã cố hết sức nhưng không thu hồi được gì: Pause Full (G1 Compaction Pause) 63M->63M(64M). Các nguồn leak hay gặp:

  • Collection static hoặc cache chỉ thêm mà không bao giờ xoá.
  • Key thay đổi được trong HashMap/HashSet (Bài 3).
  • Listener hoặc callback đăng ký mà không huỷ đăng ký.
  • ThreadLocal không gọi remove() trong thread pool (sẽ học ở phần concurrency).
Trong log demo bạn sẽ thấy chữ “Humongous Allocation”. Với G1, object có kích thước từ nửa region trở lên được gọi là humongous và được cấp phát thẳng vào old generation (G1 guide). Heap 64 MB có region nhỏ, nên mảng 1 MB đã thuộc loại này.

4. Luyện tập

Q1 (ôn Bài 5). iadd lấy hai toán hạng từ đâu?

JVM là máy stack: iload đẩy lên operand stack, iadd lấy ra từ đó, cộng, rồi đẩy kết quả lại.

Q2. Object đủ điều kiện bị GC thu hồi khi nào?

Chỉ có reachability quyết định. Object tạo trong method vẫn sống tiếp nếu được return ra ngoài hoặc được cất vào một field.

Q3. System.gc() làm gì?

Javadoc dùng đúng chữ “suggests”. JVM được phép bỏ qua, và cờ -XX:+DisableExplicitGC còn tắt hẳn nó.

Q4. Vì sao heap được chia thành young và old generation?

Weak generational hypothesis: quét riêng vùng young, nơi gần như mọi thứ đã chết, nên rất rẻ.

Q5. Memory leak trong Java nghĩa là:

Object hết reachable thì sớm muộn sẽ được thu hồi; đó không phải leak. Leak là khi bạn vô tình vẫn giữ mũi tên tới thứ không còn cần.

Q6. Hai object A và B trỏ vào nhau, nhưng không root nào đi tới được chúng. GC làm gì?

GC đánh dấu từ root. Tham chiếu vòng giữa hai object không làm chúng reachable.
