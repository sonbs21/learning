1 · == so sánh slot, equals là một method

P1: ==false equals=false
P2: ==false equals=true  set.contains=false   // ?!
P3: ==false equals=true  set.contains=true
P4: ==false equals=true  set.contains=true

Xem bytecode (javap -c Ops) để thấy hai phép so sánh khác nhau thế nào ở cấp độ JVM:

a == b      (Object) → if_acmpne       // so 2 tham chiếu
a == b      (int)    → if_icmpne       // so 2 số nguyên
a.equals(b)          → invokevirtual Object.equals
  • == chỉ so sánh hai giá trị trong slot. Với object, giá trị đó là tham chiếu. Vì vậy == trả lời câu hỏi "có phải cùng một object không?", và hai object tạo bằng hai lần new luôn cho false.[JLS §15.21.3]
  • equals chỉ là một method bình thường. Bản mặc định trong Object là return (this == obj);, tức y hệt ==.[Object.java] Đó là lý do P1 cho equals=false. Muốn so sánh theo nội dung thì bạn phải tự override.

2 · HashSet không gọi equals trước

HashSet bên trong là một HashMap. Đây là nguyên văn đoạn code tra cứu trong JDK 21:[HashMap.java]

final Node<K,V> getNode(Object key) {
    ...
    (first = tab[(n - 1) & (hash = hash(key))]) != null) {   // ① chọn bucket
        if (first.hash == hash &&                           // ② so hash
            ((k = first.key) == key || (key != null && key.equals(k))))  // ③
            return first;
  1. Gọi key.hashCode(), rồi dùng kết quả để chọn bucket (một ô trong mảng table).
  2. Trong bucket đó, chỉ xét những phần tử có hash bằng đúng hash của key.
  3. Chỉ đến bước này mới thử ==, rồi đến equals.

P2 không override hashCode, nên nó dùng bản của Object. Bản này trả về một số gắn với từng object (identity hash), nên a2 và b2 gần như chắc chắn có hash khác nhau. Lookup bị loại ngay ở bước ① hoặc ②, và equals của bạn không bao giờ được gọi.

Contract: nếu a.equals(b) thì a.hashCode() == b.hashCode() là bắt buộc. Chiều ngược lại thì không cần: hai object khác nhau được phép trùng hash (gọi là collision).[Object.hashCode Javadoc]

Cách sửa: dùng Objects.hash(x, y) trên đúng các field mà equals dùng (như P3). Hoặc dùng record (như P4): compiler tự sinh equals/hashCode/toString dựa trên mọi component.[JLS §8.10.3]

Câu trả lời phỏng vấn mẫu "== so sánh tham chiếu, equals so sánh theo logic do class tự định nghĩa (mặc định giống ==). HashMap/HashSet tìm bucket bằng hashCode trước, sau đó mới dùng equals. Nếu override equals mà không override hashCode thì hai object bằng nhau sẽ có hash khác nhau, và collection không tìm thấy phần tử."

4 · Thử thách

A. Key bị sửa sau khi đã vào Set

MutableKey.java: class P override đúng cả equals và hashCode. Ta add(p) vào set, sau đó mới gán p.x = 100. Đoán 3 dòng output: contains(p), size, và phần tử lấy ra khi duyệt set có equals(p) không?

Đáp án 
contains(p)   = false
size          = 1
iterate thấy p = true

Object nằm ở bucket được tính từ hash cũ. Sau khi sửa x, hash mới trỏ sang bucket khác, nên lookup tìm sai chỗ, dù object vẫn nằm trong set (duyệt set thì thấy). Lúc này bạn cũng không remove được nó, và đó chính là một kiểu memory leak. Bài học: field tham gia vào hashCode phải bất biến khi object còn nằm trong collection. Hướng sang Spring: một JPA entity tính hashCode từ id do database sinh ra sẽ đổi hash ngay sau khi persist, và gặp đúng lỗi này.

B. hashCode luôn trả về 42

Const.java có record K(int v) override hashCode() { return 42; }. Trả lời hai câu: (1) Cách này có vi phạm contract không? (2) Set có chạy đúng không, và có chạy nhanh không? Đoán xong thì chạy javac Const.java && java Const.

Đáp án

Không vi phạm contract: object bằng nhau vẫn có hash bằng nhau. Kết quả vẫn đúng (contains = true). Nhưng mọi phần tử dồn vào một bucket, nên mỗi lookup phải so equals với gần như cả set. Trên máy này, 20 000 lần add + contains mất ~9 ms với hash tốt so với ~2 100 ms với hash = 42, chậm hơn ~230 lần. Đúng contract mới là điều kiện tối thiểu; hash còn phải phân tán đều thì mới nhanh.
