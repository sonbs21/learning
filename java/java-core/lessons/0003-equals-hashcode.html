==, equals và hashCode: ba câu hỏi khác nhau

Bài 3 (viết lại) · Hiểu từng cái làm gì, vì sao phải override equals và hashCode cùng nhau, và cách viết chúng cho đúng

~40 phútCần biết: viết được class Java có field và constructorThư mục thực hành: lab/l0003

Học xong bài này, bạn sẽ:

  • Giải thích được ==, equals và hashCode mỗi cái trả lời câu hỏi gì.
  • Tự viết được equals và hashCode đúng cho một class, hoặc biết khi nào dùng record để khỏi phải viết.
  • Hiểu vì sao "chỉ override equals" làm HashSet và HashMap không tìm thấy dữ liệu, và tránh được hai bẫy hay gặp khi đi làm.

1 · Nhắc lại: biến kiểu object chứa gì?

Cả bài dựa trên một ý mà bạn đã gặp ở bài 4:

Object giống một tấm bảng treo trên tường (trong heap). Biến giống một tờ giấy ghi "tấm bảng ở ô số 7". Biến không chứa tấm bảng, mà chỉ chứa vị trí của nó. Vị trí đó gọi là tham chiếu (reference).

Diem a = new Diem(1, 2);   // tạo tấm bảng #1, tờ giấy a ghi "ô #1"
Diem b = new Diem(1, 2);   // tạo tấm bảng #2, tờ giấy b ghi "ô #2"
Diem c = a;                // tờ giấy c chép lại "ô #1", không tạo tấm bảng mới

Có hai tấm bảng (vì có hai lần new), và ba tờ giấy. a và c chỉ cùng một tấm bảng. b chỉ một tấm khác, chỉ là tình cờ có cùng nội dung (1, 2).

2 · Ba câu hỏi khác nhau

Bạn và một người bạn mua hai cuốn sách giống hệt nhau, cùng tên, cùng tác giả, cùng mã ISBN. Có ba câu hỏi khác nhau bạn có thể đặt ra:

  1. "Đây có phải là cùng MỘT cuốn sách không?" Không. Có hai cuốn riêng biệt, mỗi người cầm một cuốn.
  2. "Hai cuốn này có giống nhau về nội dung không?" Có. Cùng ISBN tức là cùng một đầu sách.
  3. "Cuốn này để ở kệ số mấy trong thư viện?" Thủ thư nhìn mã của sách để biết kệ. Hai cuốn giống nhau thì phải nằm cùng một kệ.

3 · ==: "có phải cùng một object không?"

== so sánh hai giá trị nằm trong hai biến. Nó không nhìn vào bên trong object:

  • Với số nguyên thuỷ (int, double, boolean...): giá trị trong biến chính là con số, nên == so hai con số. 5 == 5 là true.
  • Với object: giá trị trong biến là tham chiếu, nên == so hai tham chiếu, tức là hỏi "hai tờ giấy có ghi cùng một ô không?"
Diem a = new Diem(1, 2);
Diem b = new Diem(1, 2);
Diem c = a;
a == b   // false: hai tấm bảng khác nhau, dù nội dung giống hệt
a == c   // true : cùng một tấm bảng

Ở cấp độ bytecode, hai kiểu so sánh này là hai lệnh khác nhau. Bạn có thể tự xem bằng javap -c Ops trong lab/l0003:[JLS §15.21.3]

a == b  (kiểu Object) → if_acmpne     // "a" = reference: so hai tham chiếu
a == b  (kiểu int)    → if_icmpne     // "i" = int: so hai số
a.equals(b)           → invokevirtual Object.equals   // gọi một method bình thường
== trên object không bao giờ nhìn vào field. Hai object tạo bằng hai lần new thì == luôn ra false, dù nội dung giống hệt nhau.

4 · equals: "có giống nhau về nội dung không?"

Bản mặc định của equals chỉ là ==

Mọi class đều kế thừa Object, và Object có sẵn method equals. Đây là nguyên văn code trong JDK 21:[Object.java]

public boolean equals(Object obj) {
    return (this == obj);
}

Tức là nếu bạn không override, equals và == cho kết quả y hệt nhau. Java không thể tự đoán "giống nhau về nội dung" với class của bạn nghĩa là gì: hai NhanVien bằng nhau khi trùng mã nhân viên, hay khi trùng cả tên lẫn ngày sinh? Đó là quyết định của bạn.

Tận mắt xem: 4 phiên bản của cùng một class

Mở lab/l0003/Equality.java. File có 4 phiên bản class điểm (x, y), mỗi phiên bản tạo hai object a và b cùng là (1, 2):

  • P2 set.contains=false: đã có equals đúng mà HashSet vẫn không tìm thấy. Mục 5 sẽ giải thích lý do.

Cách viết một equals đúng

Ví dụ class Sach, coi hai cuốn là bằng nhau khi trùng mã isbn. Đi từng dòng:

@Override
public boolean equals(Object o) {
    if (this == o) return true;                    // ① cùng một object thì chắc chắn bằng nhau
    if (!(o instanceof Sach other)) return false;  // ② null hoặc không phải Sach thì không bằng
    return isbn.equals(other.isbn);                // ③ so các field quyết định "bằng nhau"
}
  1. ① Lối tắt: nếu là cùng một object thì khỏi so sánh gì nữa.
  2. ② Kiểm tra kiểu: tham số có kiểu Object, nên người ta có thể truyền vào bất cứ thứ gì, kể cả null hay một String. instanceof trả về false với null, nên dòng này lo luôn trường hợp đó. Phần Sach other (pattern matching, Java 16+) vừa kiểm tra kiểu vừa ép kiểu.
  3. ③ So field: chỉ so những field quyết định "hai cái là một". Nhớ dùng .equals để so field kiểu object như String (bài 4), và == cho field kiểu số nguyên thuỷ.

Lưu ý: tham số phải có kiểu Object. Nếu viết equals(Sach o) thì bạn đang tạo một method khác (overload) chứ không phải override, và HashSet sẽ không bao giờ gọi tới nó. Chú thích @Override giúp javac bắt lỗi này cho bạn.

5 · hashCode: "thuộc kệ nào?"

Thư viện có hàng nghìn kệ. Nếu mỗi lần tìm sách mà phải lục từng kệ thì quá chậm. Vì vậy mỗi cuốn sách có một mã số, và từ mã số đó tính ra số kệ. Cất sách thì cất vào đúng kệ đó. Tìm sách thì tính mã, đi thẳng tới kệ, rồi chỉ cần so vài cuốn trên kệ.

hashCode() chính là "mã số" đó: một con số int tính từ object. HashSet và HashMap dùng nó để chọn "kệ" (gọi là bucket). Bạn sẽ học kỹ bên trong ở bài 11. Ở đây chỉ cần biết thứ tự hai bước khi HashSet tìm một phần tử:

  1. Gọi hashCode() để chọn kệ. Chỉ xét những phần tử ở kệ đó, có hash trùng khớp.
  2. Trong kệ đó, gọi equals() để tìm đúng phần tử.

Bước 1 xảy ra trước. Nếu bước 1 đi sai kệ thì equals không bao giờ được gọi tới.

Vì sao P2 không tìm thấy?

P2 override equals nhưng không override hashCode, nên dùng bản mặc định của Object. Bản mặc định trả về một con số gắn với từng object riêng (gọi là identity hash), không liên quan gì tới nội dung. Xem tận mắt với HashValues.java:

javac HashValues.java
java HashValues
P2: equals=true  hashCode a=366712642  b=1829164700
P3: equals=true  hashCode a=994  b=994

(Số của P2 trên máy bạn sẽ khác, nhưng chắc chắn hai số khác nhau.)

  • P2: equals nói "bằng nhau", nhưng hai mã số khác hẳn nhau, nên HashSet đi tìm ở sai kệ, không thấy, và trả về false. equals của bạn không hề được gọi.
  • P3: hashCode() được override bằng Objects.hash(x, y), tính từ chính các field mà equals dùng. Hai object bằng nhau thì có cùng mã 994, nên vào đúng kệ và tìm thấy.

7 · Bẫy thật khi đi làm: sửa object đã nằm trong HashSet

Mở MutableKey.java. Class P đã override đúng cả equals và hashCode. Code bỏ p vào set, rồi sau đó mới sửa p.x = 100:

P p = new P(1, 2);
Set<P> set = new HashSet<>();
set.add(p);
p.x = 100;                       // sửa key SAU khi đã cho vào set

Đoán trước: set.contains(p) ra true hay false? set.size() bằng bao nhiêu?

javac MutableKey.java
java MutableKey
contains(p)   = false
size          = 1
iterate thấy p = true

Cùng một object p, nhưng contains(p) lại ra false!

  1. Lúc add, p là (1, 2). Hash tính từ (1, 2), và p được cất ở kệ A.
  2. Sửa x = 100. Bây giờ p là (100, 2), nên hash mới chỉ tới kệ B.
  3. contains(p) đi tìm ở kệ B, trong khi p vẫn nằm ở kệ A, nên không thấy. Duyệt cả set thì vẫn thấy p (size = 1), nhưng bạn cũng không remove nó được nữa. Đây là một dạng memory leak (bài 9).

Ngoài đời: một JPA entity tính hashCode từ id, mà id do database sinh ra. Trước khi lưu, id = null. Sau khi lưu, id có giá trị, hash đổi, và entity "biến mất" khỏi HashSet đang chứa nó.

Field dùng trong hashCode không được thay đổi khi object đang nằm trong HashSet hay là key của HashMap. Cách an toàn nhất: dùng object bất biến làm key (String, record có field bất biến, xem bài 16).
Câu phỏng vấn: "Phân biệt ==, equals và hashCode. Vì sao override equals phải override hashCode?"

"== so sánh hai giá trị trong biến: với primitive là so số, với object là so tham chiếu, tức là hỏi có phải cùng một object không. equals là method so sánh theo nội dung do class tự định nghĩa; bản mặc định trong Object chỉ là this == obj. hashCode trả về một số nguyên mà HashMap/HashSet dùng để chọn bucket. Contract: hai object equals nhau thì bắt buộc cùng hashCode, còn chiều ngược lại thì không. HashSet tìm bucket bằng hashCode trước rồi mới gọi equals. Nếu chỉ override equals thì hai object bằng nhau có hash khác nhau, nằm ở bucket khác nhau, nên contains/get trả về sai. Ngoài ra, không được sửa field dùng trong hashCode khi object đang nằm trong collection."

9 · Thử thách

A. Tự viết equals và hashCode

Viết class Sach có hai field isbn và ten. Hai cuốn sách được coi là bằng nhau khi trùng isbn, kể cả khi tên khác nhau (ví dụ một bản in lại). Sau đó kiểm tra:

Sach s1 = new Sach("978-0134685991", "Effective Java");
Sach s2 = new Sach("978-0134685991", "Effective Java (bản in lại)");
Set<Sach> kho = new HashSet<>(List.of(s1));
// Mong muốn: s1.equals(s2) == true, kho.contains(s2) == true,
//            s1.equals(null) == false, s1.equals("abc") == false
Xem lời giải 
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Sach other)) return false;
    return isbn.equals(other.isbn);
}

@Override
public int hashCode() { return isbn.hashCode(); }   // CÙNG field với equals
equals=true sameHash=true contains=true
equals(null)=false equals("abc")=false

Điểm mấu chốt: hashCode chỉ dùng isbn, giống hệt equals. Nếu bạn viết Objects.hash(isbn, ten) thì hai cuốn khác tên sẽ có hash khác nhau, vi phạm contract, và contains sẽ ra false.

B. hashCode luôn trả về 42

Const.java có record K(int v) với hashCode() luôn trả về 42. Trả lời hai câu: (1) Cách này có vi phạm contract không? (2) HashSet có chạy đúng không, và có chạy nhanh không?

(1) Không vi phạm: object bằng nhau vẫn cùng hash. (2) Chạy đúng, nhưng chậm hơn khoảng 240 lần, vì mọi phần tử dồn vào cùng một "kệ", nên mỗi lần tìm phải so equals với gần như toàn bộ set. Đúng contract mới là điều kiện tối thiểu. Hash còn phải phân tán đều thì mới nhanh.

Đào sâu: 5 tính chất mà mọi equals phải thoả

Javadoc của Object.equals yêu cầu equals phải:[Object.equals Javadoc]

  • Phản xạ (reflexive): x.equals(x) luôn true.
  • Đối xứng (symmetric): x.equals(y) thì y.equals(x).
  • Bắc cầu (transitive): x bằng y, y bằng z thì x bằng z.
  • Nhất quán (consistent): gọi nhiều lần vẫn ra cùng kết quả, nếu object không đổi.
  • Với null: x.equals(null) luôn false.

Mẫu ở mục 4 thoả cả 5 tính chất. Lỗi hay gặp nhất là phá tính đối xứng, khi class cha và class con so sánh lẫn nhau theo hai cách khác nhau. Vì vậy với class dữ liệu, record (là final, không có class con) là lựa chọn an toàn nhất.
