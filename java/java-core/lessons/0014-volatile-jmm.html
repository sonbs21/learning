Đã tắt cờ rồi, sao thread kia vẫn chạy mãi?

Bài 14 · Vấn đề "nhìn thấy" (visibility), từ khoá volatile, và quy tắc happens-before của Java Memory Model

~35 phútCần biết: Bài 8 (JIT), Bài 12 (thread), Bài 13 (thread dump)Thư mục thực hành: lab/l0014

Học xong bài này, bạn sẽ:

  • Tự tạo ra một chương trình treo vĩnh viễn chỉ vì một thread "không nhìn thấy" giá trị thread khác đã ghi.
  • Sửa được bằng volatile, và biết volatile không sửa được gì.
  • Giải thích được happens-before bằng lời thường. Đây là câu phỏng vấn concurrency nâng cao.

1 · Ôn bài 12 (trả lời trong đầu trước)

Ở bài 12, hai thread cùng chạy count++ thì mất dữ liệu. Vấn đề đó tên là gì, và nguyên nhân là gì?
Kiểm traRace condition: count++ gồm ba bước đọc → cộng → ghi, và hai thread chen ngang giữa các bước. Phần "Đào sâu" của bài 12 có nhắc tới một vấn đề khác: thread này ghi mà thread kia không nhìn thấy. Hôm nay ta tận mắt thấy nó.

2 · Thí nghiệm: cờ đã tắt mà không ai dừng

Mở lab/l0014/StopFlag.java. Ý tưởng rất đơn giản: thread worker chạy vòng lặp chừng nào cờ running còn bật. Nửa giây sau, main tắt cờ rồi chờ worker dừng.

static boolean running = true;          // cờ báo "tiếp tục chạy"

// thread worker:
while (running) {                       // cứ chạy khi cờ còn bật
    count++;
}
System.out.println("worker: thấy cờ tắt, dừng lại ...");

// thread main:
Thread.sleep(500);                      // cho worker chạy nửa giây
running = false;                        // main tắt cờ
worker.join();                          // chờ worker kết thúc
System.out.println("main: xong!");

Đoán trước: sau khoảng nửa giây, chương trình có in "main: xong!" không?

Ta chạy kèm timeout 5, nghĩa là "nếu sau 5 giây vẫn chưa xong thì giết chương trình", để khỏi phải đợi mãi:

cd lab/l0014
javac *.java
timeout 5 java StopFlag; echo "exit=$?"
main: đã tắt cờ, chờ worker dừng...
exit=124

exit=124 nghĩa là chương trình bị timeout giết sau 5 giây. Không có dòng "worker: thấy cờ tắt", không có "main: xong!". Chạy bao nhiêu lần cũng vậy.

Main đã gán running = false rõ ràng như vậy, nhưng worker không bao giờ nhìn thấy.

3 · Vì sao? Hai thủ phạm

Một nhân viên kho được dặn: "Cứ đóng hàng, chừng nào tấm biển ở văn phòng còn ghi MỞ CỬA". Đi ra văn phòng xem biển rất mất thời gian, nên anh ta chép chữ trên biển vào một mẩu giấy trong túi, rồi từ đó chỉ nhìn mẩu giấy.

Giám đốc lật biển sang ĐÓNG CỬA. Mẩu giấy trong túi vẫn ghi MỞ CỬA, nên nhân viên cứ đóng hàng mãi.

Trong máy tính có hai "mẩu giấy trong túi" như vậy:

  1. JIT tối ưu (bài 8): JIT thấy trong vòng lặp không có ai ghi vào running, nên nó "tối ưu" bằng cách đọc running một lần duy nhất rồi lặp mãi. Code JIT tạo ra tương đương với if (running) while (true) count++;.
  2. Cache của CPU: mỗi lõi CPU có bộ nhớ đệm riêng. Giá trị một lõi vừa ghi không nhất thiết được lõi khác thấy ngay.

Bằng chứng cho thủ phạm thứ nhất: tắt JIT bằng -Xint rồi chạy lại.

timeout 5 java -Xint StopFlag; echo "exit=$?"
main: đã tắt cờ, chờ worker dừng...
worker: thấy cờ tắt, dừng lại sau 89668745 vòng
main: xong!
exit=0

Không có JIT thì interpreter đọc lại running ở mỗi vòng lặp, nên thấy cờ tắt. Nhưng đừng vì thế mà nghĩ "lỗi tại JIT". Theo luật của Java, JIT được phép tối ưu như vậy, vì code không hề nói cho JVM biết biến này được dùng chung giữa nhiều thread.

Thread dump của một chương trình treo kiểu này

Nối với bài 13: chụp thread dump lúc chương trình đang treo (jps, rồi jcmd <PID> Thread.print), bạn sẽ thấy:

"main" ...
   java.lang.Thread.State: WAITING (on object monitor)      ← đang chờ join()
"worker" ... cpu=650.08ms elapsed=0.65s
   java.lang.Thread.State: RUNNABLE
	at StopFlag.lambda$main$0(StopFlag.java:8)              ← kẹt trong vòng lặp

Khác với deadlock ở bài 13 (thread BLOCKED, CPU gần 0%), ở đây worker là RUNNABLE và đốt CPU liên tục: cpu 650 ms trong 0,65 giây, tức 100% một lõi. "Treo mà CPU 100%" là dấu hiệu của vòng lặp không thoát được, và thread dump chỉ ra đúng dòng code.

4 · Cách sửa: volatile

Mở StopFlagVolatile.java. Khác biệt duy nhất là một từ khoá:

static volatile boolean running = true;
timeout 5 java StopFlagVolatile; echo "exit=$?"
main: đã tắt cờ, chờ worker dừng...
worker: thấy cờ tắt, dừng lại sau 1478437341 vòng
main: xong!
exit=0

volatile nói với JVM: "biến này được nhiều thread dùng chung. Mỗi lần đọc phải đọc giá trị mới nhất, không được giữ bản sao trong túi."[JLS §8.3.1.4] Trong câu chuyện, nhân viên bị bắt phải ra văn phòng nhìn biển mỗi lần.

5 · Happens-before: quy tắc "ai nhìn thấy gì"

Luật chính thức quy định thread nào nhìn thấy giá trị nào gọi là Java Memory Model (JMM).[JLS §17.4] Khái niệm trung tâm của nó là happens-before:

Nếu hành động X happens-before hành động Y, thì mọi thứ đã ghi trước X đều chắc chắn được nhìn thấy ở Y.
Nếu không có quan hệ happens-before nào, thì không có gì đảm bảo: thread kia có thể thấy giá trị cũ mãi mãi, như bạn vừa thấy.

Bạn không cần thuộc hết các quy tắc. Chỉ cần nhớ mấy quy tắc hay dùng nhất, trích nguyên văn từ JLS §17.4.5:[JLS §17.4.5]

Quy tắc (JLS)Nói đơn giản
"A write to a volatile field happens-before every subsequent read of that field."Ghi vào biến volatile thì thread đọc sau đó chắc chắn thấy.
"An unlock on a monitor happens-before every subsequent lock on that monitor."Thread ra khỏi khối synchronized, thì thread vào sau (cùng khoá) thấy hết những gì nó đã ghi. Đây là lý do synchronized ở bài 12 sửa được cả vấn đề "nhìn thấy".
"A call to start() on a thread happens-before any actions in the started thread."Những gì gán trước t.start() thì thread t chắc chắn thấy.

Ngoài ra còn một quy tắc tương tự cho join(): khi join() trả về, thread chờ thấy hết những gì thread kia đã ghi.

6 · volatile KHÔNG sửa được race condition

Đây là bẫy phỏng vấn kinh điển. Mở VolatileCount.java: y hệt Race.java ở bài 12, chỉ thêm volatile vào count.

static volatile int count = 0;
// 2 thread, mỗi thread count++ 100 000 lần
java VolatileCount
Mong đợi: 200000, thực tế: 132661

Vẫn mất dữ liệu. volatile chỉ đảm bảo mỗi lần đọc thấy giá trị mới nhất, nhưng count++ vẫn là ba bước đọc → cộng → ghi, và hai thread vẫn chen ngang được giữa các bước.

Vấn đềvolatilesynchronizedAtomicInteger / AtomicBoolean
Nhìn thấy giá trị mới (visibility)CóCóCó
Không bị chen ngang (atomic, chống race condition)KhôngCóCó (cho từng thao tác)
Dùng choCờ bật/tắt, một thread ghi nhiều thread đọcNhiều bước phải đi cùng nhauĐếm, cập nhật một giá trị
Câu phỏng vấn: "volatile dùng để làm gì? Nó có thay được synchronized không?"

"volatile đảm bảo visibility: một lần ghi vào biến volatile happens-before mọi lần đọc sau đó, nên các thread luôn thấy giá trị mới nhất, và JIT không được giữ bản sao của biến. Nó hợp với cờ dừng, hoặc trường hợp một thread ghi nhiều thread đọc. Nhưng volatile không đảm bảo tính atomic, nên count++ trên biến volatile vẫn bị race condition. Lúc đó cần synchronized hoặc AtomicInteger. synchronized đảm bảo cả hai: chỉ một thread vào một lúc, và unlock happens-before lock tiếp theo."

8 · Thử thách: sửa mà không dùng chữ volatile

Nhiệm vụ: sửa StopFlag.java để worker dừng đúng lúc, nhưng không được dùng từ khoá volatile. Gợi ý: ở bài 12 bạn đã dùng AtomicInteger. Có một class tương tự cho kiểu boolean.

timeout 5 java StopFlag; echo "exit=$?"     # mục tiêu: exit=0 và in "main: xong!"
Xem lời giải 
import java.util.concurrent.atomic.AtomicBoolean;
...
static AtomicBoolean running = new AtomicBoolean(true);
...
while (running.get()) { count++; }     // worker đọc
...
running.set(false);                      // main ghi
main: đã tắt cờ, chờ worker dừng...
worker: thấy cờ tắt, dừng lại sau 1118335043 vòng
main: xong!
exit=0

AtomicBoolean.get() và set() có cùng hiệu ứng nhìn thấy như đọc và ghi một biến volatile.[java.util.concurrent.atomic] Ngoài ra nó còn có những thao tác atomic như compareAndSet. Một cách khác là đọc và ghi cờ bên trong synchronized, theo quy tắc unlock happens-before lock.

Đào sâu: double-checked locking và "object chưa khởi tạo xong"

Visibility còn gây ra một lỗi khó hơn: thread khác có thể nhìn thấy tham chiếu tới một object trước khi nhìn thấy các field đã được constructor gán xong. Ví dụ kinh điển là mẫu singleton "double-checked locking":

private static Helper instance;              // thiếu volatile → có thể lỗi
static Helper get() {
    if (instance == null) {                  // đọc lần 1, ngoài khoá
        synchronized (Helper.class) {
            if (instance == null) instance = new Helper();
        }
    }
    return instance;                         // có thể trả về object "chưa xong"
}

Thread đọc instance ở dòng đầu (ngoài khoá) không có quan hệ happens-before với lần ghi bên trong khoá, nên có thể thấy object với các field vẫn còn giá trị mặc định. Cách sửa là khai báo private static volatile Helper instance;. Hoặc đơn giản hơn: dùng khởi tạo static (bài 5), vốn đã được JVM đảm bảo an toàn khi có nhiều thread.

Muốn đi sâu nữa thì đọc bài của Aleksey Shipilëv (kỹ sư HotSpot): Close Encounters of The Java Memory Model Kind. Bài dài và khó, nhưng là nguồn đáng tin nhất về JMM.
