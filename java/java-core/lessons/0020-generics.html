Generics: nhãn dán chỉ tồn tại lúc biên dịch

Bài 20 · Vì sao List<String> và List<Integer> là cùng một class lúc chạy, vì sao List<Integer> không phải là List<Number>, và khi nào dùng ? extends / ? super

Học xong bài này, bạn sẽ:

  • Giải thích được type erasure và chứng minh nó bằng code chạy thật.
  • Hiểu vì sao List<Integer> không gán được cho List<Number>, trong khi mảng thì được (và vì sao mảng làm vậy là nguy hiểm).
  • Viết đúng chữ ký method với ? extends và ? super theo quy tắc PECS.

1 · Ôn bài 10 và bài 7 (trả lời trong đầu trước)

(a) Bên trong ArrayList<String>, dữ liệu được cất trong một mảng kiểu gì?

(b) Overload được chọn bởi ai, lúc nào, dựa vào cái gì?

Kiểm tra(a) Object[], chứ không phải String[]. Lạ nhỉ? Mục 3 sẽ giải thích. (b) Compiler, lúc biên dịch, dựa vào kiểu khai báo. Hôm nay bạn gặp lại ý "compiler lo hết lúc biên dịch, lúc chạy JVM không biết gì" ở dạng mới.

2 · Không có generics thì khổ thế nào?

Hình dung một kho có những chiếc hộp không dán nhãn. Ai muốn bỏ gì vào cũng được. Tới lúc lấy ra, bạn đoán "chắc là cà phê" rồi pha luôn, và chỉ phát hiện đó là muối khi đã uống.

Generics là dán nhãn lên hộp: "hộp này chỉ đựng cà phê". Người giữ kho (compiler) kiểm tra nhãn ngay lúc bỏ đồ vào, nên lúc lấy ra bạn không phải đoán nữa.

Trước Java 5 chưa có generics, list chỉ là "hộp không nhãn". KhongGeneric.java viết theo kiểu cũ đó (gọi là raw type: dùng List trơn, không có <...>):

List ds = new ArrayList();          // "raw type": hộp không dán nhãn
ds.add("cà phê");
ds.add(42);                         // compiler không cản
for (Object o : ds) {
    String s = (String) o;          // tự ép kiểu lấy ra
    System.out.println(s.toUpperCase());
}

javac KhongGeneric.java
java KhongGeneric
Note: KhongGeneric.java uses unchecked or unsafe operations.
Note: Recompile with -Xlint:unchecked for details.
CÀ PHÊ
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String
	at KhongGeneric.main(KhongGeneric.java:10)

Lỗi chỉ lộ ra lúc chạy, ở chỗ lấy ra, xa chỗ bỏ nhầm vào. Viết List<String> ds thì dòng ds.add(42) bị chặn ngay khi biên dịch. Đó là toàn bộ lý do generics tồn tại: chuyển lỗi từ lúc chạy sang lúc biên dịch.[Oracle: Why Use Generics?]

Hai dòng "Note" là compiler cảnh báo bạn đang dùng raw type. Code mới đừng bao giờ dùng raw type (Effective Java, Item 26).

3 · Type erasure: nhãn bị bóc trước khi vào kho

Đây là điều bất ngờ nhất về generics trong Java: nhãn chỉ tồn tại lúc biên dịch. Compiler kiểm tra nhãn xong thì bóc nhãn ra rồi mới ghi vào file .class. Lúc chạy, JVM chỉ thấy List trơn. Việc bóc nhãn này gọi là type erasure (xoá kiểu).[JLS §4.6]

Kiểm chứng bằng Erasure.java:

List<String>  chu = new ArrayList<>();
List<Integer> so  = new ArrayList<>();
System.out.println("Cùng một class lúc chạy? " + (chu.getClass() == so.getClass()));
System.out.println("Class thật: " + chu.getClass().getName());

chu.add("cà phê");
String s = chu.get(0);              // không cần ép kiểu?
javac Erasure.java
java Erasure
Cùng một class lúc chạy? true
Class thật: java.util.ArrayList
cà phê

Lúc chạy không có class "ArrayList của String" hay "ArrayList của Integer", chỉ có một java.util.ArrayList. Vậy tại sao String s = chu.get(0) không cần ép kiểu? Xem bytecode:

javap -c Erasure | grep -E 'List.(add|get)|checkcast'
70: invokeinterface #45,  2   // InterfaceMethod java/util/List.add:(Ljava/lang/Object;)Z
78: invokeinterface #49,  2   // InterfaceMethod java/util/List.get:(I)Ljava/lang/Object;
83: checkcast     #53         // class java/lang/String
  1. add nhận Object, get trả về Object. Nhãn <String> đã biến mất. Đó cũng là lý do bên trong ArrayList là Object[] (bài 10): nó phải chứa được mọi thứ.
  2. Lệnh checkcast String là phép ép kiểu do compiler tự viết thay bạn. Code nhìn sạch sẽ, nhưng bytecode y hệt kiểu cũ ở mục 2. Khác biệt duy nhất: compiler đã kiểm tra nhãn rồi, nên phép ép kiểu này "chắc chắn" đúng.

Vì sao Java lại thiết kế vậy? Để tương thích ngược: code Java 5 có generics phải chạy chung được với thư viện cũ viết bằng raw type, mà không cần sửa JVM.[Oracle: Type Erasure]

Type erasure: <T> chỉ để compiler kiểm tra. Sau khi biên dịch, T bị thay bằng Object (hoặc bằng cận trên, ví dụ T extends Number → Number), và compiler tự chèn checkcast ở chỗ lấy ra. JVM lúc chạy không biết T là gì.

Hệ quả 1: những thứ không làm được với T

Lúc chạy không còn biết T là gì, nên mọi thao tác cần biết kiểu thật lúc chạy đều bị cấm:

javac loi/NewT.java          # new T() và o instanceof T
javac loi/NameClash.java     # overload in(List<String>) và in(List<Integer>)
loi/NewT.java:2: error: unexpected type
    T tao() { return new T(); }
  required: class
  found:    type parameter T

loi/NameClash.java:5: error: name clash: in(List<Integer>) and in(List<String>) have the same erasure

Lỗi thứ hai nối thẳng với bài 7: sau khi bóc nhãn, hai method đều thành in(List), cùng chữ ký, nên không còn là overload hợp lệ.

Hệ quả 2: "rác lọt kho" (heap pollution)

Nếu có ai đó lách qua compiler bằng raw type, JVM không chặn lại được, vì lúc chạy nó không thấy nhãn. LenLut.java:

static void themBay(List ds) { ds.add(42); }        // nhận raw List, nhét Integer vào

List<String> chu = new ArrayList<>();
themBay(chu);                                    // lúc chạy không ai kiểm tra
System.out.println("Kích thước: " + chu.size());
Object o = chu.get(0);                           // lấy ra dạng Object: chưa sao
System.out.println("Lấy ra được: " + o);
String s = chu.get(0);                           // compiler chèn ép kiểu String: nổ
javac LenLut.java
java LenLut
Kích thước: 1
Lấy ra được: 42
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String
	at LenLut.main(LenLut.java:14)

Một List<String> đang chứa số 42, và chương trình chạy bình thường cho tới dòng 14, nơi compiler đã chèn checkcast. Stack trace chỉ vào chỗ lấy ra, không phải chỗ bỏ vào (themBay). Ngoài đời, đây là loại bug khó tìm: thường do thư viện cũ dùng raw type, hoặc do reflection/JSON deserialize nhét sai kiểu. Vì vậy đừng bỏ qua cảnh báo "unchecked".[JLS §4.12.2]

4 · List<Integer> không phải là List<Number>

Integer là một loại Number. Vậy chắc List<Integer> cũng là một loại List<Number>? loi/ListNumber.java:

List<Integer> soNguyen = new ArrayList<>();
List<Number> so = soNguyen;
javac loi/ListNumber.java
loi/ListNumber.java:7: error: incompatible types: List<Integer> cannot be converted to List<Number>

Một giỏ táo có phải là một giỏ trái cây không? Nghe thì có. Nhưng "giỏ trái cây" cho phép bỏ chuối vào. Nếu được coi giỏ táo là giỏ trái cây, ai đó sẽ bỏ chuối vào giỏ táo, và người lấy ra "chắc chắn là táo" sẽ cắn phải chuối.

Nếu dòng trên được phép thì so.add(1.5) sẽ hợp lệ (1.5 là Number), và một Double nằm trong soNguyen. Đó đúng là heap pollution ở mục 3. Nên Java cấm: List<A> và List<B> không có quan hệ cha–con, dù A và B có. Tính chất này gọi là bất biến (invariant).

Mảng thì ngược lại, và trả giá cho điều đó. BatBien.java:

Number[] mang = new Integer[2];     // mảng: được phép
mang[0] = 1;
mang[1] = 1.5;                      // Double vào mảng Integer?
javac BatBien.java
java BatBien
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Double
	at BatBien.main(BatBien.java:5)

Mảng cho gán (gọi là covariant), nên phải tự kiểm tra lúc chạy. Làm được vì mảng nhớ kiểu thật của mình (Integer[]), không bị xoá như generics.[JLS §10.5] Generics không nhớ kiểu lúc chạy, nên chọn cách an toàn hơn: chặn ngay lúc biên dịch.

Generics bất biến: List<Integer> không phải List<Number>. Lý do: nếu được thì sẽ bỏ được Double vào list số nguyên. Mảng thì cho phép, nên lỗi chỉ lộ ra lúc chạy (ArrayStoreException).

5 · Wildcard: ? extends để đọc, ? super để ghi

Bất biến thì an toàn, nhưng gây khó khăn. Viết method tính tổng tong(List<Number> ds) thì không truyền được List<Integer> vào. Wildcard (dấu ?, nghĩa là "một kiểu nào đó") giải quyết chuyện này, với hai dạng. Wildcard.java:

// ? extends Number: "list của MỘT loại con nào đó của Number" → chỉ ĐỌC ra
static double tong(List<? extends Number> ds) {
    double t = 0;
    for (Number n : ds) t += n.doubleValue();
    return t;
}
// ? super Integer: "list chứa được Integer" → chỉ GHI vào
static void them123(List<? super Integer> ds) {
    ds.add(1); ds.add(2); ds.add(3);
}

tong(List.of(1, 2, 3));        // List<Integer>
tong(List.of(1.5, 2.5));       // List<Double>
them123(so);                   // List<Number>
them123(doVat);                // List<Object>, đang có "ly"
javac Wildcard.java
java Wildcard
6.0
4.0
[1, 2, 3] [ly, 1, 2, 3]

Vì sao ? extends chỉ đọc, còn ? super chỉ ghi? Quay lại chuyện giỏ:

List<? extends Number>List<? super Integer>
Nghĩa là"giỏ của một loại trái cây nào đó, không biết loại gì""giỏ đựng được táo, có thể là giỏ táo, giỏ trái cây, hoặc thùng đồ vật"
Có thể thật ra làList<Integer>, List<Double>...List<Integer>, List<Number>, List<Object>
Đọc ra✔ Chắc chắn là Number✘ Chỉ biết là Object
Ghi vào✘ Không biết đúng loại nào, bỏ gì cũng có thể sai✔ Bỏ Integer vào luôn đúng

Compiler chặn đúng như bảng:

javac loi/ExtendsAdd.java    # ds.add(1) với List<? extends Number>
javac loi/SuperGet.java      # Integer x = ds.get(0) với List<? super Integer>
loi/ExtendsAdd.java:6: error: incompatible types: int cannot be converted to CAP#1
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Number from capture of ? extends Number

loi/SuperGet.java:6: error: incompatible types: CAP#1 cannot be converted to Integer
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Object super: Integer from capture of ? super Integer

CAP#1 là tên compiler đặt cho "cái kiểu không biết tên đó". Đọc lỗi thứ nhất theo lời thường: "list này chứa một loại con của Number mà tôi không biết là gì, nên tôi không dám cho bạn bỏ 1 vào".

PECS: Producer Extends, Consumer Super (Effective Java, Item 31).
Tham số cung cấp dữ liệu cho bạn đọc (producer) → ? extends T.
Tham số nhận dữ liệu bạn ghi vào (consumer) → ? super T.
Vừa đọc vừa ghi → không dùng wildcard, để List<T>.[Oracle: Wildcard Guidelines]

Thư viện chuẩn làm đúng như vậy. Chữ ký của Collections.copy:[Javadoc]

public static <T> void copy(List<? super T> dest, List<? extends T> src)

src cung cấp dữ liệu nên là extends. dest nhận dữ liệu nên là super.

7 · Thử thách: sửa chữ ký theo PECS

Challenge.java có method chép phần tử từ list này sang list khác:

// TODO: sửa CHỈ chữ ký của method này để main biên dịch được
static <T> void chep(List<T> nguon, List<T> dich) {
    for (T x : nguon) dich.add(x);
}

List<Integer> soNguyen = List.of(1, 2, 3);
chep(soNguyen, so);       // so    là List<Number>
chep(soNguyen, doVat);    // doVat là List<Object>

Hiện tại nó không biên dịch được:

Challenge.java:14: error: method chep in class Challenge cannot be applied to given types;
  required: List<T>,List<T>
  found:    List<Integer>,List<Number>
  reason: inference variable T has incompatible equality constraints Number,Integer

Dòng "reason" nói: T vừa phải là Integer (theo nguon) vừa phải là Number (theo dich), không thể cả hai. Hãy tự hỏi: tham số nào là producer, tham số nào là consumer?

Xem lời giải 
static <T> void chep(List<? extends T> nguon, List<? super T> dich)
[1, 2, 3] [1, 2, 3]

nguon cung cấp dữ liệu (producer) → extends. dich nhận dữ liệu (consumer) → super. Compiler chọn T = Integer: List<Integer> khớp ? extends Integer, còn List<Number> và List<Object> khớp ? super Integer. Giống hệt chữ ký của Collections.copy.

Đào sâu: nhãn không bị xoá hết, và Spring tận dụng điều đó

Erasure xoá kiểu của object lúc chạy. Nhưng phần khai báo (kiểu của field, tham số method, class cha) vẫn được ghi lại trong file .class, ở một mục gọi là thuộc tính Signature.[JVMS §4.7.9] Reflection đọc được nó. GenericInfo.java:

List<String> danhSach;     // field

GenericInfo.class.getDeclaredField("danhSach").getGenericType()
new ArrayList<String>() {}.getClass().getGenericSuperclass()   // có {}: class con ẩn danh
new ArrayList<String>().getClass().getGenericSuperclass()      // không có {}
java.util.List<java.lang.String>
java.util.ArrayList<java.lang.String>
java.util.AbstractList<E>
  • Dòng 1: kiểu khai báo của field vẫn còn <String>. Spring dùng chính thông tin này để inject đúng bean vào field List<PaymentHandler> hay Repository<User>.
  • Dòng 2 và 3: thêm {} là tạo một class con ẩn danh, và <String> trở thành một phần khai báo class cha của nó, nên được giữ lại. Không có {} thì chỉ thấy <E> chung chung. Đây là mẹo "super type token" nằm sau new ParameterizedTypeReference<List<User>>() {} của Spring và new TypeReference<...>() {} của Jackson: cách duy nhất để báo cho thư viện biết "tôi muốn List<User>", khi List<User>.class là cú pháp không tồn tại.
