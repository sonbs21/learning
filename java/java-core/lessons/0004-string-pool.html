Vì sao "hi" == "hi" lại đúng, còn new String("hi") thì không?

Bài 4 · String pool, tính bất biến (immutable), và một bug rất hay gặp khi đi làm

~30 phútCần biết: Bài 1 (javac, chạy chương trình)Thư mục thực hành: lab/l0004

Học xong bài này, bạn sẽ:

  • Giải thích được vì sao == với String lúc ra true, lúc ra false.
  • Hiểu String pool là gì và vì sao String không sửa được.
  • Không bao giờ mắc bug so sánh String bằng == nữa.

1 · Ôn lại nhanh: biến giữ cái gì?

Trước khi nói về String, cần nhớ lại một điều: với object (String cũng là một object), biến không chứa object. Biến chỉ chứa một "tờ giấy ghi vị trí" của object.

Object giống một tấm bảng treo trên tường. Biến giống một tờ giấy ghi "tấm bảng ở ô số 7".

Hai biến có thể là hai tờ giấy khác nhau nhưng cùng ghi "ô số 7", tức là cùng chỉ tới một tấm bảng.

Từ đó có hai cách so sánh:

Cách so sánhCâu hỏi nó trả lời
a == b"Hai tờ giấy có chỉ tới cùng một tấm bảng không?"
a.equals(b)"Chữ viết trên hai tấm bảng có giống nhau không?"

Tờ giấy ghi vị trí đó có tên chính thức là tham chiếu (reference). Từ giờ ta dùng từ này.

2 · Đoán trước, rồi chạy thử

Mở file Pool.java:

String a = "hi";
String b = "hi";
String c = new String("hi");

System.out.println("1. a == b      : " + (a == b));
System.out.println("2. a == c      : " + (a == c));
System.out.println("3. a.equals(c) : " + a.equals(c));

Cả ba biến đều chứa chữ "hi". Hãy đoán ba dòng in ra là true hay false, ghi ra giấy, rồi chạy:

cd lab/l0004
javac Pool.java
java Pool
1. a == b      : true
2. a == c      : false
3. a.equals(c) : true
4. a == c.intern() : true

Dòng 3 dễ hiểu: chữ giống nhau thì equals ra true. Dòng 1 và 2 mới là điều lạ: vì sao a == b lại đúng, mà a == c thì sai? (Dòng 4 sẽ giải thích ở mục 4.)

3 · String pool: kệ chữ dùng chung

Một lớp học thường xuyên cần những tấm bảng ghi chữ "hi", "ok", "admin"... Nếu mỗi bạn cần chữ "hi" lại tự làm một tấm bảng mới thì lớp sẽ ngập bảng, rất phí.

Vì vậy lớp làm một kệ chung. Ai cần chữ "hi" thì trước tiên nhìn lên kệ:

  • Kệ đã có tấm "hi" thì dùng luôn tấm đó, chỉ cần ghi vị trí của nó vào tờ giấy của mình.
  • Kệ chưa có thì làm một tấm mới, đặt lên kệ, rồi dùng.

Trong Java, cái kệ chung đó gọi là String pool. Khi bạn viết một chuỗi trực tiếp trong code bằng dấu nháy kép, như "hi" (cách viết này gọi là string literal), Java tự động dùng kệ chung.[JLS §3.10.5]

Giờ đi lại từng dòng code:

  1. String a = "hi";: Java nhìn kệ, chưa có "hi", nên tạo một tấm "hi" đặt lên kệ. Biến a ghi vị trí tấm đó.
  2. String b = "hi";: Java nhìn kệ, đã có "hi", nên b ghi cùng vị trí với a. Không có tấm mới nào được tạo.
  3. String c = new String("hi");: từ khoá new nghĩa là "làm cho tôi một tấm bảng MỚI, đừng lấy trên kệ". Vì vậy c chỉ tới một tấm khác, nằm ngoài kệ.

Biến (tờ giấy)

main
a→ tấm #1
b→ tấm #1
c→ tấm #2

Các tấm bảng (object)

tấm #1 · trên kệ String pool
chữ"hi"
tấm #2 · tạo bằng new, ngoài kệ
chữ"hi"

a và b chỉ cùng một tấm, nên a == b là true. c chỉ tấm khác, nên a == c là false, dù chữ giống hệt nhau.

4 · intern(): tự tay đặt lên kệ

Method c.intern() nghĩa là: "nhìn lên kệ xem có tấm nào chữ giống c không. Có thì đưa tôi vị trí tấm trên kệ." Kệ đã có tấm #1, nên c.intern() trả về tấm #1. Đó là lý do a == c.intern() ra true.[String.intern]

Bạn hiếm khi phải tự gọi intern(). Chỉ cần biết nó tồn tại để hiểu cơ chế của kệ.

5 · Vì sao String không sửa được?

Quay lại cái kệ chung. Giả sử bạn A và bạn B cùng dùng tấm "hi" trên kệ. Nếu bạn A lấy bút sửa tấm đó thành "bye", thì bạn B cũng bị đổi theo mà không hề hay biết. Như vậy rất nguy hiểm.

Cách giải quyết: mọi tấm bảng đều được ép plastic, không ai sửa được. Muốn chữ khác thì phải làm tấm mới.

Đó là lý do String trong Java là immutable (bất biến): một khi đã tạo thì không thay đổi được nữa.[String Javadoc: "Strings are constant"] Mọi method trông như "sửa" String, như toUpperCase(), replace(), trim(), thật ra đều tạo String mới và trả về String mới đó.

Thử với Immutable.java. Đoán trước dòng 1 in ra gì:

String s = "hello";
s.toUpperCase();                 // gọi nhưng không giữ kết quả
System.out.println("1. s = " + s);

String t = s.toUpperCase();      // giữ kết quả vào t
System.out.println("2. t = " + t);
System.out.println("3. s = " + s);
javac Immutable.java
java Immutable
1. s = hello
2. t = HELLO
3. s = hello

Dòng 1 vẫn là hello, vì toUpperCase() tạo ra tấm "HELLO" mới, nhưng không ai giữ tờ giấy ghi vị trí của nó. s vẫn chỉ tấm "hello" cũ. Đây là lỗi người mới hay mắc: gọi s.trim() rồi tưởng s đã được sửa.

  • Chuỗi viết trong dấu nháy kép ("hi") được lấy từ String pool. Chuỗi giống nhau thì dùng chung một object.
  • new String(...) luôn tạo object mới, nằm ngoài pool.
  • String là immutable. Muốn giữ kết quả của toUpperCase(), trim()... thì phải gán vào biến.

6 · Bug thật khi đi làm: so sánh String bằng ==

Đây là lý do quan trọng nhất của bài này. Xem Login.java:

String role = args[0];      // chữ do người dùng gõ vào lúc chạy
System.out.println("role == \"admin\"      : " + (role == "admin"));
System.out.println("role.equals(\"admin\") : " + role.equals("admin"));
javac Login.java
java Login admin
role == "admin"      : false
role.equals("admin") : true

Người dùng gõ đúng chữ admin, vậy mà == lại ra false!

Lý do: chữ đến từ bên ngoài chương trình (người dùng gõ, request HTTP, database, file...) được tạo ra lúc chạy, giống như dùng new. Nó không nằm trên kệ. Vì vậy nó là một object khác với "admin" trong code của bạn.

Điều nguy hiểm là: lúc bạn tự test bằng chuỗi viết sẵn trong code, == có thể vẫn ra true (vì cả hai đều nằm trên kệ). Code "chạy được" trên máy bạn, rồi hỏng khi lên production với dữ liệu thật.

So sánh nội dung String thì luôn dùng .equals(), không bao giờ dùng ==.
Câu phỏng vấn: "String pool là gì? Vì sao String là immutable?"

"String pool là vùng nhớ nơi Java lưu các string literal. Các literal giống nhau dùng chung một object để tiết kiệm bộ nhớ. Vì nhiều biến có thể cùng chỉ tới một object, String phải là immutable: nếu sửa được thì sửa ở một chỗ sẽ làm hỏng mọi chỗ khác đang dùng chung. Đó cũng là lý do phải so sánh String bằng equals, vì == chỉ so xem có cùng object hay không."

8 · Thử thách: đoán 4 dòng

Mở Challenge.java. Đoán từng dòng là true hay false trước khi chạy. Gợi ý nằm ngay dưới mỗi dòng.

String a = "hi";
String h = "h";
System.out.println("1. " + (a == "h" + "i"));
System.out.println("2. " + (a == h + "i"));
Integer x = 127, y = 127;
Integer m = 128, n = 128;
System.out.println("3. " + (x == y));
System.out.println("4. " + (m == n));
  • Dòng 1: "h" + "i" là hai chữ viết sẵn trong code. Theo bạn, javac có thể tự ghép chúng ngay lúc biên dịch không?
  • Dòng 2: h là một biến. Giá trị của biến chỉ được biết lúc chạy.
  • Dòng 3 và 4: Integer (chữ I viết hoa) là object, không phải số int thường. Java cũng có một "kệ chung" cho một số con số...
javac Challenge.java
java Challenge
Xem đáp án 
1. true
2. false
3. true
4. false
  • Dòng 1 (true): "h" + "i" gồm toàn chữ viết sẵn, nên javac ghép thành "hi" ngay lúc biên dịch. Kết quả là một literal bình thường, lấy từ kệ.[JLS §15.29]
  • Dòng 2 (false): h + "i" có biến, nên phép ghép xảy ra lúc chạy và tạo object mới ngoài kệ (giống bug ở Login.java).
  • Dòng 3 (true) và 4 (false): Java có sẵn một "kệ" cho các Integer từ -128 đến 127. 127 nằm trong khoảng nên dùng chung object; 128 nằm ngoài nên mỗi lần là một object mới.[JLS §5.1.7] Đây là bug thật: so sánh hai Integer (ví dụ hai ID lấy từ database) bằng == chạy đúng khi test với số nhỏ, rồi hỏng khi ID vượt 127. Bài học vẫn y như cũ: object thì so bằng equals.
Đào sâu: String pool nằm ở đâu trong bộ nhớ?

Từ Java 7, String pool nằm trong heap, vùng nhớ chung chứa mọi object. Vì vậy các String trên kệ cũng được dọn rác (GC) như object thường khi không ai dùng nữa. Trước Java 7, pool nằm ở một vùng riêng tên là "permanent generation" và hay gây lỗi hết bộ nhớ.[JDK 7 Release Notes]

Ngoài việc cho phép dùng chung, tính immutable còn có lợi cho bảo mật và cho đa luồng: một String đã tạo thì không ai sửa được, nên nhiều thread đọc cùng lúc vẫn an toàn mà không cần khoá. Ta sẽ quay lại ý này ở bài về thread.
