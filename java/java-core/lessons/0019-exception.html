Exception: báo lỗi, dọn dẹp, và cái giá của stack trace

Bài 19 · Checked vs unchecked, finally, try-with-resources, vì sao tạo exception lại tốn kém, và vì sao log production đôi khi chỉ ghi NullPointerException: null

~45 phútCần biết: Bài 8 (JIT), Bài 17 (proxy, @Transactional)Thư mục thực hành: lab/l0019

Học xong bài này, bạn sẽ:

  • Phân biệt checked, unchecked và Error, và biết vì sao Spring chỉ rollback với một loại.
  • Đoán đúng thứ tự chạy của try/catch/finally, kể cả khi có return.
  • Dùng try-with-resources đúng cách, và hiểu vì sao nó tốt hơn finally kiểu cũ.
  • Biết exception tốn ở đâu, và đọc được log production khi stack trace "biến mất".

1 · Ôn bài 17 và bài 8 (trả lời trong đầu trước)

(a) Với @Transactional, ai mở và đóng (commit/rollback) transaction cho method của bạn?

(b) Code chạy càng nhiều lần thì JIT làm gì với nó?

Kiểm tra(a) Proxy do Spring tạo ra, đứng giữa người gọi và bean của bạn. Proxy quyết định commit hay rollback dựa vào loại exception bay ra khỏi method, như bạn sẽ thấy ở mục 2. (b) Biên dịch sang mã máy và tối ưu mạnh tay. Mục 6 cho thấy một tối ưu của JIT có thể làm stack trace biến mất.

2 · Ba loại "sự cố": cây gia phả của exception

Quán cà phê gặp ba kiểu sự cố:

  • Hết sữa, nhà cung cấp giao trễ: chuyện ngoài tầm kiểm soát nhưng biết trước sẽ có lúc xảy ra. Quản lý bắt buộc mọi ca phải có phương án. Đây là checked exception.
  • Nhân viên pha nhầm công thức: lỗi do chính mình, sửa quy trình chứ không cần kế hoạch dự phòng cho từng ly. Đây là unchecked exception (RuntimeException).
  • Mất điện cả toà nhà: quán không tự xử lý được. Đây là Error.

CayException.java in ra "cây gia phả" của vài exception quen thuộc:

Chữ "checked" nghĩa là compiler kiểm tra.[JLS §11.1.1] loi/ChuaXuLy.java gọi Files.readString (có thể ném IOException) mà không xử lý:

javac loi/ChuaXuLy.java
loi/ChuaXuLy.java:6: error: unreported exception IOException; must be caught or declared to be thrown

Đây hoàn toàn là luật của compiler. Lúc chạy, JVM đối xử với checked và unchecked y như nhau.

Liên hệ Spring: vì sao @Transactional "không rollback"? Mặc định, proxy của Spring chỉ rollback khi method ném ra unchecked exception (hoặc Error). Gặp checked exception, nó vẫn commit.[Spring: Rolling Back a Declarative Transaction] Bạn ném IOException giữa chừng và tưởng dữ liệu đã được hoàn tác, nhưng thật ra một nửa đã được lưu. Muốn rollback cả checked exception thì phải ghi rõ: @Transactional(rollbackFor = Exception.class).

Checked (con của Exception, không qua RuntimeException): compiler bắt phải xử lý. Unchecked (con của RuntimeException): không bắt buộc. Spring mặc định chỉ rollback với unchecked.

3 · finally: luôn chạy, kể cả khi đã return

finally là phần "dọn dẹp" luôn được chạy, dù try kết thúc bình thường, bằng return, hay bằng exception. Finally.java:

static String laySo() {
    try {
        System.out.println("  try: chuẩn bị return");
        return "từ try";
    } finally {
        System.out.println("  finally: vẫn chạy dù try đã return");
    }
}

static String nuotLoi() {
    try {
        throw new IllegalStateException("lỗi quan trọng");
    } finally {
        return "finally return đè lên";      // KHÔNG BAO GIỜ làm thế này
    }
}

java Finally

  finally: vẫn chạy dù try đã return
Kết quả: từ try
Kết quả: finally return đè lên
  • Hàm thứ nhất: return trong try không bỏ qua được finally. Finally chạy xong, giá trị "từ try" mới được trả về.[JLS §14.20.2]
  • Hàm thứ hai là một bẫy: return trong finally nuốt mất exception. Lỗi "quan trọng" biến mất không dấu vết, người gọi tưởng mọi thứ ổn. Compiler chỉ cảnh báo (-Xlint:finally), không chặn.

4 · try-with-resources: dọn dẹp mà không làm mất lỗi

Kết nối database, file, socket... dùng xong phải đóng, nếu không sẽ cạn tài nguyên (ví dụ connection pool hết kết nối, app treo). Cách cũ là đóng trong finally. Nhưng nếu chính việc đóng cũng lỗi thì sao? TaiNguyen.java có một "kết nối" mà close() ném lỗi, thử theo hai cách:

// Kiểu cũ
KetNoi k = new KetNoi("DB", true);
try {
    throw new RuntimeException("lỗi khi truy vấn");      // lỗi gốc
} finally {
    k.close();                                          // close cũng lỗi → ?
}

// Kiểu mới: try-with-resources
try (KetNoi db = new KetNoi("DB", true); KetNoi file = new KetNoi("File", false)) {
    throw new RuntimeException("lỗi khi truy vấn");
}

  1. Kiểu cũ làm mất lỗi gốc. Exception từ close() đè lên "lỗi khi truy vấn". Trong log bạn chỉ thấy "lỗi khi đóng DB" và đi tìm nhầm chỗ.
  2. try-with-resources giữ lỗi gốc, và gắn lỗi khi đóng vào làm suppressed (lấy ra bằng getSuppressed(), và được in kèm trong stack trace). Không mất thông tin nào.[JLS §14.20.3]
  3. Đóng theo thứ tự ngược: mở DB rồi File, thì đóng File rồi DB. Giống xếp chồng đĩa: cái đặt sau lấy ra trước.
  4. Tài nguyên nào dùng được trong try (...)? Bất kỳ class nào implements AutoCloseable (bài 18). Connection, InputStream, ExecutorService (Java 19+, bài 15) đều thế.
Có tài nguyên cần đóng → luôn dùng try-with-resources. Nó đóng tự động, đóng theo thứ tự ngược, và không bao giờ để lỗi khi đóng che mất lỗi gốc. Không bao giờ return trong finally.

5 · Tạo exception tốn ở đâu?

Lúc được tạo ra, exception chụp lại toàn bộ call stack (method nào gọi method nào, dòng bao nhiêu) để sau này in stack trace. Việc chụp này nằm trong fillInStackTrace(), và stack càng sâu thì càng tốn. ChiPhi.java tạo exception ở đáy một chuỗi gọi đệ quy sâu 10 hoặc 200 tầng, đo sau khi đã làm nóng JIT (bài 8). Ngoài ra nó có một loại exception tắt việc chụp stack (constructor đặc biệt của Throwable với writableStackTrace = false).[Throwable constructor]

javac ChiPhi.java
java ChiPhi
Có stack trace, sâu 10 tầng : 762 ns/lần
Có stack trace, sâu 200 tầng: 5618 ns/lần
Không stack trace, sâu 200  : 581 ns/lần
Tạo object thường, sâu 200  : (để so sánh) 562 ns/lần
  • Ở độ sâu 200, chụp stack tốn khoảng 5000 ns mỗi lần, gấp khoảng 10 lần so với không chụp. Không chụp stack thì exception rẻ ngang một object thường (phần ~560 ns còn lại là chi phí của 200 lần gọi đệ quy).
  • Ứng dụng Spring thường có stack rất sâu (filter, proxy, controller, service... thường trên 100 tầng), nên chi phí này là có thật.
  • Kết luận thực tế: đừng dùng exception để điều khiển luồng bình thường (ví dụ ném exception để báo "không tìm thấy" hàng nghìn lần mỗi giây). Exception dành cho tình huống bất thường. Còn thỉnh thoảng ném một lần thì vài micro giây không đáng lo.

(Các con số trên máy bạn sẽ khác, nhưng tỉ lệ thì tương tự.)

6 · Khi stack trace biến mất trên production

Đây là tình huống debug thật: log production đầy dòng java.lang.NullPointerException, không có message, không có stack trace. Lý do là một tối ưu của JIT. MatStack.java cố tình gây NullPointerException một triệu lần, và dừng lại ngay khi stack trace trống:

static int doDai(String s) { return s.length(); }       // s = null → NullPointerException

for (int i = 1; i <= 1_000_000; i++) {
    try { doDai(null); }
    catch (NullPointerException e) {
        if (i == 1 || e.getStackTrace().length == 0) { /* in message và độ dài stack trace */ }
    }
}

Lần 1: message = Cannot invoke "String.length()" because "<parameter1>" is null
    stack trace dài 2 dòng
Chạy hết 1 000 000 lần, stack trace vẫn đầy đủ
  1. Những lần đầu, NPE có đủ message và stack trace. (Message chi tiết "because ... is null" có từ Java 14.[JEP 358] Nó ghi <parameter1> vì file được biên dịch không có -g; biên dịch với javac -g thì sẽ hiện tên biến s.)
  2. Sau vài nghìn lần, JIT thấy chỗ này ném NPE liên tục, nên dùng lại một object exception tạo sẵn để khỏi tốn công chụp stack (đúng chi phí ở mục 5). Object dùng lại đó không có message, không có stack trace.
  3. Cờ -XX:-OmitStackTraceInFastThrow tắt tối ưu này: stack trace luôn đầy đủ.
Log production toàn NullPointerException trống trơn → lỗi đã xảy ra rất nhiều lần. Hãy tìm những dòng log đầu tiên của lỗi đó (lúc JIT chưa tối ưu, stack trace còn đầy đủ), hoặc chạy lại với -XX:-OmitStackTraceInFastThrow.

8 · Thử thách: đoán 9 dòng output

Challenge.java. Viết ra giấy toàn bộ output trước khi chạy.

record R(String ten) implements AutoCloseable {
    R { System.out.println("mở " + ten); }
    public void close() { System.out.println("đóng " + ten); }
}

static int dem() {
    int x = 1;
    try {
        return x;
    } finally {
        x = 99;
        System.out.println("finally: x = " + x);
    }
}

static void doiLoi() {
    try {
        throw new RuntimeException("A");
    } catch (RuntimeException e) {
        throw new IllegalStateException("B");
    } finally {
        System.out.println("finally của doiLoi");
    }
}

public static void main(String[] args) {
    System.out.println("dem() = " + dem());
    try { doiLoi(); } catch (Exception e) { System.out.println("bắt: " + e.getMessage()); }
    try (R a = new R("1"); R b = new R("2")) {
        System.out.println("thân try");
    }
}

Câu khó nhất: dem() trả về 1 hay 99?

  • dem() = 1: lúc chạy return x, giá trị 1 đã được chép ra để trả về (pass-by-value, bài 2), rồi mới chạy finally. Gán x = 99 trong finally không đổi được giá trị đã chép. Dòng "finally" in trước dòng "dem() =", vì finally chạy xong method mới thật sự trả về.
  • bắt: B: exception mới ném trong catch thay thế A. finally vẫn chạy trước khi B bay ra ngoài. (Muốn giữ A, viết new IllegalStateException("B", e) để A thành cause.)
  • Mở 1, 2 nhưng đóng 2, 1: try-with-resources đóng theo thứ tự ngược.
Đào sâu: bọc exception sao cho không mất dấu (cause)

Khi bắt một exception cấp thấp (ví dụ SQLException) rồi ném exception cấp cao hơn (ví dụ OrderException), luôn truyền exception gốc làm cause: throw new OrderException("Không lưu được đơn", e);. Khi in stack trace, Java in thêm phần Caused by: java.sql.SQLException: ... ngay bên dưới, và đó thường là dòng quan trọng nhất khi debug.

Đọc stack trace Spring trên production: cuộn xuống dòng Caused by: cuối cùng. Đó là lỗi gốc. Các tầng phía trên chỉ là những lớp bọc. Đây cũng là cách Spring làm: nó bọc SQLException (checked) thành DataAccessException (unchecked), để code của bạn không phải viết throws khắp nơi, và để transaction rollback đúng.
