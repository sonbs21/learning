Học xong bài này, bạn sẽ:

  • Biết vì sao tạo thread mới cho mỗi việc là cách làm tệ, và dùng được thread pool thay thế.
  • Giao việc cho pool và lấy kết quả về bằng Future.
  • Tránh được bẫy "quên shutdown()", và hiểu thread pool của Tomcat/Spring Boot hoạt động thế nào.

1 · Ôn bài 13 (trả lời trong đầu trước)

Trong thread dump, trạng thái WAITING nghĩa là gì? Nó khác BLOCKED ở đâu?
Kiểm traWAITING: thread đang chờ có chủ đích và không giới hạn thời gian, cho tới khi có thread khác báo (ví dụ join(), hoặc chờ việc mới). BLOCKED: thread đang chờ lấy khoá để vào khối synchronized. Hôm nay bạn sẽ gặp lại WAITING trong một tình huống rất hay gặp.

2 · Câu chuyện: nhà hàng và đầu bếp

Cách 1, thuê đầu bếp mới cho mỗi món: mỗi khi có khách gọi món, nhà hàng đăng tuyển, ký hợp đồng, phát đồng phục cho một đầu bếp mới. Nấu xong món đó thì cho nghỉ việc. Thủ tục thuê và cho nghỉ mất thời gian hơn cả việc nấu. Hôm nào có 10 000 khách thì nhà hàng chật kín đầu bếp.

Cách 2, giữ một đội đầu bếp cố định: nhà hàng có sẵn 8 đầu bếp. Khách gọi món thì phiếu order được treo lên dây. Đầu bếp nào rảnh thì lấy phiếu kế tiếp ra nấu, xong lại lấy phiếu tiếp theo. Không ai phải thuê mới hay cho nghỉ.

Trong câu chuyệnTrong Java
Đội 8 đầu bếp cố địnhThread pool: một nhóm thread được tạo sẵn và dùng đi dùng lại
Phiếu orderMột việc (task): Runnable hoặc Callable
Dây treo phiếuHàng đợi (queue) bên trong pool
Quản lý nhà hàngExecutorService: nơi bạn giao việc bằng submit(...)

3 · Đo thật: 10 000 việc nhỏ

NewThreadEachTask.java tạo một thread mới cho mỗi việc (cách 1). Pool.java dùng 8 thread cho cả 10 000 việc (cách 2). Mỗi việc chỉ là tăng một biến đếm.

ExecutorService pool = Executors.newFixedThreadPool(8);   // 8 thread dùng đi dùng lại
for (int i = 0; i < 10_000; i++) {
    pool.submit(done::incrementAndGet);                    // giao việc cho pool
}
pool.shutdown();                                           // không nhận việc mới nữa
pool.awaitTermination(10, TimeUnit.SECONDS);               // chờ làm xong việc đã giao

Đoán trước: cách nào nhanh hơn, và nhanh hơn khoảng bao nhiêu lần?

cd lab/l0015
javac *.java
java NewThreadEachTask
java Pool
Thread mới cho mỗi việc: 10000 việc, 347 ms
Thread pool 8 thread:   10000 việc, 17 ms

Thread pool nhanh hơn khoảng 17–20 lần. Tạo một thread rất tốn kém: JVM phải xin hệ điều hành một thread thật, cấp cho nó một stack riêng (bài 2), rồi dọn dẹp khi thread kết thúc. Với việc nhỏ, chi phí "thuê và cho nghỉ" lớn hơn cả chi phí làm việc.

Ai làm việc nào?

WhoDoesIt.java: pool 3 thread, giao 6 việc, mỗi việc in ra tên thread đang làm nó:

Việc 1 do pool-1-thread-1 làm
Việc 3 do pool-1-thread-3 làm
Việc 4 do pool-1-thread-1 làm
Việc 5 do pool-1-thread-2 làm
Việc 6 do pool-1-thread-3 làm

(Thứ tự trên máy bạn có thể khác.)

Chỉ có 3 thread (pool-1-thread-1/2/3), mỗi thread làm 2 việc. Đây chính là "đầu bếp nấu xong lại lấy phiếu tiếp". Tên pool-1-thread-N cũng là cái tên bạn sẽ thấy rất nhiều trong thread dump ở production.

4 · Lấy kết quả về: Future

Nếu việc có kết quả trả về, submit sẽ trả cho bạn một Future, giống như một tờ phiếu hẹn: "kết quả chưa có ngay, khi nào cần thì cầm phiếu này đến lấy".

ExecutorService pool = Executors.newFixedThreadPool(2);
Future<Long> f1 = pool.submit(() -> tinhTong(1_000_000));   // giao việc, nhận phiếu hẹn
Future<Long> f2 = pool.submit(() -> tinhTong(2_000_000));
System.out.println("main: đã giao 2 việc, làm việc khác trong lúc chờ...");
System.out.println("Kết quả 1 = " + f1.get());   // get(): chờ tới khi có kết quả
System.out.println("Kết quả 2 = " + f2.get());
pool.shutdown();
java FutureDemo
main: đã giao 2 việc, làm việc khác trong lúc chờ...
Kết quả 1 = 500000500000
Kết quả 2 = 2000001000000

Hai việc chạy song song trên hai thread của pool. main vẫn tiếp tục làm việc khác, và chỉ dừng lại chờ khi gọi get().[Future Javadoc]

ExecutorService pool = Executors.newFixedThreadPool(n); → pool.submit(việc) → (nếu cần kết quả) future.get() → luôn luôn pool.shutdown() khi dùng xong.

5 · Bẫy: quên shutdown()

Mở ForgotShutdown.java:

ExecutorService pool = Executors.newFixedThreadPool(2);
pool.submit(() -> System.out.println("việc đã làm xong"));
System.out.println("main: hết hàm main rồi!");
// QUÊN pool.shutdown()

Đoán trước: hàm main chạy hết rồi, việc cũng đã làm xong. Chương trình có tự thoát không?

timeout 5 java ForgotShutdown; echo "exit=$?"
main: hết hàm main rồi!
việc đã làm xong
exit=124

Không thoát, và bị timeout giết sau 5 giây. Chụp thread dump lúc đó (bài 13: jps, rồi jcmd <PID> Thread.print):

"pool-1-thread-1" ...
   java.lang.Thread.State: WAITING (parking)
	...
	at java.util.concurrent.LinkedBlockingQueue.take(LinkedBlockingQueue.java:435)
	at java.util.concurrent.ThreadPoolExecutor.getTask(ThreadPoolExecutor.java:1070)
	at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1130)
  • Thread main không còn trong dump, vì nó đã chạy xong.
  • Nhưng pool-1-thread-1 vẫn sống, ở trạng thái WAITING, đứng ở LinkedBlockingQueue.take / getTask, tức là đang chờ phiếu order mới trên dây.
  • JVM chỉ tự thoát khi mọi thread "thường" (non-daemon) đều đã kết thúc. Thread của pool là thread thường, và chúng sẽ chờ việc mới mãi mãi.
Nhà hàng hết khách, quản lý ra về, nhưng quên báo "hết giờ làm". Các đầu bếp cứ đứng cạnh dây treo phiếu chờ order mới, và nhà hàng không thể khoá cửa.

Javadoc viết rõ: "An unused ExecutorService should be shut down to allow reclamation of its resources."[ExecutorService Javadoc] Từ Java 19, ExecutorService dùng được với try (...) { }: hết khối try thì pool tự đóng và chờ mọi việc làm xong.

6 · Khi đi làm thì sao?

  • Tomcat chính là một thread pool. Spring Boot mặc định cho Tomcat tối đa 200 worker thread (server.tomcat.threads.max).[Spring Boot: application properties] Mỗi request được một thread trong pool phục vụ. Nếu cả 200 thread đều đang bận chờ một API chậm hay một database chậm, request thứ 201 phải xếp hàng, và người dùng thấy hệ thống "treo". Thread dump lúc đó sẽ toàn là các thread tên http-nio-8080-exec-N đứng chờ ở cùng một chỗ.
  • Hàng đợi không giới hạn: Executors.newFixedThreadPool dùng một hàng đợi không giới hạn (Javadoc: "operating off a shared unbounded queue").[Executors Javadoc] Nếu việc được giao vào nhanh hơn tốc độ làm, hàng đợi cứ phình ra mãi, cho tới khi gặp OutOfMemoryError (bài 9). Ở production, người ta thường tự tạo ThreadPoolExecutor với hàng đợi có giới hạn.
Câu phỏng vấn: "Vì sao nên dùng thread pool thay vì new Thread?"

"Tạo thread tốn kém, vì phải xin thread từ hệ điều hành và cấp stack riêng. Thread pool tạo sẵn một số thread cố định rồi dùng lại cho nhiều việc. Việc mới được đặt vào hàng đợi, thread nào rảnh thì lấy ra làm. Như vậy vừa nhanh hơn, vừa giới hạn được số thread để không làm sập máy. Dùng qua ExecutorService: submit trả về Future để lấy kết quả, và phải shutdown() khi dùng xong, nếu không các thread của pool giữ JVM sống mãi. Cần chú ý newFixedThreadPool dùng hàng đợi không giới hạn, nên có thể gây hết bộ nhớ nếu việc dồn quá nhiều."

8 · Thử thách: sửa ForgotShutdown.java bằng hai cách

Nhiệm vụ: sửa ForgotShutdown.java sao cho timeout 5 java ForgotShutdown; echo "exit=$?" in ra exit=0. Hãy làm bằng hai cách:

  1. Thêm một dòng gọi shutdown().
  2. Không gọi shutdown(), mà dùng try (ExecutorService pool = ...) { ... } (Java 19+).
Xem lời giải

Cách 1:

ExecutorService pool = Executors.newFixedThreadPool(2);
pool.submit(() -> System.out.println("việc đã làm xong"));
System.out.println("main: hết hàm main rồi!");
pool.shutdown();       // không nhận việc mới; thread của pool kết thúc sau khi làm xong việc cũ

Cách 2:

try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
    pool.submit(() -> System.out.println("việc đã làm xong"));
    System.out.println("main: hết khối try rồi!");
}   // tự gọi close(): shutdown + chờ mọi việc xong

Cả hai cách đều cho exit=0. Cách 2 an toàn hơn, vì nếu code trong khối try ném exception thì pool vẫn được đóng.

Đào sâu: virtual thread (Java 21), khi việc chủ yếu là chờ

Phần lớn thời gian của một request backend là chờ: chờ database, chờ API khác. Với pool 200 thread, 200 việc đang chờ là pool đầy. Java 21 có virtual thread: những "thread nhẹ" do JVM quản lý, rất rẻ, tạo hàng triệu cái cũng được. Khi một virtual thread đứng chờ, nó nhường thread thật cho việc khác.[JEP 444: Virtual Threads]

Thử 10 000 việc, mỗi việc "chờ" 100 ms (Thread.sleep giả lập chờ database):

java SleepPool    # pool cố định 200 thread
java Virtual      # Executors.newVirtualThreadPerTaskExecutor()
Pool 200 thread: 10000 việc (mỗi việc chờ 100 ms), 5021 ms
Virtual threads: 10000 việc (mỗi việc chờ 100 ms), 211 ms

Pool 200 thread chỉ chạy được 200 việc một lúc: 10 000 / 200 = 50 lượt × 100 ms ≈ 5 giây. Virtual thread cho cả 10 000 việc cùng chờ một lúc, nên chỉ mất khoảng 0,2 giây. Lưu ý: virtual thread chỉ giúp với việc chờ (I/O). Với việc tính toán nặng thì số lõi CPU vẫn là giới hạn. Spring Boot 3.2+ có thể bật virtual thread cho Tomcat. Bạn sẽ gặp lại chủ đề này ở khoá Spring.
