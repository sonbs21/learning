Overloading và Overriding: ai chọn method, và chọn lúc nào?

Bài 7 · Hai chữ nghe giống nhau, nhưng một bên do compiler quyết định lúc biên dịch, bên kia do JVM quyết định lúc chạy

Học xong bài này, bạn sẽ:

  • Phân biệt overloading và overriding bằng một câu: ai chọn method, và chọn dựa vào cái gì.
  • Đoán đúng output của câu hỏi phỏng vấn kinh điển "biến kiểu cha, object kiểu con".
  • Hiểu vì sao equals(Diem o) làm HashSet "mất trí nhớ", và vì sao luôn phải gắn @Override.
  • Biết vì sao Spring không chặn được method final, private, static.

2 · Hai câu chuyện để nhớ

Overloading giống một từ có nhiều nghĩa. Chữ "mở" trong "mở cửa", "mở máy", "mở nhạc" là ba hành động khác nhau. Người nghe biết là hành động nào ngay khi nghe câu, chỉ bằng cách nhìn chữ đi kèm. Không cần chờ xem cánh cửa trông thế nào.

Overriding giống một quy định chung mà mỗi người làm theo cách riêng. Quản lý nói "nhân viên đứng quầy hãy chào khách". Câu nói chỉ có một, nhưng người thật sự đang đứng quầy là ai thì chào theo kiểu người đó: người cúi đầu, người bắt tay. Phải tới lúc khách bước vào mới biết là kiểu chào nào.

Đổi sang ngôn ngữ Java:

Overloading (nạp chồng)Overriding (ghi đè)
Là gìNhiều method cùng tên, khác tham sốClass con viết lại method của cha, giữ nguyên tên và tham số
Ai chọn bản nàoCompiler (javac)JVM
Chọn lúc nàoLúc biên dịchLúc chạy
Dựa vàoKiểu khai báo của đối số (chữ viết trong code)Kiểu thật của object (object nằm trên heap)

Cả bài này chỉ để làm rõ bảng trên. Ta đi từng cột.

3 · Overloading: cùng tên, khác tham số

Mở Overload.java. Có ba method cùng tên tong:

static int tong(int a, int b)           { return a + b; }
static double tong(double a, double b)  { return a + b; }
static int tong(int a, int b, int c)    { return a + b + c; }

System.out.println(tong(1, 2));        // (int, int)
System.out.println(tong(1.5, 2.5));    // (double, double)
System.out.println(tong(1, 2, 3));     // (int, int, int)
cd lab/l0007
javac Overload.java
java Overload
3
4.0
6

Compiler nhìn vào các đối số (1, 2 là hai int; 1.5, 2.5 là hai double) rồi chọn bản khớp. Việc này xong trước khi chương trình chạy.

Thứ để phân biệt các bản overload gọi là chữ ký method (signature). Chữ ký là tên method + danh sách kiểu tham số. Kiểu trả về không nằm trong chữ ký.[JLS §8.4.2] Vì vậy hai method chỉ khác kiểu trả về sẽ bị báo lỗi. File loi/ReturnOnly.java:

int tinh(int a)    { return a; }
double tinh(int a) { return a; }   // chỉ khác kiểu trả về
javac loi/ReturnOnly.java
loi/ReturnOnly.java:3: error: method tinh(int) is already defined in class ReturnOnly

Nghĩ theo cách của compiler sẽ thấy hợp lý: gặp dòng tinh(5); (không dùng kết quả), nó không có cách nào biết bạn muốn bản nào.

Overload = cùng tên, khác danh sách tham số (số lượng, kiểu, hoặc thứ tự). Compiler chọn bản nào ngay lúc biên dịch. Khác mỗi kiểu trả về thì không tính.[JLS §8.4.9]

4 · Overriding: con viết lại method của cha

Mở DaHinh.java ("đa hình", tiếng Anh là polymorphism):

static class DongVat { String keu() { return "..."; } }
static class Cho extends DongVat { @Override String keu() { return "Gâu gâu"; } }
static class Meo extends DongVat { @Override String keu() { return "Meo meo"; } }

DongVat[] chuong = { new DongVat(), new Cho(), new Meo() };
for (DongVat d : chuong) {
    System.out.println(d.getClass().getSimpleName() + ": " + d.keu());
}
javac DaHinh.java
java DaHinh
DongVat: ...
Cho: Gâu gâu
Meo: Meo meo

Biến d luôn được khai báo là DongVat, và dòng d.keu() chỉ được viết một lần. Vậy mà mỗi vòng lặp lại chạy một bản khác nhau. Lý do: JVM nhìn vào object thật mà d đang trỏ tới, rồi chạy bản keu() của class đó. Cơ chế này gọi là dynamic dispatch ("chọn động", tức chọn lúc chạy).

@Override là một annotation, kiểu như ghi chú gửi compiler: "tôi định override method của cha, kiểm tra giúp tôi". Không bắt buộc, nhưng bạn sẽ thấy ở mục 6 nó cứu bạn thế nào.

Override phải theo vài luật. Bạn không cần thuộc lòng, chỉ cần nhớ ý chính là "bản của con phải dùng thay được bản của cha":[JLS §8.4.8.3]

  • Cùng chữ ký (tên + kiểu tham số). Khác tham số thì thành overload, không phải override.
  • Kiểu trả về giống của cha, hoặc là class con của kiểu đó (gọi là covariant return).
  • Quyền truy cập không được hẹp hơn. Cha là public mà con là protected thì code đang gọi qua cha sẽ không gọi được nữa.
  • Không được ném thêm checked exception mới hoặc rộng hơn bản của cha.

Thử luật thứ ba. loi/WeakerAccess.java override toString() (vốn là public trong Object) thành protected:

javac loi/WeakerAccess.java
loi/WeakerAccess.java:3: error: toString() in WeakerAccess cannot override toString() in Object
  attempting to assign weaker access privileges; was public
Override = class con viết lại method của cha, cùng chữ ký. Lúc chạy, JVM chọn bản của object thật, không quan tâm biến được khai báo kiểu gì.

5 · Cái bẫy: đặt hai thứ cạnh nhau

Đây là câu hỏi phỏng vấn kinh điển. Trap.java có cả override lẫn overload:

static class DongVat { String keu() { return "..."; } }
static class Cho extends DongVat { @Override String keu() { return "Gâu gâu"; } }

static String loai(DongVat d) { return "loai(DongVat)"; }   // overload 1
static String loai(Cho c)     { return "loai(Cho)"; }       // overload 2

DongVat a = new Cho();        // khai báo DongVat, object thật là Cho
System.out.println(a.keu());
System.out.println(loai(a));

Dừng lại và đoán hai dòng output trước khi chạy. Hầu hết mọi người đoán "Gâu gâu" và "loai(Cho)".

javac Trap.java
java Trap
Gâu gâu
loai(DongVat)

Cùng một biến a, nhưng hai dòng theo hai luật khác nhau:

  1. a.keu() là override. JVM quyết định lúc chạy, nhìn vào object thật là Cho, nên ra "Gâu gâu".
  2. loai(a) là overload. Compiler quyết định lúc biên dịch. Compiler không chạy code nên không biết a sẽ trỏ tới Cho. Nó chỉ thấy chữ viết trong code: DongVat a. Nên nó chọn loai(DongVat).

Bằng chứng nằm trong bytecode. Lệnh javap -c (bài 1) cho thấy compiler đã ghi gì vào file .class:

javap -c Trap | grep invoke
12: invokevirtual #20   // Method Trap$DongVat.keu:()Ljava/lang/String;
22: invokestatic  #32   // Method loai:(LTrap$DongVat;)Ljava/lang/String;
  • Dòng 12: compiler ghi DongVat.keu, nhưng dùng lệnh invokevirtual. Lệnh này bảo JVM: "lúc chạy, nhìn object thật rồi tìm bản keu() phù hợp nhất". JVM tìm bắt đầu từ class Cho, thấy bản override, chạy nó.[JVMS §6.5 invokevirtual]
  • Dòng 22: phần trong ngoặc (LTrap$DongVat;) là kiểu tham số. Nghĩa là compiler đã đóng đinh bản loai(DongVat) vào bytecode. Lúc chạy, JVM chỉ việc gọi đúng bản đó, không chọn lại.
Overload chọn theo chữ viết, override chọn theo object thật.
Overload: compiler nhìn kiểu khai báo của đối số, quyết định một lần, ghi cứng vào bytecode.
Override: JVM nhìn kiểu thật của object mà ta gọi method trên đó, quyết định mỗi lần gọi.

6 · Bẫy ngoài đời: equals(Diem o)

Đây là lỗi có thật trong code production, và nó dùng đúng cái bẫy ở mục 5. Ở bài 3 bạn đã học: muốn hai object "bằng nhau theo nội dung" thì phải override equals(Object o). EqualsTrap.java viết nhầm tham số thành Diem:

static class Diem {
    final int x, y;
    // Nhầm: tham số là Diem chứ không phải Object
    public boolean equals(Diem o) { return x == o.x && y == o.y; }
    @Override public int hashCode() { return 31 * x + y; }
}

Diem a = new Diem(1, 2), b = new Diem(1, 2);
Object bAnDi = b;
a.equals(b)            // ?
a.equals(bAnDi)        // ?
set.add(a); set.contains(b)   // ?
javac EqualsTrap.java
java EqualsTrap
a.equals(b)     = true
a.equals(bAnDi) = false
set.contains(b) = false

Cùng một object b, mà kết quả lúc true lúc false. Từng bước:

  1. equals(Diem o) có tham số khác equals(Object o) của class Object. Khác tham số thì đó là overload, không phải override. Bây giờ class Diem có hai method equals: bản tự viết, và bản thừa hưởng từ Object (so sánh bằng ==, bài 3).
  2. a.equals(b): b khai báo là Diem, nên compiler chọn bản equals(Diem) → true.
  3. a.equals(bAnDi): bAnDi khai báo là Object, nên compiler chọn bản equals(Object). Diem không override bản này, nên chạy bản của Object: so sánh địa chỉ → false.
  4. HashSet được viết từ trước, cho mọi loại object, nên bên trong nó luôn gọi equals(Object). Nó không hề biết có equals(Diem) → false. Bạn thêm điểm (1,2) vào set rồi hỏi lại thì set bảo "không có".

Chữ @Override bắt lỗi này ngay lúc biên dịch. loi/EqualsOverride.java viết y như trên nhưng có gắn @Override:

javac loi/EqualsOverride.java
loi/EqualsOverride.java:3: error: method does not override or implement a method from a supertype
Luôn gắn @Override khi định override. Gõ sai tham số, sai tên (hashcode thay vì hashCode), hoặc cha đổi tên method: compiler báo ngay, thay vì để bug lặng lẽ chạy trên production. Bản equals đúng luôn nhận Object.

7 · Những method không override được, và chuyện của Spring

Override chỉ áp dụng cho method thường (method của object). Các loại sau thì không:

  • final: bị cấm override (học kỹ ở bài 16).
  • private: class con không nhìn thấy, nên viết method trùng tên ở con chỉ là một method mới hoàn toàn.
  • Constructor: không được kế thừa, nên cũng không override được.
  • static: con viết method static trùng chữ ký thì gọi là che (hiding), không phải override.[JLS §8.4.8.2]

Xem trường hợp static trong StaticHide.java:

static class Cha { static String ten() { return "Cha"; }  String chao() { return "Cha"; } }
static class Con extends Cha { static String ten() { return "Con"; }  @Override String chao() { return "Con"; } }

Cha x = new Con();
x.chao()   // method thường
x.ten()    // method static
javac StaticHide.java
java StaticHide
x.chao() = Con
x.ten()  = Cha

Method static không gắn với object nào (bài 6: không có this), nên chẳng có "object thật" để JVM nhìn vào. Compiler chọn theo kiểu khai báo Cha, giống như overload. (Đó cũng là lý do nên gọi static bằng tên class, Cha.ten(), chứ đừng gọi qua biến.)

Liên hệ Spring (xem trước, học kỹ ở bài 17). Khi bean không có interface, Spring dùng CGLIB tạo một class con của class bạn. Class con đó override từng method để chèn thêm việc mở/đóng transaction. Vậy method nào không override được thì proxy không chặn được: @Transactional trên method final, private hay static sẽ lặng lẽ không có tác dụng, không báo lỗi. Tài liệu Spring ghi: "With CGLIB, final methods cannot be advised, as they cannot be overridden in runtime-generated subclasses."[Spring: Proxying Mechanisms]

9 · Thử thách: đoán compiler chọn bản nào

Challenge.java có ba bản overload. Viết ra giấy 5 dòng output trước khi chạy.

static String in(Object o)  { return "Object"; }
static String in(String s)  { return "String"; }
static String in(long n)    { return "long"; }

Object chu = "xin chào";
System.out.println("1: " + in(5));
System.out.println("2: " + in(null));
System.out.println("3: " + in(chu));
System.out.println("4: " + in('a'));
System.out.println("5: " + in(Integer.valueOf(5)));

Gợi ý: compiler chọn theo 3 vòng, dừng ở vòng đầu tiên tìm được bản khớp:[JLS §15.12.2]

  1. Vòng 1: khớp không cần boxing/unboxing (đổi qua lại giữa int và Integer). Được phép nới rộng số (int → long) và đi từ class con lên class cha (String → Object).
  2. Vòng 2: cho phép boxing/unboxing.
  3. Vòng 3: cho phép varargs (...).

Nếu một vòng có nhiều bản khớp, compiler chọn bản cụ thể nhất (bản có tham số "hẹp" hơn, ví dụ String hẹp hơn Object).

Xem đáp án 
javac Challenge.java
java Challenge
1: long
2: String
3: Object
4: long
5: Object
  1. in(5): 5 là int, không có in(int). Vòng 1 cho nới int → long → long.
  2. in(null): null khớp cả String lẫn Object. String cụ thể hơn → String.
  3. in(chu): chu khai báo là Object, dù bên trong là chuỗi. Chính là cái bẫy ở mục 5 → Object.
  4. in('a'): char nới rộng được thành long ở vòng 1 → long. (Không ra String, vì char không phải chuỗi.)
  5. in(Integer.valueOf(5)): muốn vào in(long) phải unbox, tức là vòng 2. Nhưng vòng 1 đã khớp Integer → Object rồi → Object.

Thêm một bước: nếu có cả in(String) và in(Integer) thì in(null) ra sao? Hai kiểu này không kiểu nào "hẹp" hơn kiểu nào. Thử javac loi/Ambiguous.java:

loi/Ambiguous.java:4: error: reference to in is ambiguous
  both method in(String) in Ambiguous and method in(Integer) in Ambiguous match

Sửa bằng cách ép kiểu cho rõ: in((String) null).

Đào sâu: JVM tìm bản override nhanh thế nào? (HotSpot)

Spec chỉ nói invokevirtual phải tìm bản phù hợp, bắt đầu từ class của object rồi đi lên các class cha.[JVMS §5.4.6] Spec không nói làm cách nào. HotSpot (JVM bạn đang dùng) làm thế này:

  • vtable: mỗi class có một bảng các method có thể override, lưu trong Metaspace (bài 2). Mỗi method có vị trí cố định trong bảng, và class con ghi bản override của mình vào đúng vị trí đó. Gọi method chỉ tốn một lần tra bảng, không phải lần lượt dò từng class cha.
  • JIT khử ảo (devirtualization, sẽ gặp JIT ở bài 8): nếu JIT thấy lúc đó chỉ có một class cài đặt method (dựa vào phân tích cây kế thừa, gọi là CHA), hoặc chỗ gọi luôn gặp cùng một class, nó sẽ inline thẳng bản đó và bỏ luôn bước tra bảng. Nếu sau đó có class mới được nạp làm sai giả định này, JIT bỏ code đã biên dịch (deoptimize) rồi biên dịch lại.

Hệ quả thực tế: thêm final chỉ để "chạy nhanh hơn" gần như không có tác dụng, vì JIT đã tự làm việc đó. Dùng final khi bạn muốn cấm override, vì lý do thiết kế (xem bài 16).
