Inner class vs static nested class: sợi dây vô hình

Bài 22 · Một chữ static quyết định class con bên trong có ngầm giữ object bên ngoài hay không, và vì sao điều đó gây rò rỉ bộ nhớ

~35 phútCần biết: Bài 6 (this ẩn), Bài 9 (GC, rò rỉ), Bài 21 (lambda)Thư mục thực hành: lab/l0022

Học xong bài này, bạn sẽ:

  • Phân biệt static nested class và inner class bằng một câu, và chứng minh bằng javap.
  • Thấy tận mắt inner class gây rò rỉ bộ nhớ thế nào, và sửa nó.
  • Biết mặc định nên chọn loại nào, và khi nào inner class thật sự cần.

1 · Ôn bài 6 và bài 9 (trả lời trong đầu trước)

(a) Method thường khai báo 1 tham số, nhưng javap báo args_size=2. Tham số ẩn đó là gì?

(b) Một object còn được một field static trỏ tới (trực tiếp hoặc qua nhiều bước) thì GC có dọn nó không?

Kiểm tra(a) this, được JVM truyền ngầm vào slot 0. (b) Không. Field static là một GC root, và mọi thứ "với tới được" từ root đều được giữ lại. Hôm nay bạn gặp một tham chiếu ẩn khác, tên là this$0, và nó kéo theo đúng hậu quả ở câu (b).

2 · Hai loại class nằm bên trong class

Static nested class giống một cửa hàng thuê mặt bằng trong trung tâm thương mại. Nó nằm trong toà nhà (để dễ tìm, cùng một địa chỉ), nhưng là một doanh nghiệp độc lập, không phụ thuộc vào một gian hàng cụ thể nào.

Inner class giống một nhân viên của một quán cụ thể. Mỗi nhân viên luôn thuộc về một quán, và đeo một sợi dây (thẻ nhân viên) nối về quán đó. Nhờ sợi dây, nhân viên biết quán mình tên gì, menu ra sao. Nhưng còn nhân viên thì quán đó cũng còn "tồn tại trên giấy tờ".

HaiLoai.java có cả hai loại:

public class HaiLoai {
    String tenQuan = "Cà phê Sáng";

    static class Nested {                       // static nested: không gắn với object HaiLoai nào
        String chao() { return "Nested: xin chào"; }
    }

    class Inner {                               // inner: luôn gắn với MỘT object HaiLoai
        String chao() { return "Inner: chào từ " + tenQuan; }   // đọc field của object ngoài
    }
}

HaiLoai.Nested n = new HaiLoai.Nested();        // tạo thẳng, không cần object ngoài
HaiLoai quan = new HaiLoai();
HaiLoai.Inner i = quan.new Inner();              // phải có object ngoài mới tạo được
quan.tenQuan = "Cà phê Tối";                     // đổi tên quán sau khi đã tạo i
cd lab/l0022
javac HaiLoai.java
java HaiLoai
Nested: xin chào
Inner: chào từ Cà phê Sáng
Inner: chào từ Cà phê Tối
Constructor của Inner:  [HaiLoai$Inner(HaiLoai)]
Constructor của Nested: [HaiLoai$Nested()]
  • Cú pháp lạ quan.new Inner() nói rõ: "tạo một Inner thuộc về quan".
  • i thấy tên quán đổi thành "Cà phê Tối", nghĩa là nó không chép tên lúc tạo, mà giữ tham chiếu tới chính object quan.
  • Constructor của Inner nhận một tham số HaiLoai mà bạn không hề viết. Giống this ở bài 6: compiler tự thêm vào.

3 · Sợi dây tên là this$0

Xem compiler đã thêm gì vào hai class:

javap -p 'HaiLoai$Inner'
javap -p 'HaiLoai$Nested'
class HaiLoai$Inner {
  final HaiLoai this$0;
  HaiLoai$Inner(HaiLoai);
  java.lang.String chao();
}
class HaiLoai$Nested {
  HaiLoai$Nested();
  java.lang.String chao();
}

Inner class có thêm một field ẩn this$0 trỏ tới object bên ngoài. Đó là "sợi dây". Khi bạn viết tenQuan trong Inner, compiler hiểu là this$0.tenQuan.[JLS §8.1.3] Static nested class thì không có sợi dây nào.

Hệ quả: hai lỗi biên dịch đối xứng nhau.

javac loi/NestedDocField.java      # static nested đọc field của object ngoài
javac loi/NewInnerTuStatic.java    # new Inner() bên trong main (static)
loi/NestedDocField.java:4: error: non-static variable tenQuan cannot be referenced from a static context
loi/NewInnerTuStatic.java:4: error: non-static variable this cannot be referenced from a static context
  • Static nested không có sợi dây, nên không biết đọc tenQuan của quán nào.
  • new Inner() trong main nghĩa là this.new Inner(), mà main là static, không có this (bài 6), nên không có quán nào để gắn vào.
Static nested class = class bình thường, chỉ "ở nhờ" trong class khác. Inner class (không có static) = mỗi object luôn gắn với một object bên ngoài, qua field ẩn this$0.

4 · Sợi dây giữ chặt cả object bên ngoài: rò rỉ bộ nhớ

Đây là lý do bài này quan trọng khi đi làm. Leak.java mô phỏng một hệ thống: mỗi đơn hàng nặng 1 MB (có ảnh chụp hoá đơn), xử lý xong thì chỉ cần giữ lại một biên lai nhỏ chứa mã đơn. Hai cách viết biên lai:

static class DonHang {
    byte[] anhChupHoaDon = new byte[1_000_000];       // mỗi đơn hàng nặng 1 MB
    int ma;

    class BienLaiInner { int ma() { return ma; } }    // inner: ngầm giữ cả DonHang
    static class BienLaiNested {                      // static nested: chỉ giữ cái nó cần
        final int ma;
        BienLaiNested(int ma) { this.ma = ma; }
    }
}

for (int i = 1; i <= 1000; i++) {
    DonHang d = new DonHang(i);
    lichSu.add(dungInner ? d.new BienLaiInner() : new DonHang.BienLaiNested(d.ma));
    // d ra khỏi scope ở đây: chỉ còn biên lai được giữ lại
}

Chạy với heap 64 MB (cờ -Xmx, bài 9). Đoán trước: giữ 1000 biên lai thì có hết bộ nhớ không?

javac Leak.java
java -Xmx64m Leak inner
java -Xmx64m Leak nested
inner: hết bộ nhớ sau 61 biên lai: Java heap space
nested: giữ 1000 biên lai, không sao

Vẽ ra đường đi của tham chiếu (bài 9):

inner:   lichSu (static, GC root) → BienLaiInner → this$0 → DonHang → byte[1 MB]   ✘ GC không dọn được
nested:  lichSu (static, GC root) → BienLaiNested (chỉ có int ma)               ✔ DonHang thành rác, GC dọn

Code trông không có chỗ nào giữ DonHang: biến d đã ra khỏi scope. Nhưng mỗi BienLaiInner đeo sợi dây this$0 về đơn hàng của nó, nên 1 MB ảnh chụp bị giữ lại theo. Trong heap dump, bạn sẽ thấy hàng nghìn DonHang "không ai dùng" mà không xoá được. Đó chính là dấu hiệu của loại rò rỉ này.

Mặc định hãy viết static cho class lồng bên trong. Chỉ bỏ static khi class đó thật sự cần đọc field của object bên ngoài. (Effective Java, Item 24: "If you declare a member class that does not require access to an enclosing instance, always put the static modifier in its declaration".)

5 · Thư viện chuẩn dùng cả hai, đúng chỗ

javap -p 'java.util.ArrayList$Itr' | grep this
javap -p 'java.util.HashMap$Node' | grep this
  final java.util.ArrayList this$0;
(HashMap$Node: không có dòng nào)
  • ArrayList.Itr (iterator của for (x : list)) là inner class: nó cần đọc mảng elementData và size của chính list đang duyệt (bài 10). Đây là trường hợp sợi dây là cần thiết.
  • HashMap.Node (mỗi ô key–value, bài 11) là static nested: một Node chỉ cần key, value, hash, next. Map có hàng triệu Node; nếu mỗi Node đeo thêm một sợi dây về map thì tốn bộ nhớ vô ích.
  • Mẫu Builder (new Pizza.Builder().size(30).build()) cũng là static nested: builder tồn tại trước khi có object bên ngoài, nên không thể là inner.

Thêm một lý do thực tế: thư viện như Jackson (đọc JSON) hay JPA tạo object bằng reflection, thường qua constructor không tham số. Inner class thì không có constructor đó: như bạn thấy ở mục 2, constructor của nó luôn đòi object bên ngoài (HaiLoai$Inner(HaiLoai)). Vì vậy DTO hay entity khai báo lồng bên trong class khác phải là static.

7 · Thử thách: listener làm rò rỉ bộ nhớ

Challenge.java: mỗi trang sản phẩm nặng 1 MB, đăng ký một listener vào "bus sự kiện" sống mãi (một list static) để in thông báo khi đổi giá:

void dangKy() {
    // TODO: listener này làm rò rỉ bộ nhớ. Sửa CHỈ phần đăng ký này.
    suKien.add(new Runnable() {
        public void run() { System.out.println("Sản phẩm " + maSanPham + " vừa đổi giá"); }
    });
}
javac Challenge.java
java -Xmx64m Challenge
Hết bộ nhớ sau 61 trang

Nhiệm vụ: (1) Giải thích vì sao rò rỉ. Gợi ý: class ẩn danh cũng là một inner class, thử javap -p 'Challenge$TrangSanPham$1'. (2) Sửa để đăng ký được 1000 trang, mà listener vẫn in đúng mã sản phẩm.

Xem lời giải

(1) javap cho thấy class ẩn danh có final Challenge$TrangSanPham this$0;. Nó đọc maSanPham, tức là đọc qua this$0, nên giữ cả trang 1 MB.

(2) Chép giá trị cần dùng ra biến cục bộ, rồi dùng lambda (bài 21). Lambda chỉ bắt đúng biến nó dùng:

int ma = maSanPham;                              // chép ra biến cục bộ
suKien.add(() -> System.out.println("Sản phẩm " + ma + " vừa đổi giá"));
Đăng ký 1000 trang, không sao
Sản phẩm 1000 vừa đổi giá

Cẩn thận: nếu chỉ đổi sang lambda mà vẫn viết maSanPham (field) trong thân, lambda sẽ bắt this và rò rỉ y như cũ. Mình đã chạy thử: vẫn "Hết bộ nhớ sau 61 trang". Cách khác cũng đúng: viết một static class listener nhận int ma qua constructor.

Đào sâu: từ Java 18, this$0 có thể biến mất

Nếu inner class không hề dùng tới object bên ngoài, javac từ JDK 18 trở đi sẽ không tạo field this$0 nữa.[JDK-8271623] ThisZero.java:

class KhongDungNgoai { int x() { return 42; } }       // không đụng tới object ngoài
class CoDungNgoai    { int x() { return ten; } }      // đọc field của object ngoài
javac ThisZero.java
javap -p 'ThisZero$KhongDungNgoai' 'ThisZero$CoDungNgoai'
class ThisZero$KhongDungNgoai {
  ThisZero$KhongDungNgoai(ThisZero);          ← vẫn đòi object ngoài, nhưng không giữ lại
class ThisZero$CoDungNgoai {
  final ThisZero this$0;
  ThisZero$CoDungNgoai(ThisZero);

Đừng dựa vào điều này để "khỏi cần viết static": constructor vẫn đòi object bên ngoài (nên Jackson/JPA vẫn không tạo được), code chạy trên JDK cũ vẫn giữ sợi dây, và chỉ cần sau này ai đó thêm một dòng đọc field ngoài là rò rỉ quay lại. Chữ static nói rõ ý định và được compiler đảm bảo.
