Spring "làm phép" thế nào? Tự viết một @Transactional

Bài 17 · Reflection, annotation, dynamic proxy, và vì sao @Transactional có lúc "không chạy"

Học xong bài này, bạn sẽ:

  • Biết reflection là gì: code đọc thông tin về chính code lúc đang chạy.
  • Tự viết được một dynamic proxy bắt chước @Transactional của Spring trong khoảng 30 dòng.
  • Giải thích được câu phỏng vấn rất hay gặp: "Vì sao gọi this.method() thì @Transactional không chạy?"

1 · Ôn bài 10, 11 (trả lời trong đầu trước)

Ở bài 10 và 11, để "nhìn vào trong" ArrayList và HashMap, ta đã dùng một kỹ thuật kèm cờ --add-opens. Kỹ thuật đó tên là gì?
Kiểm traReflection. Ở các bài đó ta chỉ dùng nó như một công cụ. Hôm nay ta học nó thật sự, vì đây là nền móng của Spring.

2 · Reflection: code tự soi gương

Bình thường bạn viết order.save("sách"): tên method được viết cứng trong code. Reflection cho phép bạn làm điều đó lúc đang chạy, khi chỉ biết tên dưới dạng chuỗi hay dữ liệu:

Method m = OrderServiceImpl.class.getMethod("save", String.class);  // tìm method tên "save"
boolean coTx = m.isAnnotationPresent(Tx.class);                       // method này có gắn @Tx không?
m.invoke(order, "sách");                                              // gọi nó, y như order.save("sách")
Bình thường bạn gọi điện cho một người vì đã thuộc số. Reflection giống như mở danh bạ ra tra lúc cần: tìm theo tên, đọc ghi chú bên cạnh, rồi bấm gọi.

Spring dùng reflection ở khắp nơi: quét các class có @Service, tìm field có @Autowired, đọc @Transactional trên method...[dev.java: Reflection]

Annotation chỉ là "nhãn dán"

File Tx.java định nghĩa một annotation tự viết, bắt chước @Transactional:

@Retention(RetentionPolicy.RUNTIME)   // giữ lại lúc chạy để reflection đọc được
@Target(ElementType.METHOD)            // chỉ được gắn lên method
public @interface Tx { }

Một annotation tự nó không làm gì cả. Nó chỉ là một cái nhãn dán lên method. Phải có một đoạn code khác đi đọc cái nhãn đó (bằng reflection) và quyết định làm gì. Trong Spring, "đoạn code khác" đó chính là proxy.

3 · Proxy: người đứng giữa

Bạn muốn gặp giám đốc. Bạn không vào thẳng phòng giám đốc, mà phải đi qua thư ký. Thư ký nhận yêu cầu, xem lịch, có khi ghi sổ trước khi chuyển vào, rồi ghi chú sau khi giám đốc làm xong. Với bạn, thư ký trông như "cửa vào phòng giám đốc", nhưng thật ra là một người khác đứng giữa.

Một proxy là object như vậy: nó có cùng interface với object thật nên trông y hệt, nhưng mọi lời gọi method đều đi qua nó trước. Proxy làm thêm việc (mở transaction, ghi log, kiểm tra quyền...), rồi mới chuyển lời gọi vào object thật.

Java có sẵn công cụ tạo proxy lúc chạy: java.lang.reflect.Proxy.[Proxy Javadoc] Bạn chỉ cần viết phần "thư ký làm gì", gọi là InvocationHandler. Đây là phần quan trọng nhất trong TxProxy.java:

// Mọi lời gọi method trên proxy đều chạy qua đây
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    Method real = target.getClass().getMethod(method.getName(), method.getParameterTypes());
    boolean hasTx = real.isAnnotationPresent(Tx.class);   // ① đọc nhãn @Tx

    if (hasTx) System.out.println("BEGIN transaction  (" + method.getName() + ")");   // ② việc TRƯỚC
    Object result = method.invoke(target, args);           // ③ gọi object THẬT
    if (hasTx) System.out.println("COMMIT transaction (" + method.getName() + ")");   // ④ việc SAU
    return result;
}

Và tạo proxy bọc quanh object thật:

OrderService real  = new OrderServiceImpl();
OrderService proxy = TxProxy.wrap(real, OrderService.class);   // bên trong gọi Proxy.newProxyInstance(...)

Class thật OrderServiceImpl có hai method. save có gắn @Tx. placeOrder thì không, và bên trong nó tự gọi this.save():

@Tx
public void save(String item) { ... "lưu đơn hàng" ... }

public void placeOrder(String item) {          // KHÔNG có @Tx
    ... "kiểm tra kho" ...
    this.save(item);                            // tự gọi method của chính mình
}

4 · Chạy thử: ba trường hợp

Đoán trước cho từng trường hợp: có dòng BEGIN/COMMIT hay không?

  1. proxy.save("sách")
  2. real.save("bút"), gọi thẳng object thật
  3. proxy.placeOrder("vở"), bên trong gọi this.save(), mà save có @Tx
cd lab/l0017
javac *.java
java Main
real  là class: OrderServiceImpl
proxy là class: jdk.proxy1.$Proxy0

1) proxy.save("sách")
BEGIN transaction  (save)
    [code thật] lưu đơn hàng: sách
COMMIT transaction (save)

2) real.save("bút")   -- gọi thẳng object thật
    [code thật] lưu đơn hàng: bút

3) proxy.placeOrder("vở")   -- bên trong gọi this.save()
    [code thật] kiểm tra kho...
    [code thật] lưu đơn hàng: vở          ← không có BEGIN/COMMIT!

Đọc kết quả:

  • Dòng class: proxy thuộc một class tên jdk.proxy1.$Proxy0. Bạn không hề viết class này. JVM tự sinh ra nó lúc đang chạy, rồi nạp vào giống mọi class khác (nhớ lại bài 1 và bài 5).
  • Trường hợp 1: đi qua proxy, và save có @Tx, nên có BEGIN/COMMIT.
  • Trường hợp 2: gọi thẳng object thật, không qua "thư ký", nên không ai mở transaction.
  • Trường hợp 3: lời gọi placeOrder đi qua proxy, nhưng placeOrder không có @Tx, nên proxy chỉ chuyển thẳng vào. Khi đã ở bên trong object thật, this.save() là object thật tự gọi chính nó. this là object thật, không phải proxy. Lời gọi này không bao giờ đi qua thư ký, nên @Tx trên save bị bỏ qua.

Đường đi của lời gọi (trường hợp 3)

Main
proxy.placeOrder()→ proxy
proxy ($Proxy0 + TxProxy)
placeOrder không có @Tx→ real
real (OrderServiceImpl)
this.save()→ real (bỏ qua proxy)

Muốn @Tx chạy thì phải…

gọi save() qua proxy
proxy.save()→ BEGIN … COMMIT

Proxy chỉ chặn được những lời gọi đi vào từ bên ngoài. Lời gọi nội bộ qua this thì không đi qua proxy.

5 · Đây chính là cách Spring hoạt động

Khi bạn viết @Service có method gắn @Transactional, Spring không đưa cho bạn object thật. Nó tạo một proxy bọc quanh object thật, rồi @Autowired tiêm proxy vào những chỗ cần dùng. Spring docs viết: "Spring AOP uses either JDK dynamic proxies or CGLIB to create the proxy for a given target object."[Spring: Proxying Mechanisms] (CGLIB là cách tạo proxy bằng một class con, dùng được cả khi không có interface. Ý tưởng thì y hệt.)

Và Spring docs nói thẳng về trường hợp 3:

"any method calls that it may make on itself, such as this.bar() or this.foo(), are going to be invoked against the this reference, and not the proxy. [...] self invocation is not going to result in the advice associated with a method invocation getting a chance to run."[Spring: Understanding AOP Proxies]

@Transactional, @Async, @Cacheable... chỉ có tác dụng khi lời gọi đi qua proxy, tức là được gọi từ một bean khác.
Gọi nội bộ bằng this.method() (kể cả khi không viết chữ this) sẽ bỏ qua annotation đó, mà không có lỗi hay cảnh báo nào.

Cách xử lý phổ biến ngoài đời: tách method cần @Transactional sang một bean (service) khác, rồi gọi qua bean đó. Hoặc đặt @Transactional lên chính method được gọi từ bên ngoài (ở ví dụ này là placeOrder).

Câu phỏng vấn: "Vì sao @Transactional có lúc không chạy?"

"Spring áp dụng @Transactional bằng proxy: bean được tiêm vào các nơi khác thật ra là một proxy bọc object thật. Proxy mở transaction trước khi gọi method thật và commit hoặc rollback sau đó. Nếu một method trong cùng class gọi method @Transactional qua this, lời gọi đó đi thẳng vào object thật, không qua proxy, nên transaction không được mở. Cách sửa là tách method ra bean khác, hoặc đặt @Transactional ở method được gọi từ bên ngoài. Ngoài ra, method phải gọi được từ bên ngoài (thường là public) thì proxy mới chặn được."

7 · Thử thách: bỏ một dòng, mất hết phép thuật

Mở Tx.java, xoá (hoặc comment) dòng @Retention(RetentionPolicy.RUNTIME), rồi biên dịch lại và chạy:

javac *.java
java Main

Đoán trước: trường hợp 1 (proxy.save("sách")) còn in BEGIN/COMMIT không? Vì sao?

Xem đáp án 
1) proxy.save("sách")
    [code thật] lưu đơn hàng: sách          ← mất BEGIN/COMMIT

Không có @Retention(RUNTIME) thì mặc định annotation chỉ được ghi vào file .class, chứ không được giữ lại lúc chạy (mặc định là RetentionPolicy.CLASS). Reflection lúc chạy không còn thấy nhãn @Tx nữa, nên isAnnotationPresent trả về false.[RetentionPolicy Javadoc] Mọi annotation mà Spring đọc lúc chạy (@Transactional, @Service, @Autowired...) đều được khai báo với @Retention(RUNTIME). Nhớ khôi phục lại dòng đã xoá.

Thử thách thêm (tự viết code)

Sửa OrderServiceImpl hoặc Main sao cho trường hợp 3 (đặt đơn "vở") có BEGIN/COMMIT, mà không sửa TxProxy.java. Có ít nhất hai cách. Hãy gửi lời giải của bạn cho agent để được nhận xét.

Đào sâu: cái giá của reflection, và CGLIB
  • Chậm hơn và kém an toàn hơn gọi trực tiếp: method.invoke(...) phải tra cứu và kiểm tra lúc chạy. Lỗi gõ sai tên method chỉ lộ ra lúc chạy (NoSuchMethodException) chứ không bị javac bắt. Vì vậy reflection thường chỉ nằm trong framework, không nên rải trong code nghiệp vụ.
  • Bị module system chặn: như bài 10 và 11, muốn đọc field private của thư viện chuẩn thì phải có --add-opens. Đây là cơ chế bảo vệ từ Java 9, được siết chặt hơn từ Java 17.
  • JDK proxy cần interface: Proxy.newProxyInstance chỉ tạo được proxy theo interface. Nếu class không có interface, Spring dùng CGLIB để sinh ra một class con của class của bạn, rồi override các method để chèn thêm việc trước và sau. Vì là class con nên method final hoặc private không override được, và proxy không chặn được chúng. Đây là một lý do nữa khiến @Transactional trên method private không có tác dụng.
