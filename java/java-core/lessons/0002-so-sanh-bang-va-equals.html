So sánh mũi tên hay so sánh nội dung?

==, equals(), String pool và Integer cache: vì sao "hi" == "hi" lại ra true.

Sau bài này bạn sẽ Đoán đúng kết quả của == và equals() với String, Integer và object tự viết, đồng thời giải thích được vì sao bằng sơ đồ stack/heap.
Ôn lại Bài 1 (trả lời trong đầu trước khi mở)

(1) Biến Person p thực sự chứa gì? (2) Gọi m(p) thì thứ gì được copy?

Đáp án: (1) Một giá trị tham chiếu (mũi tên) tới object trên heap, hoặc null. (2) Chính giá trị tham chiếu đó. Object không bao giờ bị copy.

1. == so sánh giá trị của biến

Bài 1 đã cho thấy biến reference chứa mũi tên. Vậy == giữa hai biến reference so sánh hai mũi tên, tức là hỏi: “hai biến này có chỉ vào cùng một object không?”

“At run time, the result of == is true if the operand values are both null or both refer to the same object or array; otherwise, the result is false.” — JLS §15.21.3

Với primitive, biến chứa chính con số nên == so sánh con số. Bản chất không đổi: == luôn so sánh giá trị nằm trong biến. Chỉ là với reference, giá trị đó là mũi tên.

2. equals() là một method, nên hành vi tuỳ class

equals chỉ là một method thường của Object. Nếu class của bạn không override nó, bạn dùng bản mặc định, và bản mặc định chính là ==:

“The equals method for class Object implements the most discriminating possible equivalence relation on objects; that is, for any non-null reference values x and y, this method returns true if and only if x and y refer to the same object (x == y has the value true).” — Object.equals — Javadoc Java 21

String, Integer, List… đều override equals để so sánh nội dung. Còn class Person tự viết mà không override thì new Person("An").equals(new Person("An")) trả về false, vì đó là hai object khác nhau.

3. String pool: vì sao "hi" == "hi"

Hai literal giống nhau không tạo ra hai object. Spec đảm bảo chúng là cùng một instance:

“a string literal always refers to the same instance of class String. This is because string literals - or, more generally, strings that are the values of constant expressions - are ‘interned’ so as to share unique instances, as if by execution of the method String.intern.” — JLS §3.10.5 
String a = "hi";
String b = "hi";
String c = new String("hi");   // new LUÔN tạo object mới

Biểu thức hằng được tính lúc compile

“Strings concatenated from constant expressions are computed at compile time and then treated as if they were literals. Strings computed by concatenation at run time are newly created and therefore distinct.” — JLS §3.10.5 
String d = "h" + "i";          // hằng ⇒ compiler gộp thành "hi" ⇒ a == d là true
String h = "h";
String e = h + "i";            // h là biến thường ⇒ nối lúc runtime ⇒ object mới ⇒ a == e là false
final String fh = "h";
String f = fh + "i";           // fh là constant variable ⇒ lại là hằng ⇒ a == f là true
“Constant variable” là biến final kiểu primitive hoặc String, được khởi tạo bằng một biểu thức hằng (JLS §4.12.4). Ở Bài 5 bạn sẽ nhìn thấy compiler gộp hằng ngay trong bytecode.

4. Integer cache: cái bẫy của autoboxing

Integer x = 127 là boxing: Java gọi ngầm Integer.valueOf(127). Spec yêu cầu các giá trị nhỏ phải được dùng chung:

“If the value p being boxed is the result of evaluating a constant expression of type […] int […] and the result is […] an integer in the range -128 to 127 inclusive, then let a and b be the results of any two boxing conversions of p. It is always the case that a == b.” — JLS §5.1.7 
Integer x = 127, y = 127;   x == y   // true  (cùng object trong cache)
Integer m = 128, n = 128;   m == n   // false (mặc định: hai object khác nhau)
m.equals(n)                          // true
Ngoài khoảng −128..127 thì kết quả không được đảm bảo: cận trên của cache có thể nới rộng bằng -XX:AutoBoxCacheMax (Integer.java). Vì thế code đúng không bao giờ được dựa vào == với Integer.

Lỗi này hay gặp ở code thật: if (order.getId() == other.getId()) với kiểu Long chạy đúng khi test bằng id nhỏ, rồi sai ở production khi id vượt quá 127.

Quy tắc dùng hằng ngày

  • Dùng == cho primitive, enum, so sánh với null, hoặc khi bạn thật sự muốn hỏi “có cùng object không”.
  • Dùng equals() cho mọi trường hợp so sánh nội dung object, kể cả String và các wrapper như Integer, Long.
  • Nếu biến có thể là null, dùng Objects.equals(a, b) để tránh NullPointerException.

5. Luyện tập

Q1 (ôn Bài 1). Sau khi chạy đoạn sau, a bằng gì?

static void f(String s) { s = "B"; }
String a = "A"; f(a);
Gán lại tham số chỉ bẻ mũi tên trong frame của f. Hơn nữa String là immutable, nên không có cách nào sửa nội dung object "A".

Q2. new String("hi") == "hi"

new luôn tạo object mới trên heap, khác với instance đã intern của literal.

Q3. ("h" + "i") == "hi"

Cả hai vế đều là biểu thức hằng, nên compiler gộp thành literal "hi" và trỏ vào cùng instance đã intern.

Q4. Integer m = 128, n = 128; thì m == n ở cấu hình JVM mặc định là?

128 nằm ngoài khoảng cache bắt buộc (−128..127), nên mỗi lần boxing tạo một object mới.

Q5. String h = "h"; thì (h + "i") == "hi" là?

h không phải final nên không phải constant variable. Phép nối chạy lúc runtime và tạo String mới.

Q6. Person không override equals. new Person("An").equals(new Person("An")) là?

Bản equals mặc định của Object chính là ==, và đây là hai object khác nhau.

Q7. == giữa hai biến reference so sánh cái gì?

JLS §15.21.3: == ra true khi cả hai cùng refer tới một object. Nó không gọi equals hay hashCode.
