Khối static chạy khi nào?

Bài 5 · Class được "khởi tạo" lúc nào, theo thứ tự nào, và chuyện gì xảy ra khi nó khởi tạo thất bại

~30 phútCần biết: Bài 1 (JVM nạp class khi cần)Thư mục thực hành: lab/l0005

Học xong bài này, bạn sẽ:

  • Biết chính xác khối static { } chạy lúc nào và chạy mấy lần.
  • Trả lời được câu phỏng vấn kinh điển về thứ tự chạy giữa static và constructor của class cha, class con.
  • Đọc hiểu lỗi NoClassDefFoundError: Could not initialize class ... và biết tìm nguyên nhân thật của nó.

1 · Ôn bài 1 (trả lời trong đầu trước)

Khi chạy chương trình, JVM có nạp tất cả class ngay từ đầu không?
Kiểm traKhông. JVM rất lười: nó chỉ nạp một class khi thật sự cần dùng tới. Ở bài 1, Helper.class có trên ổ cứng nhưng không được nạp nếu không ai dùng. Bài hôm nay đi tiếp ý đó.

2 · Câu chuyện cửa hàng

Một cửa hàng có hai loại việc:

  • Việc của cửa hàng: dọn dẹp, bật đèn, mở cửa. Chỉ làm một lần, đúng lúc vị khách đầu tiên tới. Không có khách nào thì cửa hàng không mở.
  • Việc cho từng khách: lấy một cái ghế, rót một cốc nước. Khách nào tới cũng được làm, mỗi khách một lần.

Một class Java cũng có đúng hai loại việc như vậy:

Trong câu chuyệnTrong JavaChạy mấy lần?
Việc của cửa hàngKhối static { ... } và biến staticMột lần duy nhất cho cả chương trình
Việc cho từng kháchConstructor, chạy mỗi lần newMỗi object một lần

Việc "mở cửa hàng" có tên chính thức là khởi tạo class (class initialization): JVM chạy hết các khối static và gán giá trị cho các biến static của class đó.

3 · Tận mắt xem: static chạy lúc nào?

Mở WhenStatic.java:

public class WhenStatic {
    public static void main(String[] args) {
        System.out.println("1. main bắt đầu");
        System.out.println("2. sắp gọi Shop.open() lần đầu");
        Shop.open();
        System.out.println("3. sắp gọi Shop.open() lần hai");
        Shop.open();
    }
}

class Shop {
    static {
        System.out.println("   >>> [static] Dọn dẹp, mở cửa hàng (chỉ 1 lần)");
    }
    static void open() {
        System.out.println("   Phục vụ một khách");
    }
}

Đoán trước: dòng >>> [static] sẽ in ra ở đâu? Ngay đầu chương trình, sau dòng 2, hay in hai lần? Ghi ra giấy rồi chạy:

cd lab/l0005
javac WhenStatic.java
java WhenStatic
1. main bắt đầu
2. sắp gọi Shop.open() lần đầu
   >>> [static] Dọn dẹp, mở cửa hàng (chỉ 1 lần)
   Phục vụ một khách
3. sắp gọi Shop.open() lần hai
   Phục vụ một khách

Đọc kết quả từng dòng:

  1. Dòng 1 và 2 in ra trước khối static. Lúc này chưa ai đụng tới Shop, nên cửa hàng chưa mở.
  2. Shop.open() là lần đầu tiên chương trình dùng tới Shop. JVM nạp class Shop, chạy khối static, rồi mới chạy open().
  3. Lần gọi thứ hai, khối static không chạy lại, vì cửa hàng đã mở rồi.

Vậy cụ thể "dùng tới lần đầu" là những lúc nào? Có 4 trường hợp hay gặp:[JLS §12.4.1]

  • Tạo object: new Shop()
  • Gọi method static: Shop.open()
  • Đọc hoặc gán biến static: Shop.count (trừ hằng số, xem phần thử thách)
  • Một class con của Shop được khởi tạo, vì cha luôn được khởi tạo trước con
Khối static chạy đúng một lần, vào lần đầu tiên class được dùng tới. Không phải lúc chương trình bắt đầu.

4 · Cha và con: ai chạy trước?

Đây là câu phỏng vấn rất hay gặp. Mở Order.java:

class Parent {
    static { System.out.println("A. Parent static"); }
    Parent()  { System.out.println("C. Parent constructor"); }
}

class Child extends Parent {
    static { System.out.println("B. Child static"); }
    Child()   { System.out.println("D. Child constructor"); }
}

// trong main:
new Child();   // lần 1
new Child();   // lần 2

Đoán trước: sắp xếp A, B, C, D theo thứ tự in ra, cho cả lần 1 và lần 2.

javac Order.java
java Order
--- new Child() lần 1
A. Parent static
B. Child static
C. Parent constructor
D. Child constructor
--- new Child() lần 2
C. Parent constructor
D. Child constructor

Muốn mở chi nhánh (con) thì công ty mẹ (cha) phải được thành lập trước. Cả hai chỉ mở một lần (A rồi B).

Mỗi khách tới chi nhánh thì nhận "phần của công ty mẹ" trước, rồi tới "phần của chi nhánh" (C rồi D).

  • A → B: muốn khởi tạo Child thì JVM phải khởi tạo Parent trước.[JLS §12.4.2]
  • C → D: constructor của con luôn tự gọi super() (constructor của cha) đầu tiên. Ở bài 1 bạn đã thấy javac tự thêm lời gọi super() này.
  • Lần 2 chỉ có C, D: static đã chạy rồi, không chạy lại nữa.
Câu trả lời phỏng vấn mẫu

"Static của cha → static của con (chỉ một lần, lúc class được dùng lần đầu) → constructor của cha → constructor của con (mỗi lần new)."

5 · Bug thật: cửa hàng mở cửa thất bại

Chuyện gì xảy ra nếu khối static bị lỗi? Đây là tình huống rất hay gặp ngoài đời: class Config đọc biến môi trường trong khối static, nhưng trên server lại quên cấu hình biến đó. Mở Broken.java:

class Config {
    static String URL = loadUrl();          // chạy khi Config được khởi tạo
    static String loadUrl() {
        throw new IllegalStateException("thiếu biến môi trường DB_URL");
    }
}

// trong main: thử đọc Config.URL hai lần, mỗi lần bắt lỗi và in ra
javac Broken.java
java Broken
Lần 1: java.lang.ExceptionInInitializerError
Lần 2: java.lang.NoClassDefFoundError: Could not initialize class Config

Hai lần chạy cùng một dòng code mà ra hai lỗi khác nhau!

Lần đầu mở cửa hàng thì bị cháy. Chủ cửa hàng treo một tấm biển "Cửa hàng hỏng" và không bao giờ thử mở lại nữa.

Khách thứ hai tới chỉ thấy tấm biển. Tấm biển không ghi lý do cháy.

  1. Lần 1: JVM chạy phần static, gặp lỗi. Nó bọc lỗi gốc lại thành ExceptionInInitializerError ("lỗi khi khởi tạo"). Lỗi gốc (thiếu biến môi trường DB_URL) nằm bên trong.
  2. JVM đánh dấu class Config là hỏng vĩnh viễn cho tới khi tắt chương trình. Nó không thử khởi tạo lại.[JLS §12.4.2]
  3. Lần 2 trở đi: JVM chỉ báo NoClassDefFoundError: Could not initialize class Config. Đây là tấm biển "hỏng".

Cách debug lỗi này

Tên lỗi NoClassDefFoundError rất dễ gây hiểu lầm. Nhiều người đọc thấy "Class Not Found" là nghĩ thiếu file .class hoặc thiếu thư viện, rồi mất cả buổi kiểm tra classpath. Nhưng nếu thông báo có chữ "Could not initialize class" thì file vẫn còn nguyên. Vấn đề là khối static đã bị lỗi từ trước.

Cách tìm nguyên nhân thật:

  • Java 18 trở lên (máy bạn dùng Java 21): đọc dòng Caused by: ngay dưới lỗi. JVM đã đính kèm lỗi gốc vào đó.[JDK-8048190, sửa ở Java 18]
  • Java 8, 11, 17 (vẫn rất phổ biến ở các công ty): không có thông tin đó. Bạn phải cuộn log ngược lên để tìm dòng ExceptionInInitializerError đầu tiên. Lỗi thật nằm ở đó.
Thấy NoClassDefFoundError: Could not initialize class X → đừng đi tìm file bị thiếu. Hãy tìm ExceptionInInitializerError đầu tiên trong log: đó mới là lỗi thật trong phần static của X.

7 · Thử thách: lúc nào thì Box mở cửa?

Mở Challenge.java:

System.out.println("1. tạo mảng");
Box[] boxes = new Box[3];
System.out.println("2. đọc hằng số");
System.out.println("   MAX = " + Box.MAX);
System.out.println("3. đọc biến static thường");
System.out.println("   count = " + Box.count);

class Box {
    static final int MAX = 10;   // hằng số
    static int count = 5;        // biến static thường
    static { System.out.println("   >>> [static] Box được khởi tạo"); }
}

Câu hỏi: dòng >>> [static] Box được khởi tạo sẽ in ra ngay sau dòng 1, dòng 2 hay dòng 3? Gợi ý:

  • new Box[3] tạo một mảng 3 ô trống. Nó có tạo ra object Box nào không?
  • MAX là static final với giá trị viết sẵn. Ở bài 4, javac đã tự ghép "h" + "i" ngay lúc biên dịch. Liệu nó có làm điều tương tự với MAX?
javac Challenge.java
java Challenge
Xem đáp án 
1. tạo mảng
2. đọc hằng số
   MAX = 10
3. đọc biến static thường
   >>> [static] Box được khởi tạo
   count = 5
  • Sau dòng 1, không: new Box[3] chỉ tạo một mảng gồm 3 ô rỗng (null). Chưa có object Box nào được tạo, nên cửa hàng chưa cần mở.
  • Sau dòng 2, không: MAX là hằng số lúc biên dịch (compile-time constant). javac chép thẳng số 10 vào chỗ dùng, nên lúc chạy chương trình không cần hỏi Box nữa.[JLS §13.1]
  • Sau dòng 3, có: count là biến static thường, phải hỏi Box mới biết giá trị, nên Box được khởi tạo đúng lúc này.

Hệ quả thật khi đi làm: vì javac chép thẳng giá trị hằng số vào nơi dùng, nếu bạn đổi MAX trong một thư viện mà không biên dịch lại code đang dùng thư viện đó, code cũ vẫn dùng giá trị cũ.

Đào sâu: ba giai đoạn của một class trong JVM

Từ lúc JVM "thấy" một class tới lúc dùng được nó, class đi qua ba giai đoạn:[JVMS ch.5]

  1. Loading (nạp): tìm file .class và đọc vào bộ nhớ. Đây là việc của class loader.
  2. Linking (liên kết): kiểm tra bytecode hợp lệ (verify), rồi cấp chỗ cho biến static với giá trị mặc định (0, null, false).
  3. Initialization (khởi tạo): chạy khối static và gán giá trị thật cho biến static. Đây chính là phần "mở cửa hàng" của bài này.

Muốn xem khối static nằm đâu trong bytecode thì chạy javap -c Shop. javac gom mọi khối static và mọi lệnh gán biến static vào một method đặc biệt, hiện ra dưới dạng static {}; (tên thật bên trong là <clinit>, viết tắt của "class init"):

  static {};
    Code:
       0: getstatic     #7    // System.out
       3: ldc           #21   // String    >>> [static] Dọn dẹp, mở cửa hàng ...
       5: invokevirtual #15   // println
       8: return

Đó cũng là lý do stack trace của lỗi ở mục 5 có dòng at Config.<clinit>.
