Ai dọn rác trong Java, và khi nào thì dọn không nổi?

Bài 9 · Garbage Collector (GC), đọc GC log, và lỗi OutOfMemoryError ngoài production

Học xong bài này, bạn sẽ:

  • Biết khi nào một object trở thành rác và được GC dọn đi.
  • Đọc được một dòng GC log, và nhận ra dấu hiệu của memory leak (rò rỉ bộ nhớ).
  • Hiểu vì sao Java có GC mà vẫn bị OutOfMemoryError, và biết bật heap dump để điều tra.

1 · Ôn bài 4 (trả lời trong đầu trước)

Biến kiểu object (ví dụ String s) chứa gì: chứa nguyên object, hay chứa thứ gì khác?
Kiểm traBiến chỉ chứa tham chiếu, tức "tờ giấy ghi vị trí" của object. Object thật nằm trong một vùng nhớ chung tên là heap. Bài hôm nay hỏi tiếp: khi không còn tờ giấy nào ghi vị trí của một object, chuyện gì xảy ra với object đó?

2 · Câu chuyện: những quả bóng bay

Hình dung mỗi object là một quả bóng bay, và mỗi tham chiếu là một sợi dây.

  • Bóng đang có người cầm dây thì còn được dùng.
  • Một quả bóng có thể buộc vào một quả bóng khác. Chỉ cần quả kia đang có người cầm thì quả này cũng vẫn được giữ.
  • Bóng mà không còn ai cầm dây, kể cả gián tiếp, thì không ai dùng được nữa. Nó là rác.

Có một người dọn dẹp thỉnh thoảng đi một vòng: lần theo từng sợi dây bắt đầu từ tay mọi người, đánh dấu những quả bóng còn được giữ, rồi gom hết những quả còn lại đi.

Trong câu chuyệnTrong Java
Quả bóng bayObject nằm trong heap
Sợi dâyTham chiếu (biến, field, phần tử trong List...)
Tay người đang cầm dâyGC root: biến trong các method đang chạy, và biến static
Người dọn dẹpGC (Garbage Collector, trình dọn rác)
Một object là rác khi GC không thể đi tới nó từ bất kỳ GC root nào. GC không quan tâm bạn còn "định dùng" object đó hay không. Nó chỉ quan tâm object còn bị giữ hay không.

Vì vậy trong Java, bạn không bao giờ phải tự xoá object như ở C/C++. Chỉ cần thả hết dây ra là GC sẽ tự lo phần còn lại.[Oracle GC Tuning Guide]

3 · Thí nghiệm 1: tạo 1 000 MB rác trong 32 MB bộ nhớ

Mở Temp.java:

static byte[] last;   // chỉ giữ object MỚI NHẤT

public static void main(String[] args) {
    for (int i = 1; i <= 100_000; i++) {
        last = new byte[10_000];   // ~10 KB; object cũ không còn ai giữ → thành rác
    }
    System.out.println("Đã tạo 100 000 object (~1 000 MB). Xong, không lỗi!");
}

Mỗi vòng lặp tạo một mảng mới khoảng 10 KB và gán vào last. Mảng của vòng trước lúc đó không còn sợi dây nào, nên nó thành rác.

Ta sẽ chạy với cờ -Xmx32m, nghĩa là "heap được dùng tối đa 32 MB". Chương trình tạo tổng cộng khoảng 1 000 MB, tức gấp 30 lần heap. Đoán trước: chương trình có sập không?

cd lab/l0009
javac Temp.java Leak.java
java -Xmx32m Temp
Đã tạo 100 000 object (~1 000 MB). Xong, không lỗi!

Không sập. Vì sao? Bật nhật ký GC lên để xem người dọn dẹp làm việc:

java -Xmx32m -Xlog:gc Temp
[0.002s][info][gc] Using G1
[0.024s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 17M->1M(32M) 0.460ms
[0.026s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 19M->1M(32M) 0.229ms
... (khoảng 50 dòng tương tự)

Đọc một dòng GC log

Lấy dòng GC(1) Pause Young ... 19M->1M(32M) 0.229ms ra đọc từng phần:

Cứ heap đầy lên khoảng 19 MB thì GC dọn một lần, xuống lại còn 1 MB. Khoảng 50 lần như vậy là đủ gom hết 1 000 MB rác. Chương trình không bao giờ bị thiếu chỗ.

4 · Thí nghiệm 2: memory leak

Mở Leak.java. Khác biệt duy nhất: mỗi mảng mới được bỏ vào một List static và không bao giờ bị xoá ra.

static List<byte[]> cache = new ArrayList<>();   // static: sống suốt chương trình
...
cache.add(new byte[10_000]);                      // ~10 KB, bỏ vào cache, không bao giờ xoá

Theo câu chuyện bóng bay: cache là biến static, tức là một bàn tay cầm dây suốt đời chương trình. Mọi mảng trong List đều buộc vào nó, nên không quả bóng nào bị coi là rác. Đoán trước: chuyện gì xảy ra?

java -Xmx32m Leak
Đang giữ khoảng 10 MB
Đang giữ khoảng 20 MB
Đang giữ khoảng 30 MB
Sập sau 3199 object: java.lang.OutOfMemoryError: Java heap space

Chương trình chỉ cần khoảng 32 MB, ít hơn thí nghiệm 1 tới 30 lần, vậy mà lại sập. Xem nhật ký GC ngay trước lúc sập:

java -Xmx32m -Xlog:gc Leak | grep Pause | tail -4
GC(14) Pause Full (G1 Compaction Pause) 31M->31M(32M) 1.082ms
GC(15) Pause Full (G1 Compaction Pause) 31M->31M(32M) 3.193ms
GC(16) Pause Young (Concurrent Start) ... 31M->31M(32M) 0.150ms
GC(17) Pause Full (G1 Compaction Pause) 31M->1M(8M) 1.467ms
  • Pause Full nghĩa là GC đã dọn toàn bộ heap, lần dọn kỹ nhất và tốn thời gian nhất.
  • 31M->31M nghĩa là dọn xong mà không giảm được byte nào, vì mọi object vẫn đang bị cache giữ.
  • Không còn chỗ cho object mới, nên JVM ném OutOfMemoryError: Java heap space.
  • Dòng cuối 31M->1M: sau khi code bắt lỗi và gán cache = null (buông dây), GC dọn được ngay lập tức.
Memory leak trong Java không phải là "GC quên dọn". Nó là việc bạn vô tình vẫn giữ tham chiếu tới object không còn dùng nữa, thường gặp nhất là trong một List/Map static chỉ thêm vào mà không bao giờ xoá ra.
Dấu hiệu trong GC log: sau mỗi lần dọn, con số "sau" cứ tăng dần, cho tới khi trước bằng sau (31M->31M).

5 · Khi gặp chuyện này ở production

Ứng dụng chạy vài ngày thì chậm dần, rồi sập với OutOfMemoryError: Java heap space. Có hai việc nên làm ngay:

  1. Bật GC log (-Xlog:gc) để xem con số "sau khi dọn" có tăng dần theo thời gian không. Tăng dần là dấu hiệu leak.
  2. Bật heap dump tự động: thêm -XX:+HeapDumpOnOutOfMemoryError. Khi sập, JVM tự chụp ảnh toàn bộ heap ra một file .hprof. Mở file đó bằng công cụ phân tích (ví dụ Eclipse MAT, VisualVM) sẽ thấy object nào đang chiếm nhiều bộ nhớ nhất và ai đang giữ nó.[Oracle: Troubleshooting Memory Leaks]

Thử ngay trên máy bạn:

java -Xmx32m -XX:+HeapDumpOnOutOfMemoryError Leak
Dumping heap to java_pid386375.hprof ...
Heap dump file created [35671755 bytes in 0.017 secs]
Sập sau 3199 object: java.lang.OutOfMemoryError: Java heap space

(Số pid sẽ khác trên máy bạn. Nhớ xoá file .hprof sau khi xem xong, vì nó khá nặng.)

Câu phỏng vấn: "Java có GC rồi, sao vẫn bị memory leak?"

"GC chỉ dọn những object không còn đi tới được từ GC root (biến của các method đang chạy, biến static...). Nếu code vẫn giữ tham chiếu tới object không dùng nữa, ví dụ một Map static làm cache mà chỉ thêm không xoá, thì GC coi object đó vẫn đang được dùng và không dọn. Bộ nhớ tăng dần cho tới khi gặp OutOfMemoryError. Để điều tra, tôi bật GC log xem bộ nhớ sau mỗi lần dọn có tăng dần không, và bật HeapDumpOnOutOfMemoryError để phân tích xem ai đang giữ object."

7 · Thử thách: sửa leak

Nhiệm vụ: sửa Leak.java để cache giữ tối đa 1 000 phần tử (khoảng 10 MB). Khi đầy thì bỏ phần tử cũ nhất trước khi thêm phần tử mới. Cho vòng lặp chạy 50 000 lần (thay vì chạy mãi), và chương trình phải kết thúc không lỗi với -Xmx32m.

Gợi ý:

  1. Thêm hằng số static final int MAX = 1000;
  2. Trước khi cache.add(...), kiểm tra nếu cache.size() >= MAX thì cache.remove(0). Phần tử bị bỏ ra không còn ai giữ, nên nó thành rác.
  3. Chạy java -Xmx32m -Xlog:gc Leak và để ý: con số "sau khi dọn" giờ có còn tăng mãi không?
Xem lời giải 
import java.util.ArrayList;
import java.util.List;

public class Leak {
    static List<byte[]> cache = new ArrayList<>();
    static final int MAX = 1000;                      // giữ tối đa 1000 object (~10 MB)

    public static void main(String[] args) {
        for (int i = 1; i <= 50_000; i++) {
            if (cache.size() >= MAX) cache.remove(0);  // bỏ cái cũ nhất → nó thành rác
            cache.add(new byte[10_000]);
        }
        System.out.println("Xong 50 000 object, cache đang giữ " + cache.size() + " cái. Không lỗi!");
    }
}
Xong 50 000 object, cache đang giữ 1000 cái. Không lỗi!

Trong GC log, con số "sau khi dọn" giờ dừng ở khoảng 10 MB, đúng bằng phần cache đang giữ, thay vì tăng mãi cho tới lúc sập. Ngoài đời, bạn sẽ không tự viết cache như thế này, mà dùng thư viện có sẵn giới hạn kích thước (ví dụ Caffeine). Nhưng nguyên tắc vẫn y hệt: cache nào cũng phải có giới hạn.

Đào sâu: vì sao có "Young" và "Full"?

Người ta quan sát thấy đa số object chết rất trẻ: tạo ra, dùng trong một method, rồi bỏ đi ngay (giống mảng last ở thí nghiệm 1). Vì vậy G1 chia heap thành hai khu:[Oracle: G1 GC]

  • Young generation (khu trẻ): nơi object mới được tạo ra. Khu này được dọn thường xuyên và rất nhanh (Pause Young, dưới 1 ms trong thí nghiệm của ta), vì hầu hết object ở đây đã là rác.
  • Old generation (khu già): object sống sót qua vài lần dọn sẽ được chuyển sang đây. Khu này ít khi được dọn hơn.

Pause Full là khi GC phải dọn toàn bộ heap, gồm cả khu già. Đây là lần dọn chậm nhất. Thấy Pause Full xuất hiện thường xuyên trong log production là dấu hiệu heap đang quá tải (leak, hoặc -Xmx quá nhỏ so với nhu cầu thật).

Trong Leak.java, ở cuối bài thí nghiệm bạn cũng sẽ thấy (G1 Compaction Pause): GC dồn các object còn sống lại sát nhau để tạo ra chỗ trống liền mạch. Chi tiết về tuning G1 sẽ để dành cho một bài sau.
