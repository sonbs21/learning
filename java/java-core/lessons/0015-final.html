final khoá cái gì, và không khoá cái gì?

Bài 15 · final cho biến, field, method, class. Hiểu lầm phổ biến nhất: "final List thì không sửa được"

~30 phútCần biết: Bài 4 (tham chiếu, String immutable)Thư mục thực hành: lab/l0015

Học xong bài này, bạn sẽ:

  • Biết chính xác final khoá cái gì ở 4 chỗ: biến, field, method và class.
  • Không còn nhầm "biến final" với "object không sửa được".
  • Viết được một class thật sự bất biến (immutable), và hiểu vì sao điều đó quan trọng với thread.

1 · Ôn bài 4 (trả lời trong đầu trước)

Biến kiểu object (ví dụ List<String> ds) chứa gì?
Kiểm traNó chứa một tham chiếu, tức "tờ giấy ghi vị trí" của object. Object thật (tấm bảng) nằm trên heap. Giữ hình ảnh này trong đầu, vì cả bài hôm nay dựa trên nó.

2 · final trên biến: khoá tờ giấy, không khoá tấm bảng

Bạn có một tờ giấy ghi "giỏ hàng ở ô số 7". final nghĩa là tờ giấy này được ép plastic: không ai sửa được dòng chữ "ô số 7" thành "ô số 9".

Nhưng cái giỏ hàng ở ô số 7 thì vẫn là một giỏ hàng bình thường. Ai cũng có thể bỏ thêm đồ vào, hoặc lấy đồ ra.

Mở lab/l0015/FinalList.java:

final List<String> gioHang = new ArrayList<>();
gioHang.add("sách");          // sửa NỘI DUNG object → được phép
gioHang.add("bút");
gioHang.remove("sách");
System.out.println("gioHang = " + gioHang);
// gioHang = new ArrayList<>(); // gán biến sang object khác → lỗi biên dịch

Đoán trước: có biên dịch được không? Nếu được thì in ra gì?

cd lab/l0015
javac FinalList.java && java FinalList
gioHang = [bút]

add và remove chạy thoải mái. Giờ thử gán lại biến final. File loi/ReassignFinal.java cố tình làm việc này:

final int soLuong = 5;
soLuong = 6;

final List<String> gioHang = new ArrayList<>();
gioHang = new ArrayList<>();
javac loi/ReassignFinal.java
loi/ReassignFinal.java:7: error: cannot assign a value to final variable soLuong
        soLuong = 6;
        ^
loi/ReassignFinal.java:10: error: cannot assign a value to final variable gioHang
        gioHang = new ArrayList<>();
        ^
2 errors

JLS nói đúng điều này: "If a final variable holds a reference to an object, then the state of the object may be changed by operations on the object, but the variable will always refer to the same object."[JLS §4.12.4]

final trên biến = không được gán lại biến đó. Với biến primitive (int...) thì giá trị cố định luôn. Với biến object thì chỉ tham chiếu cố định, còn object vẫn sửa được như thường.
final ≠ immutable (bất biến).

3 · Lambda và "effectively final"

Có một chỗ bạn sẽ đụng phải final mà không hề viết chữ final. File loi/LambdaCount.java:

int dem = 0;
List.of("a", "b", "c").forEach(s -> dem++);
javac loi/LambdaCount.java
loi/LambdaCount.java:6: error: local variables referenced from a lambda expression must be final or effectively final
        List.of("a", "b", "c").forEach(s -> dem++);
                                            ^

Biến cục bộ dùng bên trong lambda phải là final, hoặc effectively final: không có chữ final nhưng không bao giờ bị gán lại. Lý do: biến cục bộ nằm trên stack của method (bài 2), còn lambda có thể chạy sau, ở một thread khác (bài 14). Java chỉ cho lambda chép giá trị của biến, nên giá trị đó không được phép thay đổi.[JLS §15.27.2] Muốn đếm trong lambda thì dùng AtomicInteger (bài 10), hoặc tốt hơn là count() của Stream.

String là một class final.[JLS §8.1.1.2] Nhớ lại bài 4: String được nhiều biến dùng chung trong String pool nên phải bất biến. Nếu ai cũng kế thừa được String, người ta có thể viết một class con "trông như String" nhưng sửa được nội dung, và phá vỡ mọi đảm bảo đó.

Nối với bài 12: Spring tạo proxy bằng CGLIB, tức là sinh ra một class con rồi override method. Method final (hay class final) thì không override được, nên @Transactional đặt trên đó sẽ không có tác dụng.[JLS §8.4.3.3]

5 · Bẫy thật: class "trông như bất biến" nhưng vẫn bị sửa

Một class có field private final và không có setter thì trông rất an toàn. Mở DonHangHo.java:

static class DonHang {
    private final List<String> monHang;
    DonHang(List<String> monHang) { this.monHang = monHang; }
    List<String> getMonHang() { return monHang; }
}

List<String> ds = new ArrayList<>(List.of("sách", "bút"));
DonHang don = new DonHang(ds);
ds.add("laptop");               // sửa list GỐC bên ngoài
don.getMonHang().clear();       // sửa qua getter

Đoán trước: sau hai dòng cuối, đơn hàng còn những gì?

javac DonHangHo.java && java DonHangHo
1. Đơn hàng lúc tạo: [sách, bút]
2. Sau khi sửa ds:   [sách, bút, laptop]
3. Sau getter.clear: []

Đơn hàng bị sửa từ bên ngoài, dù field là private final. Lý do: final chỉ khoá tờ giấy monHang. Mà tờ giấy đó trỏ tới đúng cái list người gọi đang cầm (chung tấm bảng), và getter lại đưa tờ giấy ra ngoài cho bất kỳ ai.

Cách sửa: chép ra một bản không sửa được

DonHangKin.java chỉ đổi đúng một dòng trong constructor:

DonHang(List<String> monHang) { this.monHang = List.copyOf(monHang); }
javac DonHangKin.java && java DonHangKin
1. Sau khi sửa ds:   [sách, bút]
2. getter.clear() bị chặn: java.lang.UnsupportedOperationException

List.copyOf tạo ra một list mới (tấm bảng riêng) và không sửa được (tấm bảng ép plastic).[List.copyOf] Sửa list gốc không còn ảnh hưởng gì, còn sửa qua getter thì bị chặn ngay.

Công thức một class bất biến thật sự:[Oracle: Immutable Objects]
  1. Mọi field là private final, không có setter.
  2. Field nào trỏ tới object sửa được (List, Map, mảng, Date...) thì chép ra bản riêng khi nhận vào (List.copyOf), và không đưa bản gốc ra ngoài.
  3. Class final (hoặc dùng record) để không ai kế thừa rồi phá luật.

6 · Vì sao điều này quan trọng với thread?

Nhớ lại bài 13: thread khác có thể "không nhìn thấy" giá trị mới, thậm chí thấy một object chưa khởi tạo xong. Field final có một đảm bảo đặc biệt trong Java Memory Model:

"A thread that can only see a reference to an object after that object has been completely initialized is guaranteed to see the correctly initialized values for that object's final fields."[JLS §17.5]

Nói đơn giản: miễn constructor không để lộ this ra ngoài khi chưa chạy xong, thì mọi thread khác đều thấy đúng giá trị của các field final, mà không cần volatile hay synchronized. Kết hợp với tính bất biến (không ai sửa được), object immutable là loại object an toàn nhất để chia sẻ giữa nhiều thread. Đó là lý do String, Integer, List.of(...) và record đều được thiết kế bất biến.

Câu phỏng vấn: "final List thì có thêm phần tử được không? final khác immutable thế nào?"

"Được. final trên biến chỉ cấm gán lại biến đó, tức là tham chiếu không đổi, chứ object mà nó trỏ tới vẫn sửa được, nên final List vẫn add được. Immutable nghĩa là trạng thái của object không thể thay đổi sau khi tạo. Để làm một class immutable: các field private final, không có setter, chép phòng thủ (defensive copy) các field có thể bị sửa như List.copyOf, và đánh dấu class là final hoặc dùng record. Ngoài ra final trên method thì cấm override, trên class thì cấm kế thừa, ví dụ String. Field final còn được JMM đảm bảo hiển thị đúng cho các thread khác sau khi constructor chạy xong."

8 · Thử thách: tự làm một class bất biến

Nhiệm vụ: viết lại DonHang dưới dạng record (Java 16+) sao cho chạy lại thí nghiệm ở mục 5 thì đơn hàng không bị sửa, cả khi sửa list gốc lẫn khi sửa qua getter.

Gợi ý: record tự sinh constructor, getter, equals và hashCode, và mọi field của record đều là private final. Nhưng record không tự chép list cho bạn. Bạn cần viết một compact constructor:

record DonHang(List<String> monHang) {
    DonHang {
        // viết gì ở đây?
    }
}
Xem lời giải 
record DonHang(List<String> monHang) {
    DonHang {
        monHang = List.copyOf(monHang);   // gán lại THAM SỐ trước khi record gán vào field final
    }
}
Sau khi sửa ds: [sách, bút]
clear bị chặn: java.lang.UnsupportedOperationException

Trong compact constructor, monHang là tham số chứ không phải field. Bạn gán cho nó bản chép, rồi record mới tự gán tham số đó vào field final. Getter monHang() trả về bản không sửa được, nên clear() sẽ ném UnsupportedOperationException.[JLS §8.10.4] Hãy tự viết thử và chạy để kiểm chứng, rồi gửi code cho agent để được nhận xét.

Đào sâu: final có làm code chạy nhanh hơn không?

Một lời khuyên cũ hay gặp: "đánh dấu method final để JVM chạy nhanh hơn". Với JVM hiện đại thì điều này gần như không còn đúng. JIT (bài 6) tự quan sát xem lúc chạy method có thực sự bị override hay không, rồi tối ưu (inline) tương ứng, dù bạn có viết final hay không. Vì vậy hãy dùng final vì thiết kế (cấm gán lại, cấm override, làm object bất biến), không phải vì hiệu năng.

Ngoại lệ đã gặp ở bài 5: static final với giá trị viết sẵn là compile-time constant. javac chép thẳng giá trị đó vào nơi dùng, nên việc đọc nó không kích hoạt khởi tạo class.
