1 · Ôn bài 9 (trả lời trong đầu trước)

Ở cuối bài 9 có nhắc một điểm yếu của HashMap khi dùng với nhiều thread. Điểm yếu đó là gì?
Kiểm traHashMap không thread-safe: nhiều thread cùng put có thể làm mất dữ liệu. Hôm nay bạn sẽ tận mắt thấy điều đó, và hiểu tận gốc vì sao.

2 · Thread là gì?

Từ trước tới giờ, các chương trình của ta chỉ có một dòng chạy: lệnh này xong mới tới lệnh kia. Một thread (luồng) là một dòng chạy như vậy. Một chương trình có thể có nhiều thread chạy cùng lúc, mỗi thread làm việc riêng của nó. Máy bạn có 16 lõi CPU, nên có thể chạy thật sự 16 thread song song.

Thread t1 = new Thread(task);   // tạo thread, giao cho nó việc "task"
t1.start();                     // bắt đầu chạy (song song với main)
t1.join();                      // main đứng chờ t1 chạy xong

Ngoài đời, bạn dùng thread mỗi ngày mà không để ý: server Spring Boot (Tomcat) phục vụ mỗi request bằng một thread, nên 100 người dùng cùng lúc tức là 100 thread chạy cùng lúc.

3 · Thí nghiệm: hai thread cùng đếm

Mở Race.java. Hai thread, mỗi thread tăng biến chung count thêm 100 000 lần:

static int count = 0;

Runnable task = () -> {
    for (int i = 0; i < 100_000; i++) {
        count++;
    }
};
// tạo t1, t2 cùng chạy task, start cả hai, rồi join chờ cả hai xong

Đoán trước: 2 × 100 000 = 200 000. Kết quả có đúng 200 000 không?

cd lab/l0010
javac *.java
java Race
java Race
java Race
Mong đợi: 200000, thực tế: 105052
Mong đợi: 200000, thực tế: 112294
Mong đợi: 200000, thực tế: 109479

(Số trên máy bạn sẽ khác, và khác nhau sau mỗi lần chạy.)

Mất gần một nửa, và mỗi lần chạy mất một số lượng khác nhau. Không có lỗi nào được báo, chương trình chỉ âm thầm cho ra kết quả sai. Đây là kiểu bug đáng sợ nhất.

4 · Vì sao? count++ không phải một bước

Ở bài 1 ta đã biết đọc bytecode. Xem count++ thực sự là gì:

javap -c -p Race
 8: getstatic  count    // 1. ĐỌC giá trị count
11: iconst_1
12: iadd                // 2. CỘNG thêm 1
13: putstatic  count    // 3. GHI kết quả lại vào count

Một dòng count++ thật ra là 3 bước riêng biệt: đọc → cộng → ghi.[Oracle Tutorial: Thread Interference] Giữa các bước đó, thread khác hoàn toàn có thể chen vào.

Hai thu ngân cùng cập nhật một con số trên bảng kiểm kê, đang ghi 5:

  • Thu ngân A nhìn bảng: 5. Tính nhẩm: 5 + 1 = 6.
  • Đúng lúc đó, thu ngân B cũng nhìn bảng: vẫn là 5. Tính nhẩm: 6.
  • A xoá bảng, viết 6. B xoá bảng, viết 6.

Hai người đều bán được hàng, nhưng con số chỉ tăng 1. Một lần tăng đã biến mất.

Thời điểmThread 1Thread 2count
1đọc count → 55
2đọc count → 55
3cộng → 65
4cộng → 65
5ghi 66
6ghi 66 (đáng lẽ 7)

Khi kết quả phụ thuộc vào việc thread nào chạy trước, thread nào chen vào giữa, ta gọi đó là race condition (tình trạng tranh chấp). Lặp 200 000 lần thì chuyện "chen ngang" xảy ra hàng chục nghìn lần.

Một thao tác đọc → sửa → ghi trên dữ liệu dùng chung giữa nhiều thread mà không có bảo vệ gì thì sẽ mất dữ liệu. count++, x = x + 1, map.put(...) đều thuộc loại này.

5 · Cách sửa 1: synchronized, khoá cửa lại

Đặt bảng kiểm kê vào một căn phòng có một chìa khoá duy nhất. Ai muốn sửa con số thì phải cầm chìa, vào phòng, sửa xong mới ra trả chìa. Người khác muốn sửa thì đứng chờ ngoài cửa.

Mở FixSync.java:

static final Object lock = new Object();   // "chìa khoá"
...
synchronized (lock) {    // mỗi lúc chỉ MỘT thread được vào
    count++;
}
java FixSync
Mong đợi: 200000, thực tế: 200000

Khối synchronized đảm bảo ba bước đọc → cộng → ghi của một thread chạy xong trọn vẹn rồi thread khác mới được vào.[Oracle Tutorial: Intrinsic Locks] Cái giá phải trả: các thread phải xếp hàng chờ nhau, nên chậm hơn.

6 · Cách sửa 2: AtomicInteger, máy đếm bấm

Thay bảng viết tay bằng một máy đếm bấm tay: mỗi lần bấm, số tự nhảy lên 1. Không ai phải "đọc, tính nhẩm, rồi viết". Một cú bấm là trọn vẹn, không thể bị chen ngang.

Mở FixAtomic.java:

static AtomicInteger count = new AtomicInteger();
...
count.incrementAndGet();   // tăng 1, làm trọn vẹn trong một bước
java FixAtomic
Mong đợi: 200000, thực tế: 200000

AtomicInteger dùng một lệnh đặc biệt của CPU để làm cả "đọc → cộng → ghi" trong một bước không thể chia cắt (gọi là atomic, nguyên tử).[AtomicInteger Javadoc] Với một biến đếm đơn giản, đây là lựa chọn gọn và nhanh nhất.

Tình huốngNên dùng
Đếm, cộng dồn một con số dùng chungAtomicInteger / AtomicLong
Map dùng chung giữa nhiều threadConcurrentHashMap
Nhiều bước phải đi cùng nhau (ví dụ trừ tiền tài khoản A và cộng vào tài khoản B)synchronized (hoặc lock)

7 · Chuyện này xảy ra ở đâu khi đi làm?

Trong Spring, mỗi @Service hay @Controller mặc định chỉ có một object duy nhất (singleton).[Spring: Bean Scopes] Mà mỗi request lại chạy trên một thread riêng. Nghĩa là mọi request cùng dùng chung các field của service đó:

@Service
public class ViewService {
    private int views = 0;                          // dùng chung cho MỌI request
    private Map<Long, Product> cache = new HashMap<>(); // cũng dùng chung

    public void onView() { views++; }               // race condition!
}

Lúc test một mình trên máy thì đếm đúng. Lên production, 200 người xem cùng lúc thì số lượt xem bị thiếu, còn cache có thể mất dữ liệu. Cách sửa: AtomicInteger cho views, ConcurrentHashMap cho cache. Tốt hơn nữa là thiết kế service không giữ dữ liệu thay đổi trong field.

Câu phỏng vấn: "Race condition là gì? Sửa thế nào?"

"Race condition là khi nhiều thread cùng đọc và ghi một dữ liệu dùng chung, và kết quả phụ thuộc vào thứ tự chen ngang của các thread. Ví dụ kinh điển là count++: nó gồm ba bước đọc, cộng, ghi, nên hai thread có thể cùng đọc một giá trị cũ và một lần tăng bị mất. Cách sửa: dùng synchronized để chỉ một thread vào một lúc, hoặc dùng class atomic như AtomicInteger, hoặc collection thread-safe như ConcurrentHashMap. Trong Spring, bean mặc định là singleton, nên field có thể thay đổi trong service là nguồn race condition rất phổ biến."

9 · Thử thách: sửa MapRace.java

MapRace.java cho hai thread cùng put 50 000 phần tử (mỗi thread một khoảng key riêng, không trùng nhau) vào một HashMap dùng chung. Đoán trước rồi chạy:

java MapRace
Mong đợi: 100000 phần tử, thực tế: 72847

Hai thread không hề dùng chung key nào, vậy mà vẫn mất khoảng 25%. Lý do: cả hai cùng sửa cấu trúc bên trong của HashMap (các ngăn, biến size, lúc resize...). Bài 9 đã cho thấy mấy thứ đó đều là "đọc, sửa, ghi". Javadoc của HashMap cảnh báo rõ: "Note that this implementation is not synchronized."[HashMap Javadoc]

Nhiệm vụ: sửa đúng 2 dòng trong MapRace.java để luôn ra 100 000.

Xem lời giải 
import java.util.concurrent.ConcurrentHashMap;     // dòng 1: đổi import
...
Map<Integer, Integer> map = new ConcurrentHashMap<>();   // dòng 2: đổi class
Mong đợi: 100000 phần tử, thực tế: 100000

Vì biến map khai báo kiểu Map (interface), bạn chỉ cần đổi chỗ new, phần còn lại của code giữ nguyên. Đây là một lợi ích thực tế của việc "khai báo theo interface".[ConcurrentHashMap Javadoc]

Đào sâu: còn một vấn đề nữa, "nhìn thấy" (visibility)

Race condition không phải là vấn đề duy nhất của thread. Mỗi lõi CPU có bộ nhớ đệm (cache) riêng, và JIT (bài 6) có thể tối ưu bằng cách giữ giá trị của biến trong thanh ghi. Vì vậy một thread ghi giá trị mới vào biến, nhưng thread khác có thể không nhìn thấy giá trị đó, thậm chí rất lâu.

synchronized giải quyết cả hai vấn đề: vừa cho một thread vào một lúc, vừa đảm bảo thread vào sau nhìn thấy những gì thread trước đã ghi. Ngoài ra còn từ khoá volatile, chỉ lo phần "nhìn thấy" chứ không làm count++ trở nên an toàn. Bộ quy tắc đầy đủ về chuyện này gọi là Java Memory Model, sẽ là chủ đề của một bài sau.
