Vì sao cần Spring?

Bài 1 · Hiểu vấn đề mà Spring giải quyết, rồi để Spring tự tạo object cho bạn

~40 phútCần biết: class, interface, constructor trong JavaLab: ./lab

Mọi thứ trong Spring (REST API, database, security…) đều đứng trên một ý tưởng duy nhất. Nắm được ý tưởng đó ở bài này thì các bài sau sẽ dễ hơn rất nhiều. Ta bắt đầu bằng code Java thuần, chưa có Spring.

1 · Bài toán: một cửa hàng online

Khi khách đặt hàng, hệ thống tạo đơn và gửi email cảm ơn. Cách viết đầu tiên ai cũng nghĩ tới là:

public class OrderService {

    private final ConsoleEmailSender emailSender = new ConsoleEmailSender();

    public void placeOrder(String customer) {
        System.out.println("Đã tạo đơn hàng cho " + customer);
        emailSender.send(customer, "Cảm ơn bạn đã đặt hàng!");
    }
}

Code chạy được. Nhưng hãy thử hình dung ba tình huống rất thật:

  • Sếp muốn chuyển sang gửi SMS. Bạn phải mở OrderService ra sửa, dù logic đặt hàng không hề thay đổi.
  • Bạn muốn viết test cho placeOrder. Mỗi lần chạy test là một lần gửi email thật, và bạn không có cách nào thay bằng bản giả.
  • ConsoleEmailSender lại cần thêm một SmtpConfig, SmtpConfig lại cần thêm thứ khác… và OrderService phải tự new cả chuỗi đó.

Gốc rễ của cả ba: OrderService tự quyết định và tự tạo thứ nó cần dùng.

2 · Cách sửa: đừng tự tạo, hãy nhận từ bên ngoài

Ta tách ra một interface mô tả việc cần làm (gửi tin), và cho OrderService nhận nó qua constructor:

public interface EmailSender {
    void send(String to, String message);
}

public class OrderService {

    private final EmailSender emailSender;

    public OrderService(EmailSender emailSender) {   // nhận từ bên ngoài
        this.emailSender = emailSender;
    }
    // placeOrder giữ nguyên
}

// Ở hàm main, CHÍNH BẠN lắp ráp các object:
EmailSender sender = new ConsoleEmailSender();
OrderService orderService = new OrderService(sender);

Giờ muốn đổi sang SMS thì chỉ cần truyền vào một SmsSender, còn khi test thì truyền một bản giả. OrderService không phải sửa dòng nào.

Đưa vào cho một object những thứ nó cần, thay vì để nó tự tạo, gọi là Dependency Injection (DI), tức "tiêm phụ thuộc". Ở đây, EmailSender là dependency (phụ thuộc) của OrderService.

Còn một vấn đề nữa. App thật có hàng trăm class, và hàm main sẽ thành một đống new lắp ráp bằng tay khổng lồ. Ai sẽ làm việc lắp ráp đó?

3 · Spring: thuê một "thợ lắp ráp"

Spring có sẵn một object đặc biệt gọi là container. Trong code, container có tên là ApplicationContext. Bạn chỉ cần đánh dấu "class này hãy quản lý giúp tôi" bằng @Component, còn lại container lo:

  1. Khi app khởi động, Spring quét package chứa class main (dev.lab) để tìm các class có @Component.
  2. Spring thấy OrderService có constructor cần một EmailSender, và thấy ConsoleEmailSender chính là một EmailSender.
  3. Spring tạo ConsoleEmailSender trước, rồi tự truyền nó vào constructor của OrderService.
  4. Spring giữ các object này trong container. Bạn cần object nào thì xin container object đó.

Object do container tạo, lắp ráp và quản lý được gọi là bean. [docs]

"Inversion of Control" (IoC) là gì? Trước đây, class tự điều khiển việc tạo các dependency của nó. Bây giờ quyền đó được đảo ngược và chuyển sang cho container. Docs của Spring viết rõ: DI là một dạng cụ thể của IoC, trong đó object chỉ khai báo thứ nó cần (qua constructor…), còn container tiêm thứ đó vào khi tạo bean. [docs]

Spring và Spring Boot khác nhau ở đâu? Container là của Spring Framework. Spring Boot giúp khởi động Spring thật nhanh: chỉ một dòng SpringApplication.run(...) là đã có container chạy, không cần cấu hình gì thêm.

4 · Thực hành

Lab 1 · ~20 phút

Project lab/ đã có sẵn file LabApplication.java. Bạn tự gõ code dưới đây vào thư mục lab/src/main/java/dev/lab/. Hãy gõ chứ đừng copy-paste, vì gõ tay giúp bạn để ý từng chi tiết.

  1. EmailSender.java 
    package dev.lab;

public interface EmailSender {
    void send(String to, String message);
}
  2. ConsoleEmailSender.java: "gửi" bằng cách in ra màn hình 
    package dev.lab;

import org.springframework.stereotype.Component;

@Component
public class ConsoleEmailSender implements EmailSender {

    @Override
    public void send(String to, String message) {
        System.out.println("Gửi email tới " + to + ": " + message);
    }
}
  3. OrderService.java: để ý là không có chữ new nào 
    package dev.lab;

import org.springframework.stereotype.Component;

@Component
public class OrderService {

    private final EmailSender emailSender;

    public OrderService(EmailSender emailSender) {
        this.emailSender = emailSender;
    }

    public void placeOrder(String customer) {
        System.out.println("Đã tạo đơn hàng cho " + customer);
        emailSender.send(customer, "Cảm ơn bạn đã đặt hàng!");
    }
}
  4. Sửa LabApplication.java để xin container bean OrderService: 
    package dev.lab;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ApplicationContext;

@SpringBootApplication
public class LabApplication {

    public static void main(String[] args) {
        ApplicationContext context = SpringApplication.run(LabApplication.class, args);

        OrderService orderService = context.getBean(OrderService.class);
        orderService.placeOrder("an@example.com");
    }
}
  5. Chạy app: 
    cd lab
mvn -o -q spring-boot:run
    Trước khi chạy, hãy đoán: có in ra 2 dòng không? Ai đã gọi new ConsoleEmailSender()?
Kết quả mong đợi 
Đã tạo đơn hàng cho an@example.com
Gửi email tới an@example.com: Cảm ơn bạn đã đặt hàng!

Trong code của bạn không có dòng new nào cả. Spring đã tạo cả hai object và lắp chúng lại với nhau.

Thí nghiệm A: làm hỏng có chủ đích

Xoá dòng @Component trong ConsoleEmailSender rồi chạy lại. Đoán trước xem chuyện gì sẽ xảy ra, sau đó đọc kỹ thông báo lỗi.

Lỗi bạn sẽ thấy 
APPLICATION FAILED TO START

Description:
Parameter 0 of constructor in dev.lab.OrderService
required a bean of type 'dev.lab.EmailSender' that could not be found.

Action:
Consider defining a bean of type 'dev.lab.EmailSender' in your configuration.

Đọc lỗi này theo từng ý: "Tham số số 0 trong constructor của OrderService cần một bean kiểu EmailSender, nhưng container không có bean nào như vậy." Spring không biết đến ConsoleEmailSender nữa vì class đó đã mất @Component. Bạn sẽ gặp lỗi này rất nhiều khi đi làm, nên nhớ kỹ cách đọc nó. Đọc xong thì thêm @Component trở lại.

Thí nghiệm B: hai ứng viên

Tạo thêm SmsSender.java, cũng có @Component và cũng implements EmailSender (in ra "Gửi SMS tới…"). Chạy lại. Lần này Spring sẽ chọn class nào?

Lỗi bạn sẽ thấy 
Parameter 0 of constructor in dev.lab.OrderService
required a single bean, but 2 were found:
	- consoleEmailSender: defined in file [.../ConsoleEmailSender.class]
	- smsSender: defined in file [.../SmsSender.class]

Action:
Consider marking one of the beans as @Primary, ... or using @Qualifier ...

Spring không đoán bừa. Có hai bean cùng khớp thì nó dừng lại và bắt bạn chọn. Để ý thêm: tên bean mặc định là tên class với chữ cái đầu viết thường (consoleEmailSender). @Primary và @Qualifier là chủ đề của bài sau. Giờ bạn xoá SmsSender.java đi.
